Kinds do manifesto

Cada Kind com um template COMPLETO e funcional — todos os campos, com os defaults e um comentário. Aplica um só com delonix <grupo> apply -f, ou todos de uma vez com delonix stack apply (ordem por dependência: Secret → Network → NetworkRoute → Volume → Image → VirtualMachine → Container → Pod → Ingress → NetworkPolicy → HTTPRoute → Gateway). Os antigos kind: Storage, ShareVolume e Egress foram removidos: a capacidade vive agora em blocos do Volume (nfs:/cifs:/webdav:/share:) e do NetworkPolicy (direction: egress) — aplicá-los pelo nome antigo dá erro, a apontar o substituto. A lista completa, com os grupos e o que cada documento se torna, está em Estrutura de recursos.

Each Kind with a COMPLETE, functional template — every field, with defaults and a comment. Apply just one with delonix <group> apply -f, or all at once with delonix stack apply (dependency order: Secret → Network → NetworkRoute → Volume → Image → VirtualMachine → Container → Pod → Ingress → NetworkPolicy → HTTPRoute → Gateway). The former kind: Storage, ShareVolume and Egress were removed: the capability now lives in blocks on Volume (nfs:/cifs:/webdav:/share:) and on NetworkPolicy (direction: egress) — applying them by the old name errors with the replacement. The full list, with the groups and what each document becomes, is in Resource structure.

Desde a v0.47.0 o apply converge: o stack plan diz o que mudaria e porquê, e o apply reconfigura portas, volumes, redes, memória e CPU a quente, sem mudar o PID — recusando, com o nome do campo, o que obrigaria a recriar (a não ser com --replace). Sem ficheiro de estado: o último spec aplicado vive no próprio recurso. Continua fail-fast e sem rollback, e é convergência a pedido — não um loop. Os templates abaixo são os ficheiros reais em examples/.

Since v0.47.0 apply converges: stack plan says what would change and why, and apply reconfigures ports, volumes, networks, memory and CPU hot, with the PID unchanged — refusing, by field name, anything that would need a recreate (unless you pass --replace). No state file: the last applied spec lives on the resource itself. Still fail-fast and without rollback, and still convergence on demand — not a loop. The templates below are the real files in examples/.

Secret

Um segredo do cofre cifrado em repouso. Consumido por run --secret/--secret-files e por passwordSecret do Storage. Os valores NUNCA ficam no registo do container em texto — são resolvidos no arranque a partir do NOME.

A secret from the vault, encrypted at rest. Consumed by run --secret/--secret-files and by Storage's passwordSecret. Values are NEVER kept in the container's registry as plaintext — they're resolved at startup from the NAME.

# ============================================================================
# kind: Secret — a bag of KEY=value pairs, encrypted at rest (ADR-0020)
#
# A Secret holds key=value pairs encrypted at rest (XChaCha20-Poly1305 under
# the host master key). It is consumed by `Container.secret` (as env or
# /run/secrets/<name> files), by the `cifs:`/`webdav:` blocks of
# `kind: Volume` (`passwordSecret`, which reads the `password` key),
# by `Image.pullSecret` and by `provision.truenas.*Secret`. It is the
# DECLARATIVE form of `delonix secret create`, closing the loop in YAML only.
#
# Three sources — `stringData`, `fromEnvFile`, `fromEnv` — that can be
# COMBINED in one document. Precedence: `fromEnvFile` first, then `stringData`
# overrides it (inline wins over the file), and `fromEnv` adds to it. There is
# no `data:` (base64) field: the engine only reads these three.
#
# Apply:    delonix stack apply -f examples/core/secret.yaml
#   Secrets are applied BEFORE whatever references them (Volume/Container/Image).
# ============================================================================

# ── 1. stringData — inline, handy for dev ───────────────────────────────────
# The VALUES are CLEARTEXT in the file, so the apply prints a warning.
# Fine for dev; never commit real values to a repository.
---
apiVersion: core.delonix.io/v1beta1
kind: Secret
metadata:
  name: nas-creds
  labels:                      # free-form labels stored with the resource
    app: demo
  annotations:                 # free-form annotations
    delonix.io/purpose: "example only"
spec:
  stringData:
    password: change-me        # the key `Volume.<cifs|webdav>.passwordSecret` looks for
    apiKey: dummy-api-key      # `apiKeySecret` fields look for `apiKey` (or `token`)
    username: demo             # `Image.pullSecret` wants `username` + `password`

# ── 2. fromEnvFile — load KEY=value lines from a .env file ───────────────────
# Keeps the values OUT of the manifest. A relative path resolves against the
# manifest's own folder.
---
apiVersion: core.delonix.io/v1beta1
kind: Secret
metadata:
  name: app-env
spec:
  fromEnvFile: ./secret-source.env   # e.g. DATABASE_URL=..., API_TOKEN=...

# ── 3. fromEnv (mapping) — read from the PROCESS environment, renaming ───────
# `<key in the secret>: <environment variable to read>`. The key is what the
# consumer looks up; the variable is whatever the CI job exports. A variable
# that is NOT set is an ERROR at apply time, never an empty secret.
---
apiVersion: core.delonix.io/v1beta1
kind: Secret
metadata:
  name: env-map-secret
spec:
  fromEnv:
    password: EXAMPLE_DB_PASSWORD   # `provision.truenas.passwordSecret` wants `password`
    token: EXAMPLE_API_TOKEN        # `Gateway.tokenSecretRef` wants `token`

# ── 4. fromEnv (list) — shorthand when key name == variable name ─────────────
---
apiVersion: core.delonix.io/v1beta1
kind: Secret
metadata:
  name: env-list-secret
spec:
  fromEnv:
    - DATABASE_URL
    - SENTRY_DSN

# ── 5. Combined — all three sources in one document ──────────────────────────
# The file gives the base, `stringData` overrides `LOG_LEVEL`, `fromEnv` adds a
# value read from the process environment.
---
apiVersion: core.delonix.io/v1beta1
kind: Secret
metadata:
  name: combined-secret
spec:
  fromEnvFile: ./secret-source.env
  stringData:
    LOG_LEVEL: debug
  fromEnv:
    - EXAMPLE_EXTRA

CampoFieldTipoTypeObrig.Req.DefaultDefaultDescriçãoDescription
fromEnvFromEnv——Keys read from the PROCESS's environment at apply time. `["DB_PASSWORD"]` takes `$DB_PASSWORD` and stores it under that name; `{ password: DB_PASSWORD }` stores it under `password` instead — which is what the consumers of a secret usually want, since `Storage`/`Tunnel`/ `provision` each look for a key by a fixed name. This is the form a CI job has: the value arrives as an environment variable from the runner's own secret store, and there is no file to point at and nothing to write into the manifest. Neither of the other two shapes could express it.
fromEnvFilestring——Path to a `KEY=value` file (e.g. `.env`) — keeps the values OUT of the manifest. Applied BEFORE `stringData` (inline overrides the file).
stringDataobject—{}Inline `KEY: value` pairs. **Plaintext in the manifest** — convenient for dev, but the value stays in cleartext in the file; for production prefer `fromEnvFile` (outside version control) or the CLI's `secret create`. Warned at apply.

Pod

O schema de Pod do Kubernetes (spec.containers[]) — portas/env/resources/securityContext/volumeMounts estruturados. O MESMO schema continua aceite num kind: Container, com aviso, e não é reescrito de propósito: um kind: Container chamado web cria um container web, este cria a netns pod-web cujo membro é web-c0 — renomear um workload nas costas de quem o escreveu partiria o DNS e os backends de HTTPRoute. O MESMO ficheiro mostra também o pod REAL multi-container: N containers a partilhar netns (mesmo IP, localhost entre si), IPC e UTS, geridos com delonix pod create/ls/describe/rm/logs.

The Kubernetes Pod schema (spec.containers[]) — structured ports/env/resources/securityContext/volumeMounts. The SAME schema is still accepted on a kind: Container, with a warning, and is deliberately not rewritten for you: a kind: Container named web creates a container web, this creates the pod netns pod-web whose member is web-c0 — renaming a workload behind your back would break DNS and HTTPRoute backends. The SAME file also shows the REAL multi-container pod: N containers sharing netns (same IP, reachable via localhost), IPC and UTS, managed with delonix pod create/ls/describe/rm/logs.

# ============================================================================
# kind: Pod — N containers sharing one network namespace (ADR-0006)
#
# k8s schema (`spec.containers[]` with structured ports/env/resources/
#     securityContext + pod-level `volumes[]`) plus an engine-specific `network`
#     field. Members share the pod netns (same IP, `localhost` between them) and
#     the IPC/UTS namespaces; `shareProcessNamespace: true` shares PID too. Only
#     `containers[].image` is mandatory.
#
# Apply:     delonix stack apply -f examples/compute/pod.yaml
# ============================================================================

# ── 1. minimal — only containers[].image is mandatory ──────────────────────
---
apiVersion: compute.delonix.io/v1beta1
kind: Pod
metadata:
  name: minimal-pod
spec:
  containers:
    - image: alpine:3.20              # unnamed member => container "minimal-pod-c0"
      command: ["sleep", "infinity"]

# ── 2. supporting resources for the scenarios below ────────────────────────
---
apiVersion: networking.delonix.io/v1beta1
kind: Network
metadata:
  name: pod-net
spec:
  driver: bridge
---
apiVersion: storage.delonix.io/v1beta1
kind: Volume
metadata:
  name: pod-data                      # referenced via `persistentVolumeClaim.claimName`
spec:
  driver: local
---
apiVersion: storage.delonix.io/v1beta1
kind: Volume
metadata:
  name: pod-cache                     # referenced via `source` (delonix extension)
spec:
  driver: local

# ── 3. single container — k8s schema with ports/env/volumes/securityContext ─
---
apiVersion: compute.delonix.io/v1beta1
kind: Pod
metadata:
  name: web
  namespace: default
spec:
  network: pod-net                    # host | none | <custom network>
  restartPolicy: Always               # Always | OnFailure | Never (delonix spellings also OK)
  expose: 80                          # auto-register this HTTP port in the L7 proxy (optional)
  hostAliases:                        # extra /etc/hosts entries, k8s shape
    - ip: 10.0.0.9
      hostnames: [legacy-api, legacy-api.internal]
  containers:
    - name: web
      image: nginx:latest
      command: ["/bin/sh", "-c"]      # overrides ENTRYPOINT (k8s semantics)
      args: ["nginx -g 'daemon off;'"]   # overrides CMD
      ports:
        - containerPort: 80
          hostPort: 8080              # published only when hostPort is set
          protocol: TCP
      env:
        - name: TZ
          value: UTC
      volumeMounts:
        - name: site
          mountPath: /usr/share/nginx/html
          readOnly: true
        - name: scratch
          mountPath: /tmp/cache
      resources:
        limits:
          cpu: "500m"                 # 500m => 0.5 cores
          memory: 256Mi
      securityContext:
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]
  volumes:
    - name: site
      hostPath:
        path: /srv/www                # bind mount of a host directory
    - name: scratch
      emptyDir: {}                    # ephemeral => tmpfs

# ── 4. full multi-container — every pod-level and container field ───────────
---
apiVersion: compute.delonix.io/v1beta1
kind: Pod
metadata:
  name: full-pod
  namespace: default                  # isolation namespace (a pod is isolated like a container)
  labels:
    app: full-pod
spec:
  # ---- pod-level ----
  network: pod-net                    # delonix extension: SDN network of the pod's shared netns
  restartPolicy: OnFailure            # Always | OnFailure | Never (also always/on-failure/no)
  hostname: full-pod-host             # hostname shared by every member (default: pod name)
  shareProcessNamespace: false        # true => members see each other's processes (see scenario 5)
  hostAliases:                        # extra /etc/hosts entries in every member, k8s shape
    - ip: 10.0.0.9
      hostnames: [legacy-api, legacy-api.internal]
    - ip: 10.0.0.10
      hostnames: [billing]

  # ---- pod volumes, referenced via containers[].volumeMounts[].name ----
  volumes:
    - name: site
      hostPath:                       # bind mount of a host directory
        path: /srv/www
    - name: scratch
      emptyDir:                       # ephemeral, backed by tmpfs (host RAM)
        medium: Memory                # "" would warn: k8s means node disk, this engine always uses tmpfs
    - name: data
      persistentVolumeClaim:          # a NAMED volume (`kind: Volume`), by name
        claimName: pod-data
    - name: cache
      source: pod-cache               # delonix extension: named Volume by plain source string

  # ---- members ----
  containers:
    - name: web                       # member name; container is <pod>-<name> (default c<index>)
      image: nginx:latest             # REQUIRED
      command: ["/bin/sh", "-c"]      # k8s `command` => overrides ENTRYPOINT
      args: ["nginx -g 'daemon off;'"]   # k8s `args` => overrides CMD
      workingDir: /usr/share/nginx/html  # directory the process starts in
      ports:
        - containerPort: 80
          hostPort: 8080              # published only when hostPort is set
          protocol: TCP               # TCP | UDP (default TCP)
          hostIP: 127.0.0.1           # bind address of the published port
        - containerPort: 443          # no hostPort => informational only, not published
      env:
        - name: TZ
          value: Africa/Luanda
        - name: LOG_LEVEL
          value: info
      volumeMounts:
        - name: site
          mountPath: /usr/share/nginx/html
          readOnly: true
        - name: scratch
          mountPath: /tmp/cache
        - name: data
          mountPath: /var/lib/web
        - name: cache
          mountPath: /var/cache/web
      resources:
        limits:                       # enforced as cgroup limits (`requests` advisory)
          cpu: "500m"                 # 500m => 0.5 cores
          memory: 256Mi
      securityContext:
        privileged: false
        runAsUser: 101
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]

    - name: sidecar                   # 2nd member: reaches `web` on localhost (shared netns)
      image: busybox:latest
      command: ["sh", "-c"]
      args: ["while true; do wget -qO- http://localhost:80/ >/dev/null 2>&1; sleep 10; done"]
      resources:
        limits:
          cpu: "100m"
          memory: 64Mi

---

#   spec.detach, spec.expose   members always start detached and are not auto-registered in

#   containers[].tty           accepted and ignored (the engine decides tty by attach/detach).
#   resources.requests         advisory only; the engine enforces `limits`.

Workload

UM objecto declarativo para os dois tipos de computação: spec.type: container | vm | pod | microvm + o bloco com o mesmo nome. Baixa para o Kind correspondente no load — não redefine um único campo, por isso não pode divergir dele.

ONE declarative object for both kinds of compute: spec.type: container | vm | pod | microvm plus the block with that same name. Lowers to the matching Kind on load — it doesn't redefine a single field, so it can never drift from it.

# ============================================================================
# kind: Workload — ONE declarative object for every compute type (ADR-0001/0006)
#
# A Workload is sugar: it does NOT survive the load — it is rewritten into the
#     target Kind and flows through that Kind's normal apply. `spec.type` picks
#     the target and the block named after the type carries EXACTLY that Kind's
#     spec (nothing is redefined):
#       type: container -> spec.container == kind: Container     (compute/container.yaml)
#       type: vm        -> spec.vm        == kind: VirtualMachine (compute/virtualmachine.yaml)
#       type: pod       -> spec.pod       == kind: Pod           (compute/pod.yaml)
#       type: microvm   -> spec.microvm   == kind: VirtualMachine, backend FORCED to cloud-hypervisor
#     Exactly ONE block, the one matching `type` (any other is an error). The
#     `metadata` (name/namespace/labels/annotations) is inherited by the lowered resource.
#
# Apply:     delonix stack apply -f examples/compute/workload.yaml
#     See what it lowers to:  delonix stack apply --dry-run -f examples/compute/workload.yaml
# ============================================================================

# ── 1. supporting resources for the scenarios below ────────────────────────
---
apiVersion: networking.delonix.io/v1beta1
kind: Network
metadata:
  name: wl-net
spec:
  driver: bridge
---
apiVersion: core.delonix.io/v1beta1
kind: Secret
metadata:
  name: wl-secret
spec:
  stringData:
    API_TOKEN: example-token-not-real
---
apiVersion: storage.delonix.io/v1beta1
kind: Volume
metadata:
  name: wl-data
spec:
  driver: local

    expose: 80

    netBps: 10mbit
    netBurst: 20mbit
    memory: 256M
    cpus: "0.5"
    cpuWeight: "200"
    cpuset: "0"
    ioWeight: "100"
    cgroupParent: { name: wl-tier, memoryMax: "1073741824", cpus: "2", pidsMax: "512" }
    readOnly: true
    capDrop: ["ALL"]
    capAdd: ["NET_BIND_SERVICE"]
    securityOpt: ["no-new-privileges"]
    userns: true
    volumes: ["wl-data:/var/lib/app"]

    env: ["TZ=Africa/Luanda"]
    secret: [wl-secret]
    secretFiles: true
    ulimit: ["nofile=1024:2048"]

Dependency

Alcançabilidade DIRIGIDA entre containers (ao contrário da rede, que é bidireccional): from alcança to, e to não fica exposto aos outros. É açúcar reduzido no load para kind: NetworkPolicy — sem dataplane novo. Várias dependências para o mesmo alvo ACUMULAM os allows (por isso são fundidas por alvo, e não uma política por dependência).

DIRECTED reachability between containers (unlike a network, which is bidirectional): from reaches to, and to stays unexposed to the others. Sugar lowered on load into kind: NetworkPolicy — no new dataplane. Several dependencies on the same target ACCUMULATE their allows, which is why they are merged by target rather than one policy per dependency.

# ============================================================================
# kind: Dependency (alias: KnowDepends) — DIRECTED reachability between workloads
#
# Unlike a Network (bidirectional), it opens ONE direction: `from` reaches `to`,
# but `to` does NOT initiate towards `from` — and `to` stops being exposed to
# everyone else on the network. Classic case: the app knows the DB, the DB does
# not know the app. It is SUGAR: at load each Dependency is rewritten into a
# `kind: NetworkPolicy` with `direction: ingress` on `to` (default-deny + one
# allow per `from`, naming the peer by WORKLOAD so it survives restarts). Several
# Dependencies for the same `to` accumulate and merge into one policy. Run
# `delonix stack apply --dry-run` to see the real policy.
#
# spec fields: from (required, string), to (string or list), ports (list), proto.
# The rule names the peer by workload, not by IP — a container's address comes
# from the SDN and changes on a restart.
#
# Apply:    delonix stack apply -f examples/networking/dependency.yaml
# ============================================================================

NetworkRoute

O grau ACIMA do Dependency: aquele liga dois WORKLOADS, este liga duas REDES — isoladas por omissão. Uma rota diz que o pacote PODE atravessar; nunca diz que é PERMITIDO — quem decide isso continua a ser o FirewallPolicy/Dependency em cada extremidade. São duas perguntas em série (há caminho? → é aceite?), por isso são dois Kinds e não um campo routes: dentro de Network. Dirigida (from inicia, o retorno flui; to nunca inicia de volta); custo constante, não cresce com o número de redes.

The grade ABOVE Dependency: that one links two WORKLOADS, this one links two NETWORKS — isolated by default. A route says the packet CAN cross; it never says it's ALLOWED — that decision still belongs to FirewallPolicy/Dependency at each end. Two questions in series (is there a path? → is it accepted?), which is why they're two Kinds and not one routes: field inside Network. Directed (from initiates, the return flows; to never initiates back); constant cost, doesn't grow with the number of networks.

# ============================================================================
# kind: NetworkRoute — a DIRECTED path between two NETWORKS (ADR-0013 tier B)
#
# Networks are isolated by default. This declares that one MAY reach the other
# — directed, like `kind: Dependency` between containers: `from` initiates and
# the return flows (established); `to` does NOT initiate back. The spec has
# EXACTLY two fields, `from` and `to` — there is no `via`. Identity is the PAIR
# (from->to), not metadata.name; two documents for the same pair are refused.
#
# A route says the packet MAY cross; never that it is ALLOWED. Per-workload
# policy (NetworkPolicy/Dependency) still decides. Two questions in series — hence
# two Kinds: NetworkRoute (is there a path?) then the policy (is it accepted?).
# `stack apply --prune` closes routes removed from the manifest.
#
# Apply:    delonix stack apply -f examples/networking/networkroute.yaml
# Equivalent imperative:   delonix network route <from> <to>   (and `--rm` to close)

Ingress

# ============================================================================
# kind: Ingress — Kubernetes-shaped L7/HTTP Ingress (networking.k8s.io/v1)
#
# It is the k8s shape (host/path → backend service) of the SAME embedded L7
# proxy as `kind: HTTPRoute` — Compat→HTTPRoute: it compiles to that proxy and
# is composed with every Ingress/HTTPRoute of the manifest into a SINGLE proxy
# with ONE certificate (no SNI). The old `kind: Ingress`-as-L4-firewall is gone
# — the L4 firewall is now `kind: NetworkPolicy` (see

# applied), `pathType: Exact` (served as a prefix, warned), a `tls` list longer

Stack

Agrupa vários recursos num só documento. Expandido no load para os Kinds individuais, em ordem de dependência — o Stack não sobrevive ao load, tudo o resto vê os filhos.

Groups several resources into one document. Expanded on load into the individual Kinds, in dependency order — the Stack doesn't survive the load, everything else sees the children.

# ============================================================================
# kind: Stack — the aggregate that groups a whole app in one document
#
# A Stack bundles networks, containers, volumes, … (k8s-Service-like). At load
# time it expands into its constituent resources, which then flow through the
# normal per-Kind apply IN DEPENDENCY ORDER (the order `delonix stack plan
# --fields` prints — the order of the Kind table, not a list kept here). Each
# child inherits the Stack's namespace unless it sets its own, and can carry
# `labels:`/`annotations:` next to `name:`. A group item is
# `{ name, namespace?, labels?, annotations?, spec }`: `spec` is exactly the
# `spec` of the Kind the group stands for.
#
# This example uses EVERY group a Stack accepts (the test
# `the_stack_example_names_every_group` fails if one is missing), so it doubles
# as the reference for what each one looks like. For a single Kind with all of
# its options, see examples/full-<kind>.yaml.
#
#   group                Kind               reference
#   runtimePolicies      RuntimePolicy      full-runtimepolicy.yaml
#   secrets              Secret             core/secret.yaml
#   configs              Config             core/config.yaml
#   networks             Network            full-network.yaml
#   networkRoutes        NetworkRoute       full-networkroute.yaml
#   networkZones         NetworkZone        networkzone.yaml
#   storagePools         StoragePool        full-volume.yaml
#   volumes              Volume             full-volume.yaml
#   objectStorages       ObjectStorage      storage/objectstorage.yaml
#   images               Image              full-image.yaml
#   apps                 App                full-app.yaml
#   vms                  VirtualMachine     full-virtualmachine.yaml
#   systemContainers     SystemContainer    systemcontainer.yaml
#   containers           Container          full-container.yaml
#   pods                 Pod                full-pod.yaml
#   snapshots            Snapshot           storage/snapshot.yaml
#   services             Service            full-service.yaml
#   ingress              Ingress            full-ingress.yaml
#   firewallPolicies     NetworkPolicy      full-networkpolicy.yaml
#   networkAccessRules   NetworkAccessRule  full-networkaccessrule.yaml
#   networkGateways      NetworkGateway     networkgateway.yaml
#   ipPools              IPPool             full-ippool.yaml
#   ipAddresses          IPAddress          networking/ipaddress.yaml
#   httpRoutes           HTTPRoute          full-httproute.yaml
#   gateways             Gateway            full-gateway.yaml
#   gitopsSources        GitOpsSource       full-gitopssource.yaml
#   workloads            Workload           full-workload.yaml   (lowered at load)
#   dependencies         Dependency         full-dependency.yaml (lowered at load)
#
# `tunnels:` is the old spelling of `gateways:` and still loads. Not groupable:
# `Stack` (does not nest) and `KubernetesCluster` (a remote procedure over SSH,
# not a resource of this node — see full-kubernetescluster.yaml).
#

# ── 1. The blog Stack — one document naming every group ─────────────────────
---
apiVersion: core.delonix.io/v1beta1
kind: Stack
metadata:
  name: blog
  namespace: default
spec:

  # group below, in the SAME apply. Lowering it is never automatic — removing
  # this block and re-applying leaves policy.json untouched; `delonix policy
  # unset` is the only way down.
  runtimePolicies:
    - name: node-ceiling
      spec:
        denyPrivileged: true
        denyLatestTag: true     # forces fixed tags — no image below uses :latest

  # Secrets first: everything below may reference them.
  secrets:
    - name: db-credentials
      spec:
        stringData:
          POSTGRES_PASSWORD: change-me

  # Configs right after Secrets: the cleartext sibling (non-secret data).
  configs:
    - name: app-tuning
      spec:
        data:
          LOG_LEVEL: info

  networks:
    - name: blog-net
      spec:
        driver: bridge
    - name: blog-back
      spec:
        driver: bridge

  # A route says the two networks HAVE a path; the policies below still decide
  # what is allowed across it.
  networkRoutes:
    - name: net-to-back
      spec:
        from: blog-net
        to: blog-back

  # Cluster-native SDN — realized by whichever NetworkZoneProvider the RUNTIME
  # has configured (today: Proxmox, via DELONIX_PROXMOX_URL), never named here.
  # Applying without a provider refuses with a clear error (ADR-0049 addendum).
  networkZones:
    - name: dc1
      spec:
        vnets:
          - name: prod
            alias: "Production VLAN"

  # A storage pool the node's administrator declared in
  # /etc/delonix/storage-pools.yaml (ADR-0067). The Stack only says the engine
  # uses it, and how far it may be over-allocated; the driver is the admin's.
  storagePools:
    - name: fast
      spec:
        alertPct: 85

  volumes:
    - name: db-data
      spec:
        quota: 5G          # hard cap on the volume's data
        alertPct: 80       # warn when it is 80% full

  # S3-compatible object storage (see storage/objectstorage.yaml). `cephRgw`
  # provisions an S3 identity on the node's Ceph gateway; `external` points at a
  # store you already run. Credentials land in secret/<name>-s3.
  objectStorages:
    - name: media
      spec:
        backend: cephRgw
        bucket: media
        cephRgw:
          endpoint: http://rgw.internal:80

  images:
    - name: alpine-base
      spec:
        pull: alpine:3.20  # `pull` and `build` are alternatives; see full-image.yaml

  # Cloud Native Buildpacks: source in, image out (see full-app.yaml).
  apps:
    - name: shop
      spec:
        source: .
        image: shop:1.0           # tagged, not :latest — the runtimePolicy above denies :latest

  # A microVM/VM on the same SDN. Needs a VM image or disk on the host to apply.
  vms:
    - name: worker
      spec:
        disk: delonix-vm-base:ubuntu-24.04
        vcpus: 1
        memory: 1G
        network: blog-net

  # provider (today: a Proxmox node, via DELONIX_PROXMOX_URL), never named here.
  # The engine pulls the image; memory/swap/cores change in place, the rest
  # recreates (ADR-0058).
  systemContainers:
    - name: tools
      spec:
        image: alpine:3.20
        entrypoint: ["/bin/sleep", "infinity"]
        memory: 256M
        cores: 1

  containers:
    - name: web
      labels: { app: web }     # what the Service below selects by
      spec:
        image: nginx:1.27-alpine  # tagged, not :latest
        network: blog-net
        ports: ["8080:80"]
        expose: 80         # auto-register in the L7 proxy as web.<namespace>.delonix.internal
    - name: db
      spec:
        image: postgres:16
        network: blog-net
        secret: [db-credentials]
        volumes: ["db-data:/var/lib/postgresql/data"]

  # A pod: several containers sharing ONE network namespace (localhost between them).
  pods:
    - name: worker-pod
      spec:
        containers:
          - name: app
            image: nginx:1.27-alpine
          - name: sidecar
            image: alpine:3.20
            command: ["sleep", "infinity"]

  # Application (ADR-0086 D4) — the service Kind. Lowers into its `replicas` Pod
  # instances (`frontend-0`/`frontend-1`); the Pod is the instance, not written
  # by hand.
  applications:
    - name: frontend
      spec:
        replicas: 2
        containers:
          - name: frontend
            image: nginx:1.27-alpine

  # Job (ADR-0086 D3) — run-to-completion. Lowers to a Pod whose restartPolicy
  # defaults to OnFailure (retried until it succeeds).
  jobs:
    - name: db-migrate
      spec:
        containers:
          - name: migrate
            image: migrate/migrate:v4.17.0
            command: ["migrate", "-path", "/m", "-database", "$DB", "up"]

  snapshots:
    - name: db-data-nightly

# kind: KubernetesCluster — a kubeadm cluster in three modes (one per document)
#
# `spec.mode` is the discriminator and each mode reads only its own block:
#       kind  → nodes as containers, on THIS machine (no Docker, no `kind` binary)
#       vm    → every node is a real microVM from the golden image (hypervisor isolation)
#       ssh   → remote hosts that ALREADY EXIST (bare metal or someone else's VMs)

#     specific ones live in the mode's block (`kind:`, `vm:`, `ssh:`).

#       delonix cluster apply   -f examples/cluster/kubernetescluster.yaml

# kind: Volume — a named volume (data survives `container rm`)
#
# ONE Kind, SEVERAL MUTUALLY EXCLUSIVE shapes (hence one document each): a
# local volume, a raw network driver, a network-share block
# (`nfs:`/`cifs:`/`webdav:` — the block's NAME is the type), a slice of
# ANOTHER volume (`share:`), provisioning on a NAS (`provision:`) and a
# volume allocated in a storage pool (`pool:`). `quota` and `alertPct` apply
# to every shape. `kind: Storage` and `kind: ShareVolume` were FOLDED in here
# (the load refuses them and names this form); `storageRef` survives as an
# alias of `share.from`, and `options` as an alias of `mountOptions`.
#
# A workload consumes any volume the SAME way: `-v <name>:/path` (container),
# `volumes:` (pod/stack), or `spec.volumes` on a VM (libvirt 9p).
#
# Apply:    delonix stack apply -f examples/storage/volume.yaml

Firewall L4 declarativo por direcção (estilo k8s NetworkPolicy; o nome antigo FirewallPolicy continua aceite como alias). Cada documento é o estado desejado de UMA direcção de um container-alvo — allowlist + default-deny, idempotente. Declarative per-direction L4 firewall (k8s NetworkPolicy-style; the old name FirewallPolicy is still accepted as an alias). Each document is the desired state of one direction for one target container — allowlist + default-deny, idempotent. The kind: Egress no longer exists: it is direction: egress in this same policy (they shared the whole struct).

# ============================================================================
# kind: NetworkPolicy — declarative L4 firewall (k8s NetworkPolicy style)
#
# Direction is `spec.direction` (ingress|egress) and reach is `spec.scope`.
# Each document is the DESIRED STATE of ONE direction of ONE target: applying
# it REPLACES that direction's rules (allowlist + default), leaving the other
# untouched — so two documents for the same (target, direction) are refused.
# `scope: container` (default) acts on a workload; `scope: network` is a whole
# network's EGRESS policy (egress only); `scope: vm` is the firewall of the
# node the VM runs on (ADR-0052). It only acts on workloads on a custom SDN.
#
# NOTE: `kind: Ingress` is NO LONGER firewall — it is now the k8s-shaped L7/HTTP
# Ingress (host/path→backend, see examples/gateway/ingress.yaml). And `kind: Egress`
# was REMOVED — the load REFUSES it, naming `direction: egress` as the replacement:
# no known model splits inbound from outbound into TYPES, so direction is a field,
# with one struct, one validator and one apply.
#
# spec fields: direction, scope, target, defaultPolicy, rules[], allowCidrs,
# fqdnAllowlist, rateLimit. Per-rule fields (scope container/vm): proto, port,
# action, from, fromWorkload, to, toWorkload, note. allowCidrs/fqdnAllowlist/
# rateLimit are for scope: network only.
#
# Apply:    delonix stack apply -f examples/networking/networkpolicy.yaml
# ============================================================================

HTTPRoute

Reverse-proxy L7/HTTP embutido — routing por Host + prefixo de path para containers backend. TLS termina no proxy (self-signed ou secretRef); reload a quente por SIGHUP.

Built-in L7/HTTP reverse proxy — routing by Host + path prefix to backend containers. TLS terminates at the proxy (self-signed or secretRef); hot reload via SIGHUP.

# ============================================================================
# kind: HTTPRoute — declarative L7/HTTP reverse proxy (Gateway API style)
#
# Routes by Host and/or path prefix to backend containers. The proxy (embedded
# hyper) runs INSIDE the holder netns — it reaches backends by their SDN IP —
# and publishes the entry ports on the host. TLS terminates at the proxy
# (self-signed by default, or a PEM pair from a `kind: Secret`). ALL HTTPRoute
# (and Ingress) documents of a manifest compose into ONE proxy: listeners are
# merged by port (TLS wins on collision), routes are concatenated, and there is
# a SINGLE certificate (no SNI). `kind: Ingress` is the k8s spelling of the SAME
# proxy (Compat→HTTPRoute, see ingress.yaml); the L4 firewall is `kind:
# NetworkPolicy` (see ../networking/networkpolicy.yaml).
#
# Backends MUST be `kind: Container` with an IP on a custom SDN network (not

RuntimePolicy

The node's OWN admission ceiling (group security.delonix.io): refuse --privileged, host networking, :latest, unlisted registries, device passthrough into a VM. It is the same policy.json that container run and vm create already check before creating anything. A node singleton: a manifest declares at most one. It converges like any Kind, but dropping it from the manifest does not remove it — only delonix policy unset does.

# ============================================================================
# kind: RuntimePolicy — this node's admission ceiling (M04, ADR-0026)
#
# The ceiling THIS host puts on what may run. It gives a manifest form to the
#     file `<root>/policy.json`, the SAME one `container run`/`vm create` already
#     check before anything is created. Every field starts at "no opinion", so a
#     policy states only what it wants to restrict.
#
# A node-wide SINGLETON. Whatever `metadata.name` says, apply always writes
#     the ONE `policy.json` — a manifest declares at most ONE RuntimePolicy
#     document (a second is refused by `stack validate`/`apply`).
#
# It converges like any Kind (a changed field really is applied), but does
#     NOT come down on its own: removing this document and running `stack apply
#     --prune` (or `stack destroy`) leaves the ceiling as it was. The only way
#     down is `delonix policy unset` (asks for confirmation, or `--force`).
#
# Apply:    delonix stack apply -f examples/security/runtimepolicy.yaml

IPPool

Um livro de reservas de endereços DO HOST que as rotas reclamam: uma rota com spec.pool segura UM endereço do pool enquanto for declarada e responde nesse endereço em vez do loopback. Só IPv4; com announce: local o endereço já tem de estar numa interface deste host. Um pool com um endereço reservado não se remove nem encolhe.

A reservation ledger of HOST addresses that routes claim: a route with spec.pool holds ONE address of the pool for as long as it is declared, and answers on that address instead of loopback. IPv4 only; with announce: local the address must already be on an interface of this host. A pool with a leased address cannot be removed or shrunk.

# ============================================================================
# kind: IPPool (ADR-0046, D3) — a reservation ledger of HOST addresses
#
# Addresses that routes claim. A route with `spec.pool: <name>` holds ONE address
# of the pool for as long as it is declared, is reachable on that address instead
# of loopback, and (with `hosts: [host]`) has its names pointed at it in the
# operator's /etc/hosts. The ledger is observable: `delonix get ippools`,
# `delonix describe ippools <name>`. A pool cannot be removed, nor its addresses
# shrink under a lease, while a route holds an address — remove or change the

NetworkGateway

Aliases e regras de filtro numa firewall de perímetro (ADR-0051), hoje o OPNsense, registado por DELONIX_OPNSENSE_URL e um par key/secret de API. Aliases entram antes das regras e saem depois delas; a identidade de uma regra é a sua description. Uma alteração ao spec é remover e voltar a aplicar.

Aliases and filter rules on a perimeter firewall (ADR-0051), today OPNsense, registered through DELONIX_OPNSENSE_URL and an API key/secret pair. Aliases go in before rules and come out after them; a rule's identity is its description. A spec change is a remove and re-apply.

# ============================================================================
# kind: Router — aliases, rules, NAT and policies on a perimeter appliance (renamed from NetworkGateway, ADR-0086 D3)
#
# `NetworkGateway` still loads as a silent alias; `Router` is the canonical name.
# (`kind: Gateway` is a different Kind: the ADR-0086 D4 entry-point/tunnel.)
#
# `spec.provider` names a registered gateway provider: `opnsense`, registered
# through DELONIX_OPNSENSE_URL and a credential — a generated API key/secret pair
# (DELONIX_OPNSENSE_CREDENTIAL names a `kind: Secret` with `key` and `secret`); an
# account's password is refused by the appliance. `stack validate` does not
# contact it. Aliases are applied before rules and removed after them (the
# appliance checks a rule's source against its alias table). Ownership via a
# `delonix-owner:<token>` mark: an alias/rule with the same name and no mark is
# refused, never adopted. There is no update in place — a changed spec is removed
# and applied again.
#
# spec fields: provider, aliases, rules, policies, nat. `policies` declares one
# direction of a target's policy in a NetworkPolicy shape, lowered to the
# appliance's filter rules (rule n at `sequence + n - 1`, default right after).
# `nat` declares SNAT/DNAT (ADR-0051). IPv4 only.
#
# Apply:    delonix stack apply -f examples/networking/networkgateway.yaml
# ============================================================================

# ── 1. edge — aliases, a filter rule, NAT (SNAT+DNAT) and a policy ───────────
---
apiVersion: networking.delonix.io/v1beta1
kind: Router
metadata: { name: edge }
spec:
  # ADR-0071 block form; the scalar `provider: opnsense` is the same thing.
  provider: { type: opnsense }
  aliases:
    - name: delonix_web
      kind: host               # host | network
      content: ["10.20.0.10", "10.20.0.11"]
      description: web tier
  rules:
    - description: office to web tier   # the rule's identity on the appliance
      source: 192.168.1.0/24   # an alias name, a CIDR, or any
      destination: delonix_web
      protocol: TCP            # omit for any protocol
  nat:
    - description: lan source nat        # the NAT rule's identity on the appliance
      kind: snat               # snat (source NAT) | dnat (destination NAT / port-forward)
      interface: wan           # the appliance's own name for the interface (lan|wan|opt1)
      source: 10.77.0.0/24     # snat: the network translated, at its network address
      target: interface-address # snat: `interface-address` (default) or an address
    - description: forward https to web
      kind: dnat               # a port forward
      interface: wan
      protocol: tcp            # dnat: tcp | udp
      port: 443                # dnat: the port on the interface's address
      target: 10.20.0.10       # dnat: the address forwarded to (required)
      targetPort: 8443         # dnat: the port on the target; defaults to `port`
  policies:
    - name: web-in
      target: delonix_web      # an alias name, a prefix, or an address
      direction: ingress       # ingress (to the target) | egress (from it)
      defaultPolicy: deny      # the last rule's verdict; deny when omitted
      sequence: 30000          # the first rule's position among the appliance's filter rules
      rules:
        - { proto: tcp, port: "443", from: 192.168.1.0/24 }
        - { proto: tcp, port: "22", from: 10.9.0.0/24, log: true }       # log: logs every match
        - { port: "8000-8080", action: deny, stateful: false }           # stateful false: keeps no state for the flow

GitOpsSource

Um repositório git de onde o nó reconcilia (ADR-0021). Aplicar escreve um registo e, com sync.automated: true, um timer systemd; cada disparo corre UMA passagem e termina: fetch do ref → resolve a commit → verifica a assinatura → lê o YAML sob path → guarda → planeia → aplica. Um commit que não carrega, falha a guarda, ou planeia uma acção bloqueada por safety deixa o stack a correr intacto. reconcile corre uma passagem à mão; suspend/resume param e retomam as passagens.

A git repository this node reconciles from (ADR-0021). Applying writes a record and, with sync.automated: true, a systemd timer; each fire runs ONE pass and exits: fetch the ref → resolve to a commit → verify the signature → read the YAML under path → guard → plan → apply. A commit that fails to load, fails the guard, or plans a safety-blocked action leaves the running stack untouched. reconcile runs a pass by hand; suspend/resume stop and restart the passes.

# ============================================================================
# kind: GitOpsSource — a git repository this node reconciles from (ADR-0021)
#
# Applying writes a record and, with `sync.automated: true`, a systemd timer
#     (`delonix-gitops-<namespace>.<name>.timer`). Each fire runs ONE pass and
#     exits — nothing stays resident:
#       fetch the ref → resolve to a commit → verify the signature (when asked)
#       → read the YAML under `path` from the commit's tree → guard → plan → apply
#     A commit that does not load, fails the guard/graph, or plans an action
#     `safety` blocks leaves the running stack untouched; `delonix gitops status`
#     names it. `reconcile <name>` runs a pass by hand; `suspend`/`resume` stop
#     and restart the passes without a commit.
#
# TWO stacks, never one: the stack that applies THIS file (the bootstrap:
#     `delonix stack apply -f … --name bootstrap`) declares only the source; the
#     passes apply the repository into `spec.stack` (default
#     `gitops.<namespace>.<name>`). A hand-run apply/plan/prune/validate of the
#     passes' own stack is refused (DX-1601).
#
# Credentials are NAMED, never carried: each `*Ref` is a kind: Secret that
#     already exists on the node before the source is applied.
#       secretRef      → key `identity`         (the SSH private key)
#       knownHostsRef  → key `known_hosts`      (the pinned host keys)
#       trustedKeysRef → key `allowed_signers`  (an SSH allowed_signers file)
#
# Apply:    delonix stack apply -f examples/gitops/gitopssource.yaml --name bootstrap
# ============================================================================

# ── 1. ssh + signed commits — the production source, everything declared ────
---
apiVersion: core.delonix.io/v1beta1
kind: GitOpsSource
metadata:
  name: production
  namespace: production
spec:
  source:
    url: ssh://git@git.example.org/infra/web.git   # also file:///<path> and https:// (anonymous)
    ref: refs/heads/main                            # a branch or a tag, resolved to a commit first
    path: environments/production                   # hidden paths (.github/…) are never read
    interval: 60s                                   # 15s to 24h
    secretRef: web-deploy-key                        # Secret with the SSH private key, under `identity` (REQUIRED for ssh://)
    knownHostsRef: git-known-hosts                   # Secret with the pinned host keys, under `known_hosts` (REQUIRED for ssh://)
    signedCommitsRequired: true                      # refuse a commit whose SSH signature is not from trustedKeysRef
    trustedKeysRef: web-signers                       # Secret with an SSH allowed_signers, under `allowed_signers` (goes together with signedCommitsRequired)
  sync:
    automated: true                                  # installs the timer; false = registers and runs only on `gitops reconcile`
  safety:
    allow: [Create, Update]                          # the actions a pass may take; Adopt/Replace/Reboot are opt-in; Delete is prune; Conflict never
    prune: false                                     # Delete runs only with prune: true
    maximumDeletes: 5                                # the most a single pass may prune
    protectedResources:
      - Volume/*                                     # <Kind>/<name> or <Kind>/* a pass never prunes
    kinds: []                                        # empty = the default set; name VirtualMachine, SystemContainer, NetworkZone, NetworkGateway, StoragePool, Gateway or IPPool to let one in
  stack: production-web                              # the stack a pass applies into (default gitops.<ns>.<name>); never the stack that applies this file
