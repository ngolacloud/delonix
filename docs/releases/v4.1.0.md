## v4.1.0 — ADR-0043 closes on the last five crates, and a fresh root node accepts `-m`/`--cpus` again

Eleven commits since `v4.0.0`. The trigger was a production fix (#415, external
PR, reviewed and merged in this session): a FRESH root node refused `-m`/`--cpus`/
`--cpu-weight` even when the kernel delegated all three controllers — and, in the
case where delegation was indeed real but partial, the operator saw "Permission denied"
where the right answer was "`cpu` is not delegated, run this". Alongside it, the five
crates `v4.0.0` had left undone ("Known, not fixed in this series") gained
ADR-0043's `DX-CDNN` code dictionary — which now becomes **Accepted**. No CLI
surface change (commands, flags, Kinds): this series is about the QUALITY of
what the engine was already doing.

### `-m`/`--cpus`/`--cpu-weight` on a root node: the refusal was asking the wrong question (#415)

`cgroup_limits_apply()`, in root mode, only asked "can I create a cgroup under
`delonix.slice`?" — necessary, but not sufficient: the right question is "were the
controllers actually HANDED DOWN to the slice's children?". `ensure_delonix_slice`
discarded every write to `cgroup.subtree_control` with `let _ =`, so a
slice that didn't receive `cpu` from `/sys/fs/cgroup` ended up with no `cpu.max` — and
the error message said **"Permission denied"**, because `std::fs::write` opens with
`O_CREAT` and cgroupfs refuses to create a regular file with `EACCES`: same
directory, same uid, `memory.max` accepted one line before.

Two fixes, both measured and not just read:

- `cgroup_limits_apply()` in root now asks BOTH questions, the way the rootless
  leg already did — create the cgroup, **and** confirm that `memory`/`cpu`/`pids`
  are in `cgroup.subtree_control`.
- A MISSING `cpu.max` (or `memory.max`/`pids.max`) no longer reports the kernel's
  errno and instead names the missing controller and the command that fixes it. A
  file that EXISTS but refuses the write keeps the errno — that's the right answer
  there. The repair itself is bounded: it only activates a controller the level
  above already offers, never moves a process or tightens someone else's limit.

Four tests cover the pair (reading the delegation, the message, and the two
distinctions — missing file vs. file that refuses). Not validated live in this
session against a real root node (the original finding was reproduced on an aarch64
VM by the PR's author, 2026-09-18); validated in this session with the crate's full
build/clippy/tests and with the merge against current `main` (which had meanwhile
already renamed `Error::Runtime` to `Error::Syscall`, ADR-0043 — the three-way merge
resolved on its own, with no conflict).

### ADR-0043 closes — the last five crates gain numbered codes

`v4.0.0` had left it in writing: "`delonix-truenas`, `delonix-proxmox`, and
`delonix-vm` still carry the generic, shared `Error` (...) they don't make this
release, they'll make the next one as soon as they are merged." They did, and
`delonix-linux` and `delonix-sdn` (which weren't even on that list, being the two
largest) followed along:

- **`delonix-vm::cloudinit`** — the NoCloud seed generator, 5 failures (invalid
  VM name, `--user-data` copy, missing or failing `cloud-localds`).
- **`delonix-truenas`** — the 20 refusals of the storage provider (ADR-0009): 15
  variants, including a failed/disappeared/exhausted async job and a quota below
  the minimum.
- **`delonix-proxmox`** — the 19 refusals of the VM provider (ADR-0008), the first
  to populate the dictionary's `Vm` domain.
- **`delonix-linux`** — ~65 sites (`cdi.rs`, `run_host.rs`, `supervise.rs`,
  `workload.rs`, `lib.rs`: `spawn`/`exec`/`mount_live`/cgroups). The ~30 that
  built `Error::Runtime{context,message}` (clone, mount, setns, `/proc`/cgroup
  writes, `waitpid`, `busctl`) collapse into a single `Error::Syscall` — zero
  change in text or class, just the number behind it. `Domain::Host` (empty until
  now) gains the failures that are really about the HOST: the system call itself,
  AppArmor, the absence of a CDI spec.
- **`delonix-sdn`** — ~180 constructions (the rootless SDN, the ingress firewall, the
  CNI, the IPAM, the WireGuard overlay), the largest of the five: 50 of its own
  variants + a `Command{context,message}` bucket for "a host tool failed", the
  first crate to populate the dictionary's network domain.

The dictionary published at `docs/codigos.html` goes from **61 to 198** cataloged
`DX-CDNN` codes. `delonix explain <code>` still reads the same source as
the error line and `-o json` — none of these five crates invents its own separate
dictionary. ADR-0043 had already been `Accepted` since 2026-09-17; this series closes
the "landed crate by crate" rollout the ADR itself foresaw — the last five of the
crates listed in the plan gain the dictionary in this release.

### ADR-0044 (P4) — the five required spikes are done; the architecture remains `Proposed`

No observable behavior change in this series. Three investigation findings worth
recording, and a piece of code that STAYS (but has no consumer yet):

- **`StateRepository<T>`** — a new port in `delonix-model` (the foundation; the
  trait names nothing from `delonix-compute`), implemented for `Store`/`JsonStore<T>`
  in `delonix-state`. `delonix-linux`'s `wait_and_record`/`stop`/`persist_stop`/
  `remove` now receive `&impl StateRepository<Container>` instead of the concrete
  `Store` — validated live that the on-disk record stays byte-for-byte identical (an
  isolated `run`/`stop`/`rm` cycle, before and after). `spawn`/`create_with` still
  open `SecretStore` directly — left undone, for a port of their own.
- **Proxmox: `--namespace` was already refused** (the guard lives one layer above
  the provider, since before ADR-0044 itself was even written — the original static
  finding had looked in the wrong crate); **`--network` is accepted and IGNORED**,
  confirmed by the actual HTTP form sent to the Proxmox node (never the requested
  network). Recorded as a small decision (refuse, don't build a remote bridge),
  not as new work.
- **`VmSpec`/`Extensions`/`VmProvider`** (`delonix-vm::provider_spike`) — a spike
  that converged Cloud Hypervisor and libvirt under the SAME contract, proven live
  on both backends. Stays in the repository (zero risk to the public surface — not
  called by any CLI path), as a foundation for the ADR's next phase; not a new
  capability a user can invoke today.
- The `delonix-launcher`/`delonix-netns-holder` binary pair was validated in an
  isolated spike (hardlinks, per-path AppArmor profile) — neither exists as a
  published binary in this release.

The decision to accept ADR-0044 remains the repository owner's; this series only
closes the five spikes the ADR itself required before that.

### Known, not fixed in this series

- The #415 finding was measured on an aarch64 VM by the PR's author; this session
  validated the logic (build/clippy/tests/gates) and the merge against current
  `main`, but did not repeat the measurement on a real x86_64 root node.
- `image vm ls-remote` with no argument still has no `--timeout` on a slow
  connection (inherited, not touched in this series).

### Not validated in this release

The Proxmox backend's `--network`/`--namespace` path against a real SDN bridge
(the test host's topology already answered the question without needing a real
guest — see `docs/discovery/58_P4_D1_D8_PROXMOX_NETWORK_NAMESPACE_LIVE.md`); and
the `delonix-launcher`/`delonix-netns-holder` pair against a production workload
(only the isolated spike was run).
