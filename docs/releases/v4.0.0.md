## v4.0.0 — the engine gains layers and ports (ADR-0040), errors gain numbers (ADR-0043), and three crates are renamed

One hundred and fifteen commits since `v3.1.0`, the largest series since the repo's
extraction: ADR-0040's layered restructuring (phases P0–P3x), ADR-0043's numbered
`DX-CDNN` code dictionary, three crate renames, the elimination of `delonix-runtime-core`,
and a dozen real production fixes (CRI/cgroups, VM, networking, containers). This is the
reason for the major bump: anyone consuming this repo via `git`+path/tag feels the crate
renames as a compile break, and the CLI gained several incompatible changes.

### BREAKING — three crates were renamed, and one stopped existing

ADR-0040 phase P3 (#393–#396, #406): each crate's directory already stated the layer
(`crates/adapters/`, `crates/contexts/`, ...) since P0; this phase aligned the NAME to
each one's real role.

| before | now |
|---|---|
| `delonix-scan` | `delonix-scanner` |
| `delonix-image` | `delonix-oci` |
| `delonix-net` | `delonix-sdn` |
| `delonix-runtime` | `delonix-linux` |
| `delonix-runtime-core` | **eliminated** — the shared types (`Error`, `records`, `secret`, `typestate`, `exitcode`, the `DX-CDNN` codes) moved to `delonix-model`; the persisted state (`JsonStore` and what it stores) moved to the new `delonix-state` |

Anyone depending on this repo via `path`/`git`+tag in an external `Cargo.toml` (the
`delonix-paas` case) must update the crate names on the next pin bump — the `delonix`
binary and its behaviour don't change because of this, only the internal names of the
Rust crates that make it up.

### ADR-0040 — the layered engine: contexts, ports, and one binary per interface

Five phases (P0–P3x, #319 and the `arch(Pxx)` commit series that follows) close out
the restructuring `AGENTS.md` had already imposed since P0 (the `LAYERS`/`ALLOWED` table
in `scripts/arch_fitness.py`), now complete down to the code:

- **New context crates** (`crates/contexts/`): `delonix-compute` (the execution ports —
  `RunHost`, `ImageStore`, `StorageProvider`, `DeviceResolver`, `VmNetwork`,
  `NetworkProvider`, `WorkloadRuntime` — and the single `RunSpec` that `container run` and
  `container start` now share instead of each rebuilding its own), `delonix-node`
  (the node contract, `proto/delonix/node/v1`), `delonix-stack` (the 3-way reconciler and
  the Kind table).
- **Each port gained ITS OWN adapter**, one use case at a time (P2c–P3m):
  `DeviceResolver` in the kernel adapter (CDI), `NetworkProvider`/`VmNetwork` in the
  network adapter, `StorageProvider`/`ImageStore` in the storage and image adapters,
  `RunHost`/`WorkloadRuntime` in the engine adapter. `container run`, `container start`
  and starting a VM now resolve the same phase sequence (network → secrets →
  `--security-opt` → log path → start) through these ports, instead of three
  diverging copies.
- **One binary composes ONE interface** (P3k–P3m): `delonix serve cri` now EXECs the
  `delonix-cri` binary instead of embedding it; `delonix serve api` execs `delonix-mgmt`;
  `delonix mcp` execs `delonix-mcp`. `delonix` no longer links three servers inside
  itself — each gained its own `[[bin]]`.
- **Telemetry left the foundation** for `delonix-telemetry` (P3j) — the foundation
  (`delonix-model`) now holds only what any layer names without depending on a mechanism.
- **`build` starts the work container via `HostWorkload`** (#391), closing the
  last direct call to the engine that `build` still made outside the ports.

See `docs/adr/0040-*.md` for each phase's detail and measured evidence.

### ADR-0043 — the `DX-CDNN` code dictionary

Every failure gains a four-digit number — class (what to do next) + domain
(where it happened) + sequence — that never changes meaning and is never reused.
`delonix explain <code>` reads the same dictionary as the error line, the JSON and the
page generated at `docs/codigos.html`. Five steps close the foundation (#399–#403):

1. The dictionary itself + `delonix explain codes`/`delonix explain <code>`.
2. The number appears in the error line, in `-o json` and on the generated page.
3. The exit code is asked for the error's CLASS, not a variant `match`.
4. The specific number travels INSIDE the error (`delonix-scanner` was the first crate
   to gain its own typed `Error` with numbers).
5. `delonix-volume` gained its own.

Later, with no formal step number: `delonix-scanner` (#398) and `delonix-oci`
(#407) also gained their typed `Error`. **`delonix-truenas`, `delonix-proxmox` and
`delonix-vm` (including the cloud-init seed generator) have their own PRs in progress** —
they don't go into this release, they go into the next one once merged.

### CRI/cgroups — three production fixes measured against a real kubelet

- **A fresh root node started no pods at all** (#310): the cgroup delegation probe
  measured a path that only exists in user-delegated mode; as root, anything that
  requested `-m`/`--cpus`/`--cpu-weight` was refused — including the control plane's own
  static pods. Fixed by creating the slice by hand when it doesn't yet exist.
- **The single-node control plane went into a crash-loop** (#315): the kubelet creates
  pod cgroups as `systemd` slices, and `systemd` strips the `cpuset` controller from a
  slice with no units underneath it — exactly this engine's pattern, whose containers
  live OUTSIDE the kubelet's hierarchy. The CRI now reports `cgroupDriver: cgroupfs`,
  which is the truth.
- **As root, the node stayed `NotReady` with `BridgeMissing`** (#322): `RunPodSandbox`
  as root never had any pod network — it called a command `clap` refused. Five
  chained defects closed: real CNI network on the host for root sandboxes, non-root
  `USER` starting with `--cap-drop ALL`, writable `/proc/sys` under `--privileged`,
  `ContainerConfig` environment variables finally delivered to the container, and
  `NET_ADMIN`+non-privileged ports per pod netns.
- CRI containers enter the kubelet's cgroup hierarchy (ADR-0038 phase 1, #325):
  "no limit" is only really no limit under the kubelet — the host's ceiling still
  protects outside of it. The eviction manager got its statistics back and
  `kubeadm reset` no longer leaves orphans (#316).

### `runtime`/`container` — supervisor, restart, and a more honest `run -d`

A dozen chained fixes around the `--restart` supervisor and the container
registry (#357, #362, #365, #367, #368, #372, #374, #377–#380): an allow-all seccomp
profile no longer aborts the container; restart-policy restarts now count in
`RESTARTS`; a `run -d` whose command doesn't start is refused with `exec`'s real
reason; a `stop` that interrupts the wait between restarts is honoured; a delayed
supervisor, a resuming stop, and a concurrent restart no longer stomp on each other on
the recorded PID — each of these was a real race, reproduced before the fix.
`container run --net-bps` on a `-d` is now applied (P2e); a refused `run` no longer
leaves the container's directory behind (#359); a privileged container has writable
`/proc/sys` again (#318, the same root defect as the CRI finding above).

### `vm` — cloud-hypervisor, libvirt, pause and recreation

- **cloud-hypervisor's `boot` now only returns once the VMM confirms the VM is running**
  (#350) — it used to return on launching the process, without confirming it had started.
- **`vm stop` tries a graceful shutdown and detects a corrupted disk immediately** (#304).
- **A paused libvirt VM stopped showing up in `vm ls` without `-A`** (#312, #363).
- **A VM recreated with the same name stopped announcing the previous one's IP** (#320).
- The VM engine connects to the SDN through the `VmNetwork` port and no longer depends
  directly on `delonix-net`/`delonix-sdn` (P3i, #383).

### `network`/`proxmox`/`pod` — IPAM reaper, pod ports, and the Proxmox node lock

- **`network ipam ls`/`prune`** — the lease registry reaper, respecting pod
  liveness (#308), closing the leak documented in `AGENTS.md`.
- **A pod member's ports are released and republished correctly**, and publishing
  live on a pod member now goes through ingress (#375, #376).
- **`delonix-proxmox`**: `create` no longer sends `ipconfig0` twice, and back-to-back
  operations no longer die on the node lock (#314).

### `delonix init` — CI/CD, adopting an existing project, and the Odoo template

- `stack init --template --up` now honours the declarative manifest (`stack apply`)
  instead of a raw `container run` written separately (#291).
- `delonix init` over an already-existing directory now **adopts** instead of dumping
  sample code over it (#292).
- The 7 templates with real code gained CI/CD (GitHub Actions + GitLab CI),
  `sonar-project.properties`, `CONTRIBUTING.md` (git-flow + Conventional Commits + SemVer)
  and `commitlint` in the three JS templates (#293).
- `-v/--template-version` reached all 11 templates (#297); the `odoo` template follows
  OCA recommendations, with live reload (#296).
- **Validated live, all 11 Delonixfiles**: a real build and service confirmed for each one
  (#300).

### `docker-api`/`compatibility`/other fixes

- `POST /wait` returns the real exit code; `HostConfig.RestartPolicy` is now
  honoured (#370, #371).
- `delonix compatibility docker` — the top-level Docker compatibility matrix, with
  `-o json` (#306).
- An image the registry doesn't authorize reading now replies "doesn't exist" instead of
  leaking its existence (#381); a cached layer now correctly replaces the obsolete one
  instead of duplicating it (#299).

### Known, not fixed in this series

- `delonix-truenas`, `delonix-proxmox` and `delonix-vm` still use the generic,
  shared `Error` — the three conversions to the `DX-CDNN` dictionary are in an open PR,
  not merged in time for this release.
- `image vm ls-remote` with no argument can take over 90s on a slow connection and has no
  `--timeout` (inherited from `v3.1.0`, untouched in this series).

### Not validated in this release

The full `kubeadm apply`/`kubeadm` multi-VM cycle with real SSH between nodes, and the
CNI path as root beyond what `crictl` already exercised directly — these need a second
physical node or a real kubelet, neither available in this sandbox.
