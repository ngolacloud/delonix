## v0.2.1 — a `depends_on` that names nothing is an error, not a panic

Patch release on top of `v0.2.0`, cut from `main` — the released line — over
the **9 commits** that landed there since the tag, release commits aside: five
user-facing fixes, and the rest test isolation and release tooling. Each fix
reached `main` as its own squash PR, twinned on `develop`; the features that
landed on `develop` since `v0.2.0` **do not** come here — functionality does
not ship in a PATCH, it ships in the next minor. There is no contract change:
the one new refusal (`--rm` with a restart policy) is a combination that could
never have worked, and Docker refuses it too. The section-categorized summary
is in
[CHANGELOG.md](https://github.com/ngolacloud/delonix/blob/main/CHANGELOG.md).

---

### A compose `depends_on` that names nothing is an error, not a panic (#1060)

`delonix compose config` (and `up`) died with `no entry found for key`, exit
101, when a `depends_on` named a service the file does not declare — seen on
`v0.2.0`. The active set took in every name an active service depends on,
declared or not, and the topological sort indexed the service map with each of
them: the missing name blew up whenever it sorted before the service naming it
(`db` < `web`). The check that already existed only ran for the dependent
service, too late in that order.

Now `load_compose` validates the graph right after `extends:` is resolved, so
`config`, `up`, `down`, `ps` and `logs` all refuse the file **before doing
anything**, with the same message:

```
service 'web' depends_on undefined service 'db'
service 'a' depends_on itself
depends_on cycle: a -> b -> a
```

The same holds for the short list form and the long form with `condition:`. A
cycle and a self-dependency were already errors, but they said
`circular depends_on involving: a, b`; they now name the path, like
`extends cycle:` does. The sort itself no longer indexes the map with `[]`.

### A cluster's node network never lands on the pod or service subnet (#1054)

The node network of a cluster (`dlx-<name>` in kind mode, and the network of
`cluster kubeadm` without `--network`) was chosen by a hash of the name in
10.201–10.254 — a range that contains `10.244.0.0/16`, kubeadm's default
podSubnet. About one name in 55 fell there. Inside each node that range is
routed to the CNI, so the API answered from inside the node and hung from the
host, with nothing refused at creation; the workaround was an explicit
`--pod-subnet`.

The allocator now treats the cluster's pod and service ranges as taken, and
says which ones when no /16 is left outside them. A network that already exists
on top of one of them is refused with **DX-1704** before anything is created,
naming the `delonix network rm` that clears it. Kind mode also checks its CIDRs
against the engine's other networks — `cluster kubeadm` always did, kind never
had — so a kind cluster with the default podSubnet on a host that already has a
network in `10.244.0.0/16` is refused instead of created broken.

Not validated live: a real `cluster create` whose name hashes into 244.

### `run -d --rm` removes the container when it exits (#1051)

Every CLI `run -d` runs under a per-container supervisor, and `run` returned on
that path before reaching the `--rm` branch. So
`delonix container run -d --rm --net none python:3.11-slim python3 -c 'import sys; sys.exit(3)'`
was still listed as `Exited (3)`, with its record and directory left behind.

The supervisor now carries `--rm` and, after the last incarnation, removes the
container exactly as `rm -f` does — only if the record still exists and is not
live, so a record that `rm -f` already took, or that a `container start`
brought back, is left alone. `rm`, foreground `--rm`, the unsupervised watcher
and the supervisor share one cleanup. Two visible consequences, both as in
Docker: `container stop` of a `-d --rm` container succeeds instead of exiting 4
("no such container"), and **`--rm` with a `--restart` policy other than `no`
is refused** before anything is pulled.

### `stack init -t django --up` becomes healthy (#1050)

The Django template could not get healthy: the container started, exited 1 and
restarted until `--up` gave up at 120 s with
`ModuleNotFoundError: No module named 'config'`. The launcher runs as a script
(so `sys.path[0]` is `/app/docker`), the image's `PYTHONPATH` carries only the
dependencies, and `os.chdir("/app")` changes the working directory but not
`sys.path` — so the in-process migrate that `MIGRATE_ON_START=true` turns on
could not import the settings. The launcher now puts `/app` on `sys.path`
before it, and a gate pins the class: any template with a `docker/launch.py`
and an in-process bootstrap must put the application root on the path first.

### The docs stop teaching `vm build` (#1043)

`delonix vm build` was retired in #772, but 32 files still taught it —
`images/**`, the appliances README and the pt-AO/fr-FR/zh-CN translations of
the Delonixfile/Vmfile guide — and copying the line gave
`unrecognized subcommand 'build'`. They now say `vm image build`, and
`docs_cli_gate` covers those folders.

### Under the hood

- **Test isolation** (#1046): a `delonix-sdn` test that resolved the ambient
  root without holding the test lock wrote into another test's temporary root,
  and that test's cleanup failed with `Directory not empty` on CI. A test
  thread that resolves the root unpinned now fails on every run, not only when
  two tests overlap by microseconds.
- **The scaffold unit tests no longer run the host's package manager** (#1055):
  generating a project in a test used to run `pnpm`/`uv`/`composer`/`cargo`
  against the network.
- **The release gate** no longer reads the check-runs of the run that is asking
  as evidence about the commit (`e126a878`) — they showed as red when the
  dispatch sat on the tag's own commit — and the generated `docs/RELEASES.md`
  header is in English, as LANG-01 requires (#1043).
