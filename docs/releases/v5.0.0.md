## v5.0.0 — the image's `USER` is who runs, the typed `provider` block, and the node contract now served

Two hundred and two commits since `v4.5.0` (162 not counting merges), from `#572` to
`#720` — measured at `831b9601`, the tip after the second `main` merge of
2026-10-08 (`git rev-list --count v4.5.0..831b9601`).

The number now goes together with the commit at which it was measured, because without that
it ages silently: the "180 (152)" of this note were correct at `ea38d89b`, where they were
counted, and stopped matching the branch as soon as it grew. Pinning it to a
sha makes it verifiable instead of a claim about "the tip".

**Numbered as MAJOR for one reason only, and it is in the next section**: a container
now runs as the user the image declares. Everything else in this release
is additive, or is a refusal to replace a success the engine could not
prove — but that change breaks the `container run` contract, and a broken
contract does not ship in a MINOR.

The thread running through this release is the same as the last few, carried onto the
declarative surface: **what the engine cannot prove is not reported as a success, and what it
does not understand is not swallowed in silence**. In this release that reaches manifests (an
unknown field rejects the whole document), isolation (a namespace the host
would not enforce is refused rather than applied), limits (`--device-*` with no disk
that accepts them) and lifecycle (an `rm -f` that gave up is not resurrected by the
supervisor).

---

### Contract break — read before upgrading

**A container runs as the image's `USER`** (ADR-0062, `#632`, `#633`, `#637`,
`#638`, `#639`). Up to v4.5.0, `container run` ignored the `USER` the image
declared and the process ran as uid 0 — since v1.0.0, with no error or warning.
Measured with `haproxy:3.4-alpine`, which declares `USER haproxy`: `id` inside the
container answered `uid=0`.

What changes, and what to do about it:

- **Without `--user`, the process runs as the image's `USER`.** A service that
  depended on being root without asking for it stops being so. To keep it, `--user 0`.
- **On a rootless host with no subuid range, only one uid fits**: it stays at 0 and the
  `run` says so out loud, instead of failing.
- **`--user` no longer hands the whole filesystem to the user.**
  The old sweep (`chown_tree_once("/")`) gave it 940 of the 986 entries of a
  15 MB image — including `/etc/passwd` and the service's own binary — and
  crossed mounts, re-owning a HOST bind mount (a file owned `1000:1000`
  ended up owned by a subuid, and the owner could no longer write to their
  own file). Now the container receives **what the image gives it**: an ownership
  index recorded when extracting the layer, applied once by the init, never on another
  filesystem. Measured afterwards, on the same image: 2 user-owned entries
  instead of 940, a 56 K write layer instead of 13 MB, and the host bind
  untouched. On `odoo:20.0` (~2 GB), the first boot with `-u odoo` went
  from "still sweeping at 16 minutes" to **1.7 s**.
- **An EMPTY named volume** gets the owner the image assigns to the mount point,
  or the container's user when the image names nobody. A volume with
  data and a bind mount are **never touched** — a filestore written as root by
  a previous run is not migrated.
- **`build` follows the same rule**: a `RUN` runs as the `USER` in effect at that
  step (previously it always ran as root, even after a `USER app`), and the layer
  cache preserves ownership — a cached rebuild used to lose it.

**Two public signatures of `delonix-sdn` changed** (`#718`):
`can_bind_host_port` and `host_port_busy` now take a `Proto`. Consumers of the
crate via `git` + tag are not broken today, but bumping that pin requires a
pass. The old signature couldn't stay, because it **was** the trap: the two
probes always opened a `TcpListener`, whatever the spec, so a UDP publish
was checked against TCP — blind by construction, with the conflict showing
up only inside slirp as opaque JSON. The enum forces every call site
to state the transport, and refuses at that boundary the `sctp` the CRI can
emit instead of probing it as TCP.

Side effect of the same pass: extraction now preserves **setuid, setgid
and sticky**. Every container's `/tmp` used to be `777` instead of `1777`, and a `su`
setuid lost the bit. A layer extracted by an earlier engine is fixed up from
the blob headers the first time an image uses it.

### Behaviour changes

**The bind address of a published port is now RECORDED** (`#718`). It was
in-memory state at publish time and never persisted: the record stored the spec as
written (`51072:80`) and `DELONIX_PUBLISH_ADDR` was re-read from the environment on every
`start`. Fifth occurrence of the trap "state needed to REBUILD the
resource must be persisted". Measured both ways, against the bind read from
the kernel:

- published with `DELONIX_PUBLISH_ADDR=0.0.0.0`, it came back on **`127.0.0.1`** after
  a `start` — which is what a `net boot enable` unit runs, with no environment
  at all. Service down, listing saying published;
- and the OPPOSITE, which is what matters for security: a port published on purpose
  **without** an address (loopback only) came back on **`0.0.0.0`**,
  exposed to the whole LAN, because the shell that ran `start` had the
  variable exported.

In both cases rc=0, no warning, with `net ingress ls` printing the same line
before and after — `51070:80` and `51072:80` were identical bytes on disk with
opposite reach. Now the stored spec is always `addr:hostPort:contPort/proto`, and
`container ls` shows the address (`0.0.0.0:55070->5070/udp`) in the column read
precisely to decide what is exposed. A spec **without** an address now
means "record predating this version".

New refusals. In all of these cases the engine **used to accept and not honour**.

**A `hostPort` the node does not publish (ADR-0074, `#720`)** — and the refusal is **per
path**, because the paths differ and measuring them is what showed it: the
`slirp4netns` refuses SCTP in `add_hostfwd` (`bad arguments.proto`), the CNI
`portmap` publishes it end to end, and `hostNetwork` publishes nothing (the container
is in the host's REAL netns and binds the ports itself). A blind response would have
closed a port that is actually open in root mode. The refusal comes from
`RunPodSandbox`, before the sandbox exists, as `failed_precondition` — which the
kubelet shows as a pod event rather than a `StartContainer` retried
forever. A `containerPort` without `hostPort` is still dropped, which is the way
an SCTP **Service** works: no SCTP service is affected.

**Manifests (ADR-0069, `#682`, `#687`)**

- **A field the engine doesn't understand rejects the manifest, before any
  effect** — including inside the items of a Pod's `spec.containers[]`, where
  probes and `lifecycle` don't exist and used to disappear silently there too.
  `stack validate` still REPORTS instead of refusing, and
  `DELONIX_MANIFEST_LENIENT=1` is the explicit escape valve.
- **A field a Kind refuses BY NAME keeps its own code.** The
  `unprivileged: false` of a `SystemContainer` used to answer `DX-1000 unknown field —
  check the spelling` for a correctly spelled field; it now answers `DX-1540`, which says
  what the field is.
- **The same Pod name in a different namespace is a conflict**, not "already exists"; and
  `Container` and `Service` are now identified by `(namespace, name)` —
  two namesakes in different namespaces are no longer one resource in the plan.
- **An unreadable store is an error, not an empty machine** (VM, volumes, container
  presence). A `plan` that reads zero because it couldn't read used to propose recreating
  everything from scratch.

**Isolation and networking**

- **A named namespace on a host that doesn't filter bridge traffic is refused**
  (`DX-6305`, exit 69, decision D5 of the maturity plan, `#664`). Without
  `br_netfilter` the chains are installed, the sets are filled, every
  command reports success — and the boundary doesn't exist. It is the most expensive
  kind of silent failure this engine can have, because what fails is a
  security property that reads as enforced. Escape valve:
  `DELONIX_ALLOW_UNENFORCED_ISOLATION=1`.
- **Anti-spoofing moved to a `bridge` table, where it actually cuts**
  (`#671`). The old rule (`ip … iifname <veth> ip saddr != <ip> drop`) had its
  counter at zero: between two ports of the same bridge, the `iifname` the IP
  layer sees is the BRIDGE, never the port. Measured: a container with `NET_ADMIN`
  spoofed the source and reached its neighbour (3/3), and spoofing the address of a member
  of another namespace broke through isolation. It now pins by port the MAC, the IPv4
  source, and the ARP sender. **A lesson that stays: a security rule is only proven
  once a spoofed packet is counted being dropped** — the audit that "closed"
  this read the ruleset and saw the rule there.
- **Grants belong to the administrator, not to the request** (`#672`):
  `--allow-source <cidr>` and `--no-source-check` exist for a container that
  forwards, but they are PERMISSIONS in node policy. Without a policy, nothing is granted,
  and `mode: warn` does not grant.

**Lifecycle**

- **A `--wait` that times out exits with 124 (`DX-8503`) and leaves the VM running**
  (decision D6, `#661`). It used to return 0: a `--wait` that never saw the VM respond
  reported success.
- **`--device-read-bps`/`--device-write-bps` are refused when there is no disk
  that accepts them** (`#663`). `io.max` now names the disk the container's
  rootfs lives on; before, the limit was written and not applied.
- **An `rm -f` that gave up is not resurrected by the supervisor** (`#647`). With the
  disk full, `rm -f` returned `DX-8101` and kept the record as the rule
  demands — and when the process finally exited, the `--restart always`
  supervisor restarted it. The removal intent is now recorded BEFORE the signal.
- **A `stop` that gave up keeps the process recorded**, and a `start` that fails
  after an `rm -f` takes its directory with it (`#604`, `#607`).
- **A container's `slirp4netns` dies with it** (`#646`, `#648`, `#651`). It used to be
  spawned mid-boot and inherit the caller's descriptors, so it stayed
  alive holding the published port after the container exited — and the next
  `start` hung forever waiting for an EOF only that slirp could give.
  Measured: over an hour of survival with the disk full.

**Declarative surface**

- **The `provider` block is `type` + `spec`** (ADR-0070, ADR-0071). What only a
  manufacturer understands lives **inline** in the resource, typed by provider AND by
  resource: a key the `type` doesn't know is refused. `backend:` became
  `provider.type` on a `VirtualMachine`, and the `libvirt:` group and flat fields
  normalize to the same thing. **The earlier spellings still load and still
  mean the same thing**, reported as superseded; repeating a field in both
  places is refused.
- **`kind: NetworkZone` became `kind: Network` with `spec.provider.proxmox`.**
  Networks naming the same zone merge on load into the single document the
  reconciler already reconciles — the zone is created with the first vnet and removed
  with the last, with no reference counting. The old name still loads, flagged
  as superseded.
- **A workload governed by policy is born CLOSED** (ADR-0069 D6, `#685`,
  `#686`). A container or Pod named by a `NetworkPolicy`, `NetworkAccessRule`, or
  manifest `Dependency` is created with the default-deny chain installed
  before the process, and is only opened to what the policies say once they are
  in place. If one layer fails, the workload stays closed and `apply` says so.

### What's new

**`hostPort` is now published in root/CNI mode** (ADR-0074 D3, `#720`). It wasn't, for
ANY protocol: mappings were stored and then dropped, and the pod came
up `Running` with a port that didn't respond — silence, rc=0. The
`portMappings` now pass through as the plugin's `runtimeConfig`, the way containerd
does, and that delivers tcp, udp, **and** sctp at once. The capability
argument is injected into the conflist, and that is what spares new plumbing on either
CNI path: root hands the list to `attach_named_netns`, rootless hex-encodes the SAME
JSON over the holder's control line (whose shape doesn't change, so an old
holder still works), and storing the result as the sandbox's conflist
returns the identical configuration to `DEL`. The declaration is read from
the plugin's own `capabilities.portMappings`, never from a list of names; a
chain that doesn't declare it is refused the right to name `portmap`. Measured on a
VM from this repo's golden with `crictl`, against both binaries: before **0**
DNAT rules and no response on the port, after **3** rules, response on the
host port, and **0** rules after `rmp`.

And `hostIP` now travels this same path: dropping it would publish on all
interfaces a port the pod asked for on just one — exposure widened silently, the
same defect `#718` fixed from the other end.

**System containers on Proxmox — `kind: SystemContainer`** (ADR-0058, plan
63, `#579`, `#582`, `#583`, `#588`, `#590`–`#594`)

A Proxmox LXC doesn't fit `kind: Container` — the node API has no `exec`, logs,
or exit code, and the engine's dataplane doesn't reach there. It comes in as its own
resource, with semantics close to a VM: the engine pulls the image and writes the
OCI archive the node accepts, the node runs the container, and a hand edit on the node is
**drift** (`plan` returns 2 and `drift` shows it). `memory`, `swap`, and `cores` are
hot; `rootfs` only grows (shrinking plans a `Replace`). Full Day 2: snapshots (with a
`restore` that waits for the node to respond again — measured, ~40 s
during which pveproxy returns 596 to anyone waiting), backup to the node's storage,
clone, firewall via `kind: NetworkPolicy` with `scope: systemcontainer`, and
migration between nodes (offline, because the node aborts a `restart=1` when the init
ignores SIGTERM and leaves the container at the origin while `pvesh` exits 0). `exec`,
logs, and exit code are `unsupported-by-provider` with the reason written out.

**The node contract is now served** (ADR-0042, `#659`, `#662`, `#669`,
`#670`, `#673`, `#674`, `#680`, `#681`)

Until now `proto/delonix/node/v1` was a contract with not a single Rust producer.
Now there is `delonix serve node-api`: **gRPC and HTTP/JSON from the same `.proto`**, on
a local unix socket, own uid only.

- `NodeService`: `GetApiRoot` (`GET /v1`, with `links` to everything served),
  `GetNodeInfo`, `GetHealth`, `GetCapacity`, `ListProviders`.
- `NetworkService`: the reads (`ETag`/`If-None-Match` with 304, `label_selector`,
  pagination with `Link rel=next`) and the first two mutations, `CreateNetwork` and
  `DeleteNetwork`.
- `VolumeService`: `GetVolume` and `ListVolumes`. `Get` measures usage; `List` does
  not measure, and says so — scanning the data of every volume on each listing is a
  cost already measured on the dashboard. Unknown is never zero.
- `OperationService`: **every mutation responds with an `Operation` persisted before
  the work**. An unfinished record whose owner no longer exists is terminated
  `FAILED` with reason `Interrupted` — the server is socket-activated and has nobody
  to do it for it. `Idempotency-Key` is the `request_id` and `If-Match` the `etag`.
- **REST errors are RFC 9457 documents** (`application/problem+json`),
  built from the engine's code dictionary, and the published OpenAPI declares it.
- **REST routes are GENERATED** from the `google.api.http` annotations in `build.rs`: a
  contract route not yet served answers 501 (`DX-6001`), a path outside the
  contract 404.
- `GET /openapi.json`, and the `GET /docs` (Swagger UI) and `GET /redoc` pages,
  served from files embedded in the binary — byte-identical to the npm
  packages, checked against their `SHA256SUMS` at build time, under a CSP that only allows
  the socket (measured in a browser: the logo ReDoc fetches from a CDN is blocked before
  any request leaves).

**Role-based network providers** (ADR-0059 F2–F5, `#614`–`#636`, `#654`, `#656`)

The network contract is now organized by ROLE, with its own context
(`delonix-networking`): `GatewayProvider` and `SegmentProvider`, chosen by
name in `providers.yaml`. On top of this:

- **A typed policy IR** with a reference evaluator: the firewall record
  either parses against it or is refused whole, and the holder's chain, a VM's
  firewall, and a gateway's perimeter filter are three **descents from the same IR**.
- **A network plan observes the device and names drift**, has a **digest**
  (`--plan-digest` refuses a stale plan with `DX-5390`), and a **steps log**
  that resumes an apply killed midway.
- **New roles on `NetworkGateway` and on the segment**: `nat:` (SNAT and 1:1),
  `ipam:` (subnets, DHCP, reservations), and `dns:` (records written by the node).
- **A failure states which provider, role, and step it came from** — and remote
  clients no longer echo the credential back inside it (a real leak, closed with a test
  that greps for both).

**Storage pools** (ADR-0067 P0, `#689`)

`kind: StoragePool` and the `delonix-storage` context, with the `dir` driver. The
administrator declares pools in an allowlist (`/etc/delonix/storage-pools.yaml`);
a manifest only NAMES a pool, and `driver`/`path`/`device` in a manifest are
refused by name. Ownership is by marker, never by name: a directory with data
and no marker is never adopted. Above 95% occupancy nothing is allocated (`DX-5202`).
The engine **never creates or destroys** a pool.

**`delonix init`** (ADR-0061, `#625`, `#631`, `#640`–`#645`, `#649`, `#653`)

- The seven application templates generate **a small, complete service**: a
  transport-to-port capability, configuration validated at boot, readiness
  `starting → ready → draining`, bounded shutdown, webhooks in both
  directions, OpenTelemetry, an OpenAPI contract with a drift test, and a
  dependency-direction test. The generator **checks what it replaces**.
- **The three edge templates are born with HTTPS** (certificate generated by `init`,
  `mkcert`, or self-signed), sized for load, with JSON logging and
  `request_id`. `scripts/tls.sh` renews, installs a certificate of your own, or runs
  Let's Encrypt via **HTTP-01 or DNS-01** — both proven against Let's Encrypt's
  real production.
- **Every template ships an opt-in tunnel to the internet** (`delonix-tunnel.yaml`),
  for anyone without a public IP.
- `--port`, `--tls-port`, and `--hostname` answer on the command line what
  `init` asks in a terminal; a second `--up` on a project already standing
  converges it and deploys what was rebuilt.
- The `odoo` template boots again (Odoo 20 by default) and runs as `odoo`; the
  `python` one is now called `fastapi`, with the old name as a silent alias.

**Versioned secrets** (ADR-0069 item 6, `#696`, `#700`)

A `Secret` now carries a **version** the store assigns (1 at creation, +1 when
values change), and `secret apply` reports `created`/`unchanged`/`rotated to version
N (changed: KEYS)` — **by key name, never by value**. `stack plan`
converges a Secret that carries its own values, comparing key names and a
**keyed** fingerprint (never a value; the node's master key is in it, and
a node without the key plans a `Create` and creates nothing). A container records the
version of each `--secret` it booted with, and `describe` says when it was rotated
since.

**FreePBX appliance** (`#657`, `#693`): FreePBX 17 + Asterisk 22 on Debian 12,
with secrets per clone on first boot, proven end to end (27/27 in both
modes).

### Structure (ADR-0044 P4b)

Backend knowledge moved out of orchestration, and VMs stopped living in a single
adapter:

- **Three ports in the compute context** (`LocalDiskImages`, `SeedBuilder`,
  `VmNetwork`) and the use cases over an injected store (`#596`, `#597`).
- **The backend registry** moved to the context, seeded from the composition
  root (`#599`).
- **Two new provider crates**: `delonix-provider-libvirt` (`#602`) and
  `delonix-provider-cloud-hypervisor` (`#608`).
- **`delonix-vm` was reduced to the composition root** (`#610`), and each
  provider carries its own locale guards.

### Performance

Measured, per item, with the reasoning for each decision (including the rejected ones) in
`AGENTS.md`:

| Path | Before | After |
|---|---|---|
| Memory on `pull` of `node:22` | 214 MB | **27 MB** |
| Memory on `pull` of a VM image | 278 MB | **13 MB** |
| Memory on `push` of a VM image | 837 MB | **10–13 MB** |
| `push` of 4 layers at 20 MB/s | 65 s | **11 s** (in parallel) |
| `push` of a tag the registry already has in another repo | 356 s | **7.0 s** (mounts instead of uploading) |
| Cold build of a template | 6.8 s | **2.2 s** |
| Build with only `COPY` changed | 7.2 s | **1.1 s** |
| Extraction of `node:22` on the first `run` | 4.3 s | **2.1 s** (layers in parallel) |
| `run --rm … true` with 1 GB dirty on disk | 9.5–14 s | **0.14 s** (`volatile` overlay, ADR-0056) |
| `cluster load` across 3 nodes | 33.2 s | **17.6 s** |

A `pull` cut off midway **resumes** from what's already on disk, across
processes (measured with a `kill -9`: the next pull continued and the digest matched), and
a cut-off `push` continues from the last block the registry confirmed. A registry
token issued **anonymously** is cached on disk (ADR-0060) — never one
obtained with `image login`, never on a push.

### Build and development

- **The catalogue maturity metric is now COMPUTED, with a ratchet**
  (plan 65 F0.1, `#715`). It used to be counted by hand over the published markdown, and the
  two counts in circulation were **both wrong**: plan 66's came from
  a `grep -c` that counted the per-provider summaries, the introduction's prose, and the
  word `supported` inside `unsupported-by-provider`; plan 65's said 99
  of 265. The real count is **100 of 252 (39.7%)**, and `provider ls` agrees.
  A number measured by grepping a document is not a metric — it's the document
  talking about itself.
- **A lab's credentials stopped being one `git add -A` away from being
  published** (`#716`). Measured at this repo's root, which is PUBLIC:
  `opnsense-lab.env`, with a key and secret in plain text, was not ignored by anything —
  the only thing between it and a push was the house rule to never use `git add -A`.
  A rule is an intention; this is a lock. Nothing was deleted.
- **A `Makefile` for the developer cycle**: `bootstrap`, `doctor`, `build`,
  `install`, `ci`.
- **The release binary no longer depends on the checkout path** — two
  different trees produce the same binary.
- Lighter `dev` profile, `release-ci` profile, and `nextest` in `make test`.
- **Nightly lab** (`lab.yml`): a workflow on a self-hosted runner with a
  preflight that fails if the host lacks KVM, userns, delegated cgroup, and
  `br_netfilter`, and a gate that fails a scenario that skips without an accepted
  reason. **The runner is not registered, and the schedule is firing into the void**:
  measured on 2026-10-06, the runs for 2026-10-04 and 2026-10-05 sat in a queue
  waiting for a runner that doesn't exist and were cancelled at 24 hours, and today's
  has been queued since 09:04. Registering the runner is the owner's step.
- Contributor manual up to date with `main`, in all four languages (`#601`).
- New ADRs: **0060** (anonymous token cache), **0061** (template contract),
  **0065** (IPv6 in the dataplane), **0066** (L4 load balancer), **0067** (storage
  pools), **0068** (VM hotplug), **0069** (reassessment of the Kind catalogue
  and strict manifests), **0070** and **0071** (the `provider` block). The
  0065, 0066, and 0068 are accepted as decisions and **have nothing implemented** — they are
  work for upcoming releases, not this one.

### Consolidation and what measurement found (2026-10-06)

The last pass before this release consolidated the work of five parallel
sessions into a single plan (`docs/discovery/66_CONTINUITY_PLAN.md`) and ran the
measurements it requires. What that produced, besides the numbers in the next
section:

**A store opened on one root stopped writing on another** (`#719`), and the
obvious hypothesis was wrong. `tmp_roots_gate.py` was failing on `main` at random —
`cargo test -p delonix-sdn` left 3, 0, and 1 leftovers across three identical
runs. The natural reading was "the `TempDir`'s `Drop` swallows the removal error", and a
`TempDir::close()` with the error visible would have **passed without catching anything**:
followed with `strace` across the six parallel test binaries, the removal did work and
the directory **came back** afterward, put there by ANOTHER test. It wasn't a
cleanup that failed; it was a store writing to a root that wasn't its own.

- **A guest governed by policy is born closed, or is not born** (ADR-0069
  D6, `#705`). D6 closed containers and Pods; a VM and a system container
  were left out, and the reason was real — their firewall belongs to the provider, not to
  the holder. It is now created with its own firewall in effect, default-deny in both
  directions, **before the guest has CPU**, and a backend that can't do this
  (`VmBackend::holds_at_boot`) **refuses by name** (DX-1501) instead of creating the
  guest open. Only Proxmox has it today; both local backends refuse, and the
  refusal says where `scope: vm` applies.
- **The same VM name in a different namespace is a conflict, not "ensured"** (`#706`).
  The record is `vms/<name>.json`, regardless of namespace, so the name is
  unique on the node — and a manifest requesting the same name in a different namespace used to get
  `stack plan` = "1 unchanged" and `stack apply` = "ensured" with rc 0, **with the VM
  staying in the first namespace**. On a VM the namespace IS the isolation
  boundary, so the tenant requesting the second one ended up with a VM the first one could reach
  and theirs couldn't. It now refuses (class 5) before resolving or creating anything.
- **Two battery preconditions that made an ENVIRONMENT failure read as
  thirteen engine failures** (`#703`): a second image pull with its output
  discarded, and fixed idempotency keys on the node API.
- **A test that asked the hex digit itself** (`#702`): the check that a secret's
  fingerprint doesn't leak the value used `"bc"`, which IS hex —
  21 failures in 300 runs, measured.
- **Nine ADRs accepted** (0020, 0040, 0041, 0049, 0055, 0061, 0063, 0064, 0067) and
  **two new ones** (0072, 0073) closing the last two rows of the
  ADR-0070 table through measurement rather than motion. Accepting 0040 unblocked
  M01's `capability discovery`.
- **Two new gates over the registry itself** (`#707`, `#708`): an ADR cannot
  contradict itself about its own status, and the index cannot disagree with the document —
  seven lines disagreed, two of them for twelve days.
- **A policy written by pod name is read by the same name** (ADR-0069
  pending item 1, `#713`). Mutations had already accepted the pod name since `#705`;
  READS had not. `net ingress ls <pod>` and `describe networkpolicies <pod>/<dir>`
  used to answer `no such container` about a policy the engine had just
  accepted under that name, and `get networkpolicies` named the MEMBER where the
  operator had written the POD — on a two-member pod, four lines, and the two
  for the member with no firewall saying "allow (default), 0 rules" on top of a policy
  that exists. Measured live against `main`: the write passes, the three reads
  fail. **And generic DELETE wasn't deleting**: with a `deny` in effect,
  `delete networkpolicies <c>/ingress` returned rc 0 and "removed 0 inbound
  rule(s)", reads still showed `deny`, and traffic stayed
  blocked. This closes the last "STILL TO DO" of ADR-0069's pending item 1.
- **A field the workspace already declares is no longer hand-written** (`#711`, `#712`).
  `inline_versions` only looked at DEPENDENCY versions, so the crate's own
  `[package]` metadata had no guard — and that's how `delonix-mgmt`'s
  manifest said `version = "0.1.0"` for two and a half months
  while the workspace moved toward 4.5.0. The four copied fields now go
  through the workspace, and a new gate rejects the fifth.

### What was NOT validated

Stated here because the implicit reads as proven:

- **The nightly lab never RAN**: the schedule fires, but every
  run sits in a queue waiting for the `delonix-lab` runner, which isn't registered,
  and gets cancelled at 24 hours. All the evidence for this release comes from manual
  runs, on a development host — and the cost of that was measured in this pass: the
  performance gate needed **three attempts** to produce a verdict,
  because the first two caught the machine with I/O spreading the measurement 27×.
- **The capability catalogue cell metric is 100 of 252 applicable
  (39.7%)** — that is, 88 cells are implemented and **not proven**, and 64
  don't exist. The matrix (`docs/providers/capability-matrix.md`) states, cell by
  cell, which is which, and since this release it prints the number at the top: it is
  COMPUTED from the catalogue in code and locked by a two-way ratchet
  (`scripts/capability_ratchet.py`). Until now it was counted by hand over the
  markdown, and the two counts in circulation — "111 of 281" and "99 of 265" —
  were both wrong: the first came from a `grep -c` that counted the
  file's own summaries as if they were cells.
- **Root/CNI `hostPort` was not validated with a kubelet** (`#720`): everything was
  driven through `crictl` — the Kubernetes project's own official client, over the same
  transport a kubelet uses — and through tests, not through a kubelet scheduling the
  pods with its own retries and its own notion of readiness. And it was **one node, one
  chain** `bridge`+`portmap`: a real cluster CNI (Calico, Cilium) declaring the
  capability differently, and more than one node, remain unmeasured.
- **SCTP is proven on the `portmap` path, not on the engine's own nftables**
  (ADR-0074 D3.1): the route where the engine would write its own
  `sctp … dnat` in root mode was only loaded into a kernel as a ruleset — no
  packet crossed it. Whoever builds it starts by closing that gap.
- **The recorded bind address was not measured across a reboot** (`#718`): the
  proven cycle is `publish` → `stop` → `start`, which is what a `net boot
  enable` unit runs, but the machine's own boot was not exercised.
- **No conformance is claimed**: the OCI, CRI, CNI, and CSI suites did not
  run. The published CRI number (79/103) is from `critest` v1.36 against engine
  **v0.63.1** and was not re-measured.
- **IPv6, the L4 load balancer, and VM hotplug don't exist** — they have an accepted ADR and
  zero code.
- **Storage pools are at phase P0**: only the `dir` driver. The privileged
  helper, btrfs, ZFS, LVM-thin, and VM disks on pools need root and
  disks on a lab VM.
- **OpenStack is not an engine provider**: ADR-0039 exists in *Proposed*, with no
  backend, and `provider.type: openstack` is refused on load.
- The ordering of remaining work is at
  `docs/discovery/66_CONTINUITY_PLAN.md`.
