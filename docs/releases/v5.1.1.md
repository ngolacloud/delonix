## v5.1.1 — the installer shows where the release is, and `--l18n` stops being accepted after a subcommand

Patch release on top of `v5.1.0`, with **three commits** on top of the tag and
no merges (`git rev-list --count 1843b321..a0da90f5`): one new line at the end
of the installer, a change to the `--l18n` flag with two helpers that have no caller, and
the version bump with regenerated documentation. These notes were written
after the release shipped; the release was published with the notes generated by
GitHub.

---

### Read before upgrading: `--l18n` after a subcommand becomes an error (`cb047291`)

The `--l18n` flag lost `global = true`. The intent was for it to stop
appearing in the `--help` of every subcommand. But `global` is also what lets the
flag be *read* after a subcommand, so the change did more than
hide the flag. Measured on the published binary (`delonix 5.1.1`, commit `a0da90f5`):

| Invocation | Result |
|---|---|
| `delonix --l18n=pt volume --help` | help in Portuguese |
| `delonix volume --help --l18n=pt` | help in Portuguese |
| `DELONIX_L18N=pt delonix volume inspect x` | `erro[DX-4201] …` (in Portuguese) |
| `delonix --l18n=pt volume inspect x` | `erro[DX-4201] …` (in Portuguese) |
| `delonix volume inspect x --l18n=pt` | **rc=2**, `error: unexpected argument '--l18n' found` |
| `delonix volume ls --l18n=pt` | **rc=2**, the same error |

`--help` still works in any position, because the language is decided by
reading argv *before* clap processes it, and `--help` exits during
processing. What stops working is a normal command with the flag at the end.
This contradicts the flag's own help text, which says to use it with
`<command> --help`, and the manual's examples, which treat it as global.

**In v5.1.1, what always works** is putting the flag before the subcommand
(`delonix --l18n=pt …`) or using `DELONIX_L18N=pt`.

The fix is already on `main` (`d22e9336`, #862): the flag goes back to being
`global` and gets `hide = true`, meaning it is accepted everywhere and shows up in
no help text. It ships in the next release.

### The installer shows the release's address at the end (`54179fdb`)

When the install finishes without errors, `install.sh` now prints a
`downloads and documentation:` line with the address of the installed release.

**With a default install, the first address is broken.** Without
`--version`, the script's `VERSION` is `latest`, and the installer prints
`…/releases/tag/latest` (HTTP 404) and then `…/releases/latest` (which redirects
to the most recent release). With `--version v5.1.1` it prints only
`…/releases/tag/v5.1.1` (HTTP 200). Measured with `curl` on 2026-10-21. `main`
has the same line; the fix is left for another commit.

### Two template helpers, still with no caller (`cb047291`)

`build.rs` now reads the `tls=` key from `template.meta`, and `scaffold.rs`
gains `template_supports_tls` and `template_has_version`. In v5.1.1 nothing calls them
(`git grep` on the tag), which is why CI's `clippy -D warnings` fails the tag
with `dead_code` on both functions. On `main` they are now used to hide
`--tls-port`/`--hostname` and `-v`/`--template-version` from autocompletion for
templates that don't accept them. That also ships in the next release.

### Version and documentation (`a0da90f5`)

`Cargo.toml` moves to `5.1.1` and the `docs/commands/` pages are
regenerated from the binary, so the release workflow's documentation gate doesn't
fail on stale documentation.

### How this release was validated

It was poorly validated, and that's recorded here.

- The three commits were pushed directly to `main`, **with no PR**. `ci.yml`
  runs on push to `main` and **failed** at `54179fdb` and `cb047291`.
  At `a0da90f5`, the tag, it failed `rustfmt` (differences in
  `scaffold.rs`) and `clippy -D warnings` (`dead_code` in the two helpers
  above, and `type_complexity` in the generated `templates.rs`), and the other
  jobs, `test` included, were cancelled.
- Part of this already came from `v5.1.0`: CI for the v5.1.0 commit
  (`1843b321`) was also failing `rustfmt`, the generated documents, and two tests
  (`the_published_matrix_is_the_generated_one` and
  `no_string_in_the_sources_tells_the_operator_to_run_a_dead_command`).
- `release.yml` failed three times (08:57, 08:58, and 09:38 UTC on 2026-10-15)
  before publishing on the fourth attempt, at 10:05 UTC. The failed runs were not
  investigated for these notes. The run that published used the `release.yml` from `727c8d3d` (`main`
  at that time) and built the tag: the published binary says
  `commit: a0da90f50`.
- After publication, `--l18n`'s behaviour and the installer's addresses were measured
  against the published binary and against GitHub, as
  described above.
- **Not run**: the `scripts/e2e.sh` battery, the chaos harness, and `cargo test`
  against this tag.
