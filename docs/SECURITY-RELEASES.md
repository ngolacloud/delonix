# Release signing (minisign)

## The problem this solves

`install.sh` has always verified binaries against the release's `SHA256SUMS`. That
proves the **download was not corrupted** — it does not prove **who produced the
file**. The `SHA256SUMS` comes from the same URL as the binary, so whoever manages to
publish a tampered release (compromised GitHub account, stolen CI token, insider)
also publishes a matching `SHA256SUMS`. Verification passes, successfully, and
installs the backdoor.

A signature closes that: the private key is never in the release, and `install.sh`
ships the public one embedded. Forging now requires the private key, not just write
access to the release.

## Setup (one time)

**The private key is generated by you, on your own machine.** Do not generate it in
CI, do not ask an assistant for it, do not paste it anywhere except the repository
secret.

```bash
# 1. Generate the pair. Choose a strong password when prompted.
minisign -G -p delonix.pub -s delonix.key

# 2. Keep the PRIVATE one outside the repository (password manager / offline vault).
#    If you lose it, you cannot sign new releases — only generate a new key and
#    update install.sh, which breaks verification for whoever has the old one.

# 3. View the public one (2 lines: comment + base64):
cat delonix.pub
```

Then:

1. **`scripts/install.sh`** — replace `MINISIGN_PUBKEY="__TO_FILL_IN__"` with the
   **second line** of `delonix.pub` (base64 only, without the comment).
2. **Repository secrets** (Settings → Secrets and variables → Actions):
   - `MINISIGN_SECRET_KEY` — the ENTIRE content of `delonix.key`.
   - `MINISIGN_PASSWORD` — the password chosen in step 1.

The release workflow fails loudly if the secret is missing, instead of publishing an
unsigned release that every installer would refuse.

## How the installer behaves

| Situation | Behaviour |
|---|---|
| Valid signature | installs |
| Tampered `SHA256SUMS` | **aborts** — `SIGNATURE verification FAILED` |
| Signed by another key | **aborts** — key id does not match |
| Release without `.minisig` | **aborts**, mentioning `--insecure-skip-signature` in the message |
| `minisign` missing | tries to install via the package manager; if it fails, **aborts** |
| `MINISIGN_PUBKEY` unfilled | warns and proceeds (download integrity only) |

Fail-closed on every real failure path. Verification runs **before** any
`verify_asset` — without an authentic `SHA256SUMS`, the hashes it contains are
worthless.

## Verifying by hand

```bash
curl -fsSLO https://github.com/angolardevops/delonix-runtime/releases/latest/download/SHA256SUMS
curl -fsSLO https://github.com/angolardevops/delonix-runtime/releases/latest/download/SHA256SUMS.minisig
minisign -Vm SHA256SUMS -P '<the public key, from install.sh or the site>'
sha256sum -c SHA256SUMS --ignore-missing
```

## What this does NOT cover

- **`install.sh` itself.** Run via `curl … | bash`, it executes without
  verification — its authenticity depends on TLS and GitHub. To close that link,
  download it first, check it against the signed `SHA256SUMS` (`install.sh` is
  listed there) and only then run it.
- **A compromise of the build machine itself.** The signature proves the artefact
  came out of our pipeline, not that the pipeline was intact. **Since 2026-08-25
  there is SLSA provenance** (`actions/attest-build-provenance`, signed with an
  ephemeral OIDC identity of the runner via Sigstore — no private key to keep),
  which states from which commit and which workflow the binary came:

  ```bash
  gh attestation verify delonix-x86_64-linux --repo angolardevops/delonix-runtime
  ```

  The two signatures coexist on purpose and answer different questions: minisign
  proves the release is **ours** to whoever has the public key embedded in
  `install.sh`; provenance proves **where** it was built, to whoever does not trust
  us at the outset. It is still not reproducible builds — that is a different
  thing, and neither promises it.
- **`cloud-hypervisor-static` and `hypervisor-fw`**, installed from upstream over
  HTTPS only — upstream does not publish checksums in a convenient format. Known
  and recorded risk; see the comment in `install.sh`.

## Rotation

Rotating the key breaks verification for whoever has an old `install.sh` cached.
Publish the new public key on the site and in the release notes **before** using
it, and keep the old one documented. The workflow verifies, before publishing, that
the signature matches the public key embedded in `install.sh` — a swap forgotten
halfway fails in CI, not on users' machines.

## SBOM

Every release publishes **`delonix-sbom.spdx.json`** — SPDX 2.3, generated from
`Cargo.lock` by `scripts/sbom.py`. It is what answers «does this CVE affect me?»:
380 packages with name, version and the registry's checksum.

**It goes into `SHA256SUMS`, and therefore into the signature.** Publishing it
outside that would give an inventory anyone could replace — and a tampered SBOM is
worse than none, because it is trusted.

It comes out of a script of ours and not a `syft`/`cyclonedx`, for the same reason
provenance uses GitHub's own action: adding a third-party tool to the step that
exists to secure the supply chain increases the surface exactly where it matters.
`Cargo.lock` **is** the resolved tree; the script translates, it does not discover.

**What it does not cover, and is written in the document itself:** what is linked
from the system (libc, what `protoc` generates) and any claim of reproducibility.
