## v5.1.1 — the installer shows where the release is, and `--l18n` stops being accepted after a subcommand

Patch release on top of `v5.1.0`, with **three commits** on top of the tag and
no merges (`git rev-list --count 1843b321..a0da90f5`): one new line at the end
of the installer, a change to the `--l18n` flag with two helpers that have no caller, and
the version bump with regenerated documentation. These notes were written
after the release shipped; the release was published with the notes generated by
GitHub.

---

### Read before upgrading: `--l18n` after a subcommand becomes an error (`cb047291`)

The `--l18n` flag lost `global = true`. The intent was for it to stop
appearing in the `--help` of every subcommand. But `global` is also what lets the
flag be *read* after a subcommand, so the change did more than
hide the flag. Measured on the published binary (`delonix 5.1.1`, commit `a0da90f5`):

| Invocation | Result |
|---|---|
| `delonix --l18n=pt volume --help` | help in Portuguese |
| `delonix volume --help --l18n=pt` | help in Portuguese |
| `DELONIX_L18N=pt delonix volume inspect x` | `erro[DX-4201] …` (in Portuguese) |
| `delonix --l18n=pt volume inspect x` | `erro[DX-4201] …` (in Portuguese) |
| `delonix volume inspect x --l18n=pt` | **rc=2**, `error: unexpected argument '--l18n' found` |
| `delonix volume ls --l18n=pt` | **rc=2**, the same error |

`--help` still works in any position, because the language is decided by
reading argv *before* clap processes it, and `--help` exits during
processing. What stops working is a normal command with the flag at the end.
This contradicts the flag's own help text, which says to use it with
`<command> --help`, and the manual's examples, which treat it as global.

**In v5.1.1, what always works** is putting the flag before the subcommand
(`delonix --l18n=pt …`) or using `DELONIX_L18N=pt`.

The fix is already on `main` (`d22e9336`, #862): the flag goes back to being
`global` and gets `hide = true`, meaning it is accepted everywhere and shows up in
no help text. It ships in the next release.

### The installer shows the release's address at the end (`54179fdb`)

When the install finishes without errors, `install.sh` now prints a
`downloads and documentation:` line with the address of the installed release.

**With a default install, the first address is broken.** Without
`--version`, the script's `VERSION` is `latest`, and the installer prints
`…/releases/tag/latest` (HTTP 404) and then `…/releases/latest` (which redirects
to the most recent release). With `--version v5.1.1` it prints only
`…/releases/tag/v5.1.1` (HTTP 200). Measured with `curl` on 2026-10-21. `main`
has the same line; the fix is left for another commit.

### Two template helpers, still with no caller (`cb047291`)

`build.rs` now reads the `tls=` key from `template.meta`, and `scaffold.rs`
gains `template_supports_tls` and `template_has_version`. In v5.1.1 nothing calls them
(`git grep` on the tag), which is why CI's `clippy -D warnings` fails the tag
with `dead_code` on both functions. On `main` they are now used to hide
`--tls-port`/`--hostname` and `-v`/`--template-version` from autocompletion for
templates that don't accept them. That also ships in the next release.

### Version and documentation (`a0da90f5`)

`Cargo.toml` moves to `5.1.1` and the `docs/commands/` pages are
regenerated from the binary, so the release workflow's documentation gate doesn't
fail on stale documentation.

## v5.1.0 — what the engine cannot enforce it now refuses, and the projects it generates are born with a gate

Two hundred and eighty-nine commits since `v5.0.2` (197 not counting merges),
from `#723` to `#843` — measured at `a46095a3`
(`git rev-list --count v5.0.2..a46095a3`). The number travels with the commit it
was measured at: without that it ages silently as `main` grows.

**MINOR, and the reason is verifiable**: nothing in this release breaks a
contract that any version declared. The new refusals (there are many) all land
on requests the engine **could no longer fulfil** and reported as success, or
on surfaces that `docs/cli-stability.md` lists as «no promise declared in any
version» — `init` among them.

The thread is the same as the last two releases, now pushed into the places
where there was still a cheap yes: **what the engine cannot enforce, it
refuses; what it does not understand, it does not swallow; and what it has not
measured, it does not claim.** The novelty is that this has reached what the
engine **generates** — a project born from `delonix init` now comes with
tests, two CIs, Conventional Commits, SonarQube and a README that advises on
architecture, with a gate requiring it.

---

### Read before upgrading

None of these is a break of a declared contract, but the four change what a
command that returns `0` today does tomorrow.

- **The CRI now has a capabilities ceiling BY DEFAULT** (`#828`). Without
  configuration, the ceiling is the engine's `KEPT_CAPS` in `reject` mode: a
  normal pod runs as before, and `privileged: true` or a `capabilities.add`
  above that set are **refused on `CreateContainer`**. Absent or empty no
  longer means «no ceiling» — the only way out is to write it
  (`DELONIX_CRI_CAP_CEILING=all`), and an invalid value or mode stops the
  server from starting rather than falling back to «unlimited».
- **`delonix vm image <verb>` is the only path** (`#772`). `image vm …`,
  `image --vm …` and the flat forms `vm build|convert|pull|push|ls-remote` fail
  with `unrecognized subcommand`. A clean cut, no alias: the `vm` group is on
  the non-stable list.
- **`delonix init` refuses more than it used to** (`#842`, `#843`): a port
  this host cannot publish stops `--up` **before** the build; an
  `init -t <other>` over a directory that already has another project is a
  conflict (exit 5) instead of «nothing to do» followed by a build of the
  wrong project; and an unknown key in `template.meta` stops the engine's own
  build.
- **`cluster kubeadm` refuses the default CNI on a multi-node cluster**
  (`#810`), before creating a single VM. Previously it provisioned everything
  and the cluster was left with no network between nodes.

---

### A generated project is born with a gate (`#842`, `#843`)

It started with a production bug: `delonix init -t nginx --port 9000 --tls-port 943`
generated the project and `build` **always** died with `nginx: [emerg] bind()
to 0.0.0.0:943 failed (13: Permission denied)`, at the step that was only
supposed to check the configuration syntax.

Four measurements, and each one changed the fix:

1. the `build`'s working container runs in the HOST's netns (same inode),
   where the engine's userns does not have `CAP_NET_BIND_SERVICE`;
2. `nginx -t` **binds** every `listen` it reads — it is not a parser;
3. and it tolerates `EADDRINUSE`: **only `EACCES` is fatal**, so the obvious
   gate («occupy the port and build») would pass over the defective binary;
4. only nginx has the problem — `httpd -t` and `haproxy -c` built with the
   same ports without a single complaint.

The check now runs over a copy whose two `listen` directives are unix sockets.
The port itself was never actually unusable: inside the container's own netns
the same `listen 943` returns `rc=0`.

**The eleven templates were then generated with the adversarial port and
built: 11/11.** The sweep found another defect, which remains **open** and is
written down: `init -t go ./go` generates, with exit 0, a `go` module that Go
refuses, and `-t django ./django` a package that depends on itself.

And the templates' contract gained a gate. Before, `nginx`, `httpd`, `haproxy`
and `odoo` had **zero** CI, SonarQube and `CONTRIBUTING.md`; `nestjs` had lost
the `commitlint` the two siblings have; and none of the eleven had an
architecture section in the README. Now all of them do, two tests require it,
and `scripts/init-ci.sh` **runs** the generated CI of all eleven — the GitLab
job and the GitHub steps on the seven application ones, `ci-check.sh` on the
three edge ones (which builds the image and probes it **from the outside**,
the only way the smoke test itself is honest) and `pre-commit` on `odoo`.

Running that CI instead of reading it found three bugs in the generated
projects: the `smoke.sh` of the three edge ones **ignored** the URLs it
receives as an argument (`127.0.0.1` hardcoded, so it FAILs against any
correct server outside the loopback); a `haproxy` check required a
delonix-managed container and now **skips with the reason**; and the OCA's
`prettier` reformatted the files that `init` generates, failing `odoo`'s gate
on an untouched project.

## v5.0.2 — a route between networks now serves containers attached to more than one

Patch release on top of `v5.0.1`, cut from the same maintenance branch
(`release/5.0.x`) with **exactly one code commit** on top of the tag — the
`cherry-pick -x` of `delonix-runtime#733`. Commits that landed on `main` since
`v5.0.0` and bring new functionality stay out: they ship in the next MINOR.

---

### An open `NetworkRoute` did not pass traffic to a container attached via `network connect` (`9d0f5ec2`, #733)

A `NetworkRoute` is an `iifname A . oifname B` pair in the holder's `@netpair` map: it
serves a packet that ENTERS the holder through network A's bridge. A container attached to
network A with `network connect` (an additional network, not the primary one) kept
whatever route table it already had: a packet for network B left via the default
route, entered through the PRIMARY network's bridge, and never matched the pair. The route showed up
listed, the pair was installed, and nothing crossed it — measured on v4.5.0: 100 %
loss in both directions, with the routes open in both directions.

The holder now maintains, on every container with more than one network, a route to
the other network's prefix via this network's gateway, on the interface the container has
here, and the mirrored route on the other side, so the response comes back the way it
went (through the default route it would carry a source address that that
interface's anti-spoofing refuses).

- `route_plan::plan` computes it, pure and with unit tests: the default
  interface stays untouched, a directly connected destination is never routed through a
  gateway, a destination gets one route.
- `sync_workload_routes` executes it: on `netroute add`/`del` (all
  containers) and on `attach-extra`/`detach-extra` (that container). The routes carry
  their own protocol identifier, so only what the engine installed gets removed.

ADR-0013's composition rule still holds: a route in a container's table says where
a packet goes out; the pair still decides whether it gets forwarded. Measured with the
fix on `main`: A → B 0 % loss, B → A still 100 % (the route is directed),
both directions open 0 %/0 %, a container attached after the route already exists
0 %, and with the routes closed 100 % and nothing in either table. A
microVM's table belongs to the guest and is not covered.

## v5.0.1 — two failures that opened instead of closing: `--secret-files` and scan-based admission

Patch release on top of `v5.0.0`, cut from a maintenance branch
(`release/5.0.x`) with **exactly two code commits** on top of the tag — the
two `cherry-pick -x` from `main` — plus the `.github/actions/protoc` action, CI-only,
which the `main` branch's `release.yml` requires in the tag's tree. The other ~140 commits that landed on
`main` since `v5.0.0` **do not** come here: they bring new functionality, and functionality does not ship
in a PATCH. Whoever only needs the fix updates to this one; the rest ships in the
next MINOR.

The two failures are of the same family that this engine chases everywhere:
an error path that, instead of refusing, carried on and made the result
look good.

---

### `--secret-files` stopped closing when the tmpfs failed to mount (`3626ae70`)

Each step of `write_secret_files` — the `create_dir_all`, the two
`mount(2)` calls for the tmpfs on `/run/secrets`, and each file write — had its error
discarded. If the tmpfs failed to mount (a flag refused by a kernel, a
`/run/secrets` already occupied, a userns more restricted than expected), the cycle
kept writing **directly to whatever `/run/secrets` existed**, i.e. to the
container's persistent layer. Hence the secret survives a `container commit`
into a published image and any backup or snapshot of the container — the
exact exposure that `--secret-files` exists to avoid relative to environment
variables.

Now the mount and the write are two functions that propagate the error, and the container's
init **aborts** (exit 126, the same pattern as `setup_rootfs`) instead of
starting a container whose secrets may be on disk. A container that does not
start leaks nothing; one that silently wrote the secret to the persistent layer has
already leaked it.

**What is proven and what is not**: the write half (`write_secret_values`)
has its own unit test against a temporary folder; the mount's error propagation is
enforced by the compiler (`?`), not by a simulated `mount(2)`. The mount
failure itself **was not reproduced live**.

### Scan-based admission stopped blocking when the scan itself failed (`f59c9f8a`, #778)

With `DELONIX_SCAN_ON_PULL=<severity>`, `admission_scan_on_pull` treated
**any** scanner error as "this image has no package manager I can read" (DX-1401, the
legitimate case of a `scratch` image): it warned and let the pull through. A truncated
`advisories.json` (`scan --update` wrote it without atomicity, and an interrupted write left it
truncated) or an unreadable layer blob followed the same path. A gate documented as *fail-closed* ended
up doing nothing the moment its own database broke, with a
warning on stderr as the only signal.

Now only DX-1401 lets the pull through — the distinction is made by the dictionary
number, not by the message text. Any other scan failure **refuses the pull and removes
the image**. And the "Image removed" message is no longer said unconditionally:
it says whether the removal actually succeeded.

Measured live on `main`, with an isolated `DELONIX_ROOT`: a `scratch` image
(`hello-world`) warns and gets in (rc 0, unchanged); a real vulnerability
(`alpine:3.19`, busybox < 1.37.0) is refused (rc 1, unchanged);
a hand-corrupted `advisories.json` is now **refused and removed** (rc 1) — previously
it got in with rc 0.

## v5.0.0 — the image's `USER` is who runs, the typed `provider` block, and the node contract now served

Two hundred and two commits since `v4.5.0` (162 not counting merges), from `#572` to
`#720` — measured at `831b9601`, the tip after the second `main` merge of
2026-10-08 (`git rev-list --count v4.5.0..831b9601`).

The number now goes together with the commit at which it was measured, because without that
it ages silently: the "180 (152)" of this note were correct at `ea38d89b`, where they were
counted, and stopped matching the branch as soon as it grew. Pinning it to a
sha makes it verifiable instead of a claim about "the tip".

**Numbered as MAJOR for one reason only, and it is in the next section**: a container
now runs as the user the image declares. Everything else in this release
is additive, or is a refusal to replace a success the engine could not
prove — but that change breaks the `container run` contract, and a broken
contract does not ship in a MINOR.

The thread running through this release is the same as the last few, carried onto the
declarative surface: **what the engine cannot prove is not reported as a success, and what it
does not understand is not swallowed in silence**. In this release that reaches manifests (an
unknown field rejects the whole document), isolation (a namespace the host
would not enforce is refused rather than applied), limits (`--device-*` with no disk
that accepts them) and lifecycle (an `rm -f` that gave up is not resurrected by the
supervisor).

---

### Contract break — read before upgrading

**A container runs as the image's `USER`** (ADR-0062, `#632`, `#633`, `#637`,
`#638`, `#639`). Up to v4.5.0, `container run` ignored the `USER` the image
declared and the process ran as uid 0 — since v1.0.0, with no error or warning.
Measured with `haproxy:3.4-alpine`, which declares `USER haproxy`: `id` inside the
container answered `uid=0`.

What changes, and what to do about it:

- **Without `--user`, the process runs as the image's `USER`.** A service that
  depended on being root without asking for it stops being so. To keep it, `--user 0`.
- **On a rootless host with no subuid range, only one uid fits**: it stays at 0 and the
  `run` says so out loud, instead of failing.
- **`--user` no longer hands the whole filesystem to the user.**
  The old sweep (`chown_tree_once("/")`) gave it 940 of the 986 entries of a
  15 MB image — including `/etc/passwd` and the service's own binary — and
  crossed mounts, re-owning a HOST bind mount (a file owned `1000:1000`
  ended up owned by a subuid, and the owner could no longer write to their
  own file). Now the container receives **what the image gives it**: an ownership
  index recorded when extracting the layer, applied once by the init, never on another
  filesystem. Measured afterwards, on the same image: 2 user-owned entries
  instead of 940, a 56 K write layer instead of 13 MB, and the host bind
  untouched. On `odoo:20.0` (~2 GB), the first boot with `-u odoo` went
  from "still sweeping at 16 minutes" to **1.7 s**.
- **An EMPTY named volume** gets the owner the image assigns to the mount point,
  or the container's user when the image names nobody. A volume with
  data and a bind mount are **never touched** — a filestore written as root by
  a previous run is not migrated.
- **`build` follows the same rule**: a `RUN` runs as the `USER` in effect at that
  step (previously it always ran as root, even after a `USER app`), and the layer
  cache preserves ownership — a cached rebuild used to lose it.

**Two public signatures of `delonix-sdn` changed** (`#718`):
`can_bind_host_port` and `host_port_busy` now take a `Proto`. Consumers of the
crate via `git` + tag are not broken today, but bumping that pin requires a
pass. The old signature couldn't stay, because it **was** the trap: the two
probes always opened a `TcpListener`, whatever the spec, so a UDP publish
was checked against TCP — blind by construction, with the conflict showing
up only inside slirp as opaque JSON. The enum forces every call site
to state the transport, and refuses at that boundary the `sctp` the CRI can
emit instead of probing it as TCP.

Side effect of the same pass: extraction now preserves **setuid, setgid
and sticky**. Every container's `/tmp` used to be `777` instead of `1777`, and a `su`
setuid lost the bit. A layer extracted by an earlier engine is fixed up from
the blob headers the first time an image uses it.

### Behaviour changes

**The bind address of a published port is now RECORDED** (`#718`). It was
in-memory state at publish time and never persisted: the record stored the spec as
written (`51072:80`) and `DELONIX_PUBLISH_ADDR` was re-read from the environment on every
`start`. Fifth occurrence of the trap "state needed to REBUILD the
resource must be persisted". Measured both ways, against the bind read from
the kernel:

- published with `DELONIX_PUBLISH_ADDR=0.0.0.0`, it came back on **`127.0.0.1`** after
  a `start` — which is what a `net boot enable` unit runs, with no environment
  at all. Service down, listing saying published;
- and the OPPOSITE, which is what matters for security: a port published on purpose
  **without** an address (loopback only) came back on **`0.0.0.0`**,
  exposed to the whole LAN, because the shell that ran `start` had the
  variable exported.

In both cases rc=0, no warning, with `net ingress ls` printing the same line
before and after — `51070:80` and `51072:80` were identical bytes on disk with
opposite reach. Now the stored spec is always `addr:hostPort:contPort/proto`, and
`container ls` shows the address (`0.0.0.0:55070->5070/udp`) in the column read
precisely to decide what is exposed. A spec **without** an address now
means "record predating this version".

New refusals. In all of these cases the engine **used to accept and not honour**.

**A `hostPort` the node does not publish (ADR-0074, `#720`)** — and the refusal is **per
path**, because the paths differ and measuring them is what showed it: the
`slirp4netns` refuses SCTP in `add_hostfwd` (`bad arguments.proto`), the CNI
`portmap` publishes it end to end, and `hostNetwork` publishes nothing (the container
is in the host's REAL netns and binds the ports itself). A blind response would have
closed a port that is actually open in root mode. The refusal comes from
`RunPodSandbox`, before the sandbox exists, as `failed_precondition` — which the
kubelet shows as a pod event rather than a `StartContainer` retried
forever. A `containerPort` without `hostPort` is still dropped, which is the way
an SCTP **Service** works: no SCTP service is affected.

**Manifests (ADR-0069, `#682`, `#687`)**

- **A field the engine doesn't understand rejects the manifest, before any
  effect** — including inside the items of a Pod's `spec.containers[]`, where
  probes and `lifecycle` don't exist and used to disappear silently there too.
  `stack validate` still REPORTS instead of refusing, and
  `DELONIX_MANIFEST_LENIENT=1` is the explicit escape valve.
- **A field a Kind refuses BY NAME keeps its own code.** The
  `unprivileged: false` of a `SystemContainer` used to answer `DX-1000 unknown field —
  check the spelling` for a correctly spelled field; it now answers `DX-1540`, which says
  what the field is.
- **The same Pod name in a different namespace is a conflict**, not "already exists"; and
  `Container` and `Service` are now identified by `(namespace, name)` —
  two namesakes in different namespaces are no longer one resource in the plan.
- **An unreadable store is an error, not an empty machine** (VM, volumes, container
  presence). A `plan` that reads zero because it couldn't read used to propose recreating
  everything from scratch.

**Isolation and networking**

- **A named namespace on a host that doesn't filter bridge traffic is refused**
  (`DX-6305`, exit 69, decision D5 of the maturity plan, `#664`). Without
  `br_netfilter` the chains are installed, the sets are filled, every
  command reports success — and the boundary doesn't exist. It is the most expensive
  kind of silent failure this engine can have, because what fails is a
  security property that reads as enforced. Escape valve:
  `DELONIX_ALLOW_UNENFORCED_ISOLATION=1`.
- **Anti-spoofing moved to a `bridge` table, where it actually cuts**
  (`#671`). The old rule (`ip … iifname <veth> ip saddr != <ip> drop`) had its
  counter at zero: between two ports of the same bridge, the `iifname` the IP
  layer sees is the BRIDGE, never the port. Measured: a container with `NET_ADMIN`
  spoofed the source and reached its neighbour (3/3), and spoofing the address of a member
  of another namespace broke through isolation. It now pins by port the MAC, the IPv4
  source, and the ARP sender. **A lesson that stays: a security rule is only proven
  once a spoofed packet is counted being dropped** — the audit that "closed"
  this read the ruleset and saw the rule there.
- **Grants belong to the administrator, not to the request** (`#672`):
  `--allow-source <cidr>` and `--no-source-check` exist for a container that
  forwards, but they are PERMISSIONS in node policy. Without a policy, nothing is granted,
  and `mode: warn` does not grant.

**Lifecycle**

- **A `--wait` that times out exits with 124 (`DX-8503`) and leaves the VM running**
  (decision D6, `#661`). It used to return 0: a `--wait` that never saw the VM respond
  reported success.
- **`--device-read-bps`/`--device-write-bps` are refused when there is no disk
  that accepts them** (`#663`). `io.max` now names the disk the container's
  rootfs lives on; before, the limit was written and not applied.
- **An `rm -f` that gave up is not resurrected by the supervisor** (`#647`). With the
  disk full, `rm -f` returned `DX-8101` and kept the record as the rule
  demands — and when the process finally exited, the `--restart always`
  supervisor restarted it. The removal intent is now recorded BEFORE the signal.
- **A `stop` that gave up keeps the process recorded**, and a `start` that fails
  after an `rm -f` takes its directory with it (`#604`, `#607`).
- **A container's `slirp4netns` dies with it** (`#646`, `#648`, `#651`). It used to be
  spawned mid-boot and inherit the caller's descriptors, so it stayed
  alive holding the published port after the container exited — and the next
  `start` hung forever waiting for an EOF only that slirp could give.
  Measured: over an hour of survival with the disk full.

**Declarative surface**

- **The `provider` block is `type` + `spec`** (ADR-0070, ADR-0071). What only a
  manufacturer understands lives **inline** in the resource, typed by provider AND by
  resource: a key the `type` doesn't know is refused. `backend:` became
  `provider.type` on a `VirtualMachine`, and the `libvirt:` group and flat fields
  normalize to the same thing. **The earlier spellings still load and still
  mean the same thing**, reported as superseded; repeating a field in both
  places is refused.
- **`kind: NetworkZone` became `kind: Network` with `spec.provider.proxmox`.**
  Networks naming the same zone merge on load into the single document the
  reconciler already reconciles — the zone is created with the first vnet and removed
  with the last, with no reference counting. The old name still loads, flagged
  as superseded.
- **A workload governed by policy is born CLOSED** (ADR-0069 D6, `#685`,
  `#686`). A container or Pod named by a `NetworkPolicy`, `NetworkAccessRule`, or
  manifest `Dependency` is created with the default-deny chain installed
  before the process, and is only opened to what the policies say once they are
  in place. If one layer fails, the workload stays closed and `apply` says so.

### What's new

**`hostPort` is now published in root/CNI mode** (ADR-0074 D3, `#720`). It wasn't, for
ANY protocol: mappings were stored and then dropped, and the pod came
up `Running` with a port that didn't respond — silence, rc=0. The
`portMappings` now pass through as the plugin's `runtimeConfig`, the way containerd
does, and that delivers tcp, udp, **and** sctp at once. The capability
argument is injected into the conflist, and that is what spares new plumbing on either
CNI path: root hands the list to `attach_named_netns`, rootless hex-encodes the SAME
JSON over the holder's control line (whose shape doesn't change, so an old
holder still works), and storing the result as the sandbox's conflist
returns the identical configuration to `DEL`. The declaration is read from
the plugin's own `capabilities.portMappings`, never from a list of names; a
chain that doesn't declare it is refused the right to name `portmap`. Measured on a
VM from this repo's golden with `crictl`, against both binaries: before **0**
DNAT rules and no response on the port, after **3** rules, response on the
host port, and **0** rules after `rmp`.

And `hostIP` now travels this same path: dropping it would publish on all
interfaces a port the pod asked for on just one — exposure widened silently, the
same defect `#718` fixed from the other end.

**System containers on Proxmox — `kind: SystemContainer`** (ADR-0058, plan
63, `#579`, `#582`, `#583`, `#588`, `#590`–`#594`)

A Proxmox LXC doesn't fit `kind: Container` — the node API has no `exec`, logs,
or exit code, and the engine's dataplane doesn't reach there. It comes in as its own
resource, with semantics close to a VM: the engine pulls the image and writes the
OCI archive the node accepts, the node runs the container, and a hand edit on the node is
**drift** (`plan` returns 2 and `drift` shows it). `memory`, `swap`, and `cores` are
hot; `rootfs` only grows (shrinking plans a `Replace`). Full Day 2: snapshots (with a
`restore` that waits for the node to respond again — measured, ~40 s
during which pveproxy returns 596 to anyone waiting), backup to the node's storage,
clone, firewall via `kind: NetworkPolicy` with `scope: systemcontainer`, and
migration between nodes (offline, because the node aborts a `restart=1` when the init
ignores SIGTERM and leaves the container at the origin while `pvesh` exits 0). `exec`,
logs, and exit code are `unsupported-by-provider` with the reason written out.

**The node contract is now served** (ADR-0042, `#659`, `#662`, `#669`,
`#670`, `#673`, `#674`, `#680`, `#681`)

Until now `proto/delonix/node/v1` was a contract with not a single Rust producer.
Now there is `delonix serve node-api`: **gRPC and HTTP/JSON from the same `.proto`**, on
a local unix socket, own uid only.

- `NodeService`: `GetApiRoot` (`GET /v1`, with `links` to everything served),
  `GetNodeInfo`, `GetHealth`, `GetCapacity`, `ListProviders`.
- `NetworkService`: the reads (`ETag`/`If-None-Match` with 304, `label_selector`,
  pagination with `Link rel=next`) and the first two mutations, `CreateNetwork` and
  `DeleteNetwork`.
- `VolumeService`: `GetVolume` and `ListVolumes`. `Get` measures usage; `List` does
  not measure, and says so — scanning the data of every volume on each listing is a
  cost already measured on the dashboard. Unknown is never zero.
- `OperationService`: **every mutation responds with an `Operation` persisted before
  the work**. An unfinished record whose owner no longer exists is terminated
  `FAILED` with reason `Interrupted` — the server is socket-activated and has nobody
  to do it for it. `Idempotency-Key` is the `request_id` and `If-Match` the `etag`.
- **REST errors are RFC 9457 documents** (`application/problem+json`),
  built from the engine's code dictionary, and the published OpenAPI declares it.
- **REST routes are GENERATED** from the `google.api.http` annotations in `build.rs`: a
  contract route not yet served answers 501 (`DX-6001`), a path outside the
  contract 404.
- `GET /openapi.json`, and the `GET /docs` (Swagger UI) and `GET /redoc` pages,
  served from files embedded in the binary — byte-identical to the npm
  packages, checked against their `SHA256SUMS` at build time, under a CSP that only allows
  the socket (measured in a browser: the logo ReDoc fetches from a CDN is blocked before
  any request leaves).

**Role-based network providers** (ADR-0059 F2–F5, `#614`–`#636`, `#654`, `#656`)

The network contract is now organized by ROLE, with its own context
(`delonix-networking`): `GatewayProvider` and `SegmentProvider`, chosen by
name in `providers.yaml`. On top of this:

- **A typed policy IR** with a reference evaluator: the firewall record
  either parses against it or is refused whole, and the holder's chain, a VM's
  firewall, and a gateway's perimeter filter are three **descents from the same IR**.
- **A network plan observes the device and names drift**, has a **digest**
  (`--plan-digest` refuses a stale plan with `DX-5390`), and a **steps log**
  that resumes an apply killed midway.
- **New roles on `NetworkGateway` and on the segment**: `nat:` (SNAT and 1:1),
  `ipam:` (subnets, DHCP, reservations), and `dns:` (records written by the node).
- **A failure states which provider, role, and step it came from** — and remote
  clients no longer echo the credential back inside it (a real leak, closed with a test
  that greps for both).

**Storage pools** (ADR-0067 P0, `#689`)

`kind: StoragePool` and the `delonix-storage` context, with the `dir` driver. The
administrator declares pools in an allowlist (`/etc/delonix/storage-pools.yaml`);
a manifest only NAMES a pool, and `driver`/`path`/`device` in a manifest are
refused by name. Ownership is by marker, never by name: a directory with data
and no marker is never adopted. Above 95% occupancy nothing is allocated (`DX-5202`).
The engine **never creates or destroys** a pool.

**`delonix init`** (ADR-0061, `#625`, `#631`, `#640`–`#645`, `#649`, `#653`)

- The seven application templates generate **a small, complete service**: a
  transport-to-port capability, configuration validated at boot, readiness
  `starting → ready → draining`, bounded shutdown, webhooks in both
  directions, OpenTelemetry, an OpenAPI contract with a drift test, and a
  dependency-direction test. The generator **checks what it replaces**.
- **The three edge templates are born with HTTPS** (certificate generated by `init`,
  `mkcert`, or self-signed), sized for load, with JSON logging and
  `request_id`. `scripts/tls.sh` renews, installs a certificate of your own, or runs
  Let's Encrypt via **HTTP-01 or DNS-01** — both proven against Let's Encrypt's
  real production.
- **Every template ships an opt-in tunnel to the internet** (`delonix-tunnel.yaml`),
  for anyone without a public IP.
- `--port`, `--tls-port`, and `--hostname` answer on the command line what
  `init` asks in a terminal; a second `--up` on a project already standing
  converges it and deploys what was rebuilt.
- The `odoo` template boots again (Odoo 20 by default) and runs as `odoo`; the
  `python` one is now called `fastapi`, with the old name as a silent alias.

**Versioned secrets** (ADR-0069 item 6, `#696`, `#700`)

A `Secret` now carries a **version** the store assigns (1 at creation, +1 when
values change), and `secret apply` reports `created`/`unchanged`/`rotated to version
N (changed: KEYS)` — **by key name, never by value**. `stack plan`
converges a Secret that carries its own values, comparing key names and a
**keyed** fingerprint (never a value; the node's master key is in it, and
a node without the key plans a `Create` and creates nothing). A container records the
version of each `--secret` it booted with, and `describe` says when it was rotated
since.

**FreePBX appliance** (`#657`, `#693`): FreePBX 17 + Asterisk 22 on Debian 12,
with secrets per clone on first boot, proven end to end (27/27 in both
modes).

### Consolidation and what measurement found (2026-10-06)

The last pass before this release consolidated the work of five parallel
sessions into a single plan (`docs/discovery/66_CONTINUITY_PLAN.md`) and ran the
measurements it requires. What that produced, besides the numbers in the next
section:

**A store opened on one root stopped writing on another** (`#719`), and the
obvious hypothesis was wrong. `tmp_roots_gate.py` was failing on `main` at random —
`cargo test -p delonix-sdn` left 3, 0, and 1 leftovers across three identical
runs. The natural reading was "the `TempDir`'s `Drop` swallows the removal error", and a
`TempDir::close()` with the error visible would have **passed without catching anything**:
followed with `strace` across the six parallel test binaries, the removal did work and
the directory **came back** afterward, put there by ANOTHER test. It wasn't a
cleanup that failed; it was a store writing to a root that wasn't its own.

- **A guest governed by policy is born closed, or is not born** (ADR-0069
  D6, `#705`). D6 closed containers and Pods; a VM and a system container
  were left out, and the reason was real — their firewall belongs to the provider, not to
  the holder. It is now created with its own firewall in effect, default-deny in both
  directions, **before the guest has CPU**, and a backend that can't do this
  (`VmBackend::holds_at_boot`) **refuses by name** (DX-1501) instead of creating the
  guest open. Only Proxmox has it today; both local backends refuse, and the
  refusal says where `scope: vm` applies.
- **The same VM name in a different namespace is a conflict, not "ensured"** (`#706`).
  The record is `vms/<name>.json`, regardless of namespace, so the name is
  unique on the node — and a manifest requesting the same name in a different namespace used to get
  `stack plan` = "1 unchanged" and `stack apply` = "ensured" with rc 0, **with the VM
  staying in the first namespace**. On a VM the namespace IS the isolation
  boundary, so the tenant requesting the second one ended up with a VM the first one could reach
  and theirs couldn't. It now refuses (class 5) before resolving or creating anything.
- **Two battery preconditions that made an ENVIRONMENT failure read as
  thirteen engine failures** (`#703`): a second image pull with its output
  discarded, and fixed idempotency keys on the node API.
- **A test that asked the hex digit itself** (`#702`): the check that a secret's
  fingerprint doesn't leak the value used `"bc"`, which IS hex —
  21 failures in 300 runs, measured.
- **Nine ADRs accepted** (0020, 0040, 0041, 0049, 0055, 0061, 0063, 0064, 0067) and
  **two new ones** (0072, 0073) closing the last two rows of the
  ADR-0070 table through measurement rather than motion. Accepting 0040 unblocked
  M01's `capability discovery`.
- **Two new gates over the registry itself** (`#707`, `#708`): an ADR cannot
  contradict itself about its own status, and the index cannot disagree with the document —
  seven lines disagreed, two of them for twelve days.
- **A policy written by pod name is read by the same name** (ADR-0069
  pending item 1, `#713`). Mutations had already accepted the pod name since `#705`;
  READS had not. `net ingress ls <pod>` and `describe networkpolicies <pod>/<dir>`
  used to answer `no such container` about a policy the engine had just
  accepted under that name, and `get networkpolicies` named the MEMBER where the
  operator had written the POD — on a two-member pod, four lines, and the two
  for the member with no firewall saying "allow (default), 0 rules" on top of a policy
  that exists. Measured live against `main`: the write passes, the three reads
  fail. **And generic DELETE wasn't deleting**: with a `deny` in effect,
  `delete networkpolicies <c>/ingress` returned rc 0 and "removed 0 inbound
  rule(s)", reads still showed `deny`, and traffic stayed
  blocked. This closes the last "STILL TO DO" of ADR-0069's pending item 1.
- **A field the workspace already declares is no longer hand-written** (`#711`, `#712`).
  `inline_versions` only looked at DEPENDENCY versions, so the crate's own
  `[package]` metadata had no guard — and that's how `delonix-mgmt`'s
  manifest said `version = "0.1.0"` for two and a half months
  while the workspace moved toward 4.5.0. The four copied fields now go
  through the workspace, and a new gate rejects the fifth.

## v4.5.0 — network that fails closed, Proxmox measured route by route, providers in one file per node

One hundred and three commits since `v4.4.0` (110 counting merges), from `#474` to `#576`.
Numbered as MINOR: there are new verbs (`vm resize`, `vm cloud-init`,
`vm move`, `provider ls|describe|matrix|config`, `net netns gc`,
`serve node-api`), new Kinds (`NetworkGateway`, `NetworkZone`), a new
configuration file (`providers.yaml`), and a new MCP tool
(`workload.usage`). No surface was removed. **Several changes deliberately alter
behaviour that already existed**: a limit, a rule, or a removal that used to pass
with a warning or silently now gets rejected. They are all together in the first
section, before the new features.

The thread running through this release is the usual one, taken further: **a
result the engine cannot prove does not get reported as a success**. This holds
for an invalid firewall rule, for an `rm -f` whose process has not yet died, for a
Proxmox task that "finished OK" without applying anything, and for a `push` that
died without saying why.

### Behaviour changes

Anyone upgrading should read this section first.

**Container networking (network audit, sessions S1–S4, #554, #560, #553, #555, #552)**

- **The per-container firewall fails closed.** A spec with an invalid rule is
  rejected whole (before, the rule was skipped and the rest applied). An unknown
  `dir`, `action`, or policy outside the documented values is also rejected:
  before, an unknown `dir` was read as `in` and an unknown policy as `allow`.
- **A namespace isolation failure is an error, not a warning**, in
  `container run`, `start`, and `pod create`. The attach is undone. Before, `run`
  exited with rc=0 and the container remained reachable from another namespace.
- **The source's egress is always evaluated.** Before, an `accept` in the
  destination's chain ended the evaluation, and the source's `egress deny`
  policy never ran (measured: A→B passed 3/3 with A's egress set to `deny`). Now
  there are two base chains, `fwout` and `fwcont`.
- **Explicit ingress rules no longer switch off isolation** (#560). A
  container with, for example, `ingress deny tcp/22` ended up accepting new
  connections from any other namespace on every other port. There is now a
  guardrail that no ingress rule removes; an explicit `allow` still opens the
  pair it names. **A container with explicit ingress rules no longer accepts
  new connections from other namespaces on ports no rule opens.**
- **Removing the last rule (`ingress rm`/`clear`) outside the `default`
  namespace keeps the chain**, which is also the isolation. Before, the container
  was left open to other namespaces.
- **Networks with a CIDR outside 10.200–254 now get a firewall and isolation.**
  Before, they had no chain and were outside the workload set: measured on
  `172.30.5.0/24`, two namespaces talked 2/2 in both directions.
- **`network connect`/`disconnect` fail when the firewall fails**, instead of
  warning and exiting with 0.
- **`network rm` refuses a network with anything connected** (**DX-5307**, exit 5)
  and names the containers, pod members, and VMs. Before it exited with rc=0 and
  left the container "Up" on a deleted bridge. `stack --replace/destroy`
  keeps its explicit path.
- **Transactional IPAM** (#553): reserving an IP that already belongs to another
  owner is rejected (**DX-5308**, before it was recorded with a warning); `stop`
  keeps the lease, and `start` returns to the same address; `rm` also frees the
  leases of the extra networks. `--subnet 10.200.0.0/16` (the ingress space) and
  `10.0.2.0/24` are now rejected.
- **The VM DHCP pool lives inside the network.** On a network that is not a
  `/16`, DHCP served the wrong network (on a `/24` it offered a `/16` address
  with a different router, and the VM ended up with no IP). The pool now sits at
  the top of the network, with `min(240, size/8)` addresses; on a `/16` it stays
  `.254.10–.249` byte for byte, so no existing VM changes IP. Consequence: a
  `/28` now has 11 addresses for containers and 2 for the VM pool.
- **The network holder validates every control token before running a command**
  (S4, #552): a token that goes into an argv cannot start with `-`, IPs and
  gateways must be strict IPv4, `rate`/`burst` only digits, and a CNI plugin's
  `type` must be a plain name (before, `"type": "/tmp/x"` would execute
  that binary on the holder). The lines a legitimate client sends do not change.
- **`vm bridge` validates subnets**: neither `default`, nor `/0`, nor a subnet
  overlapping the SDN, and root is checked before any command.

**Management API (`delonix-mgmt`)**

- **The seven network mutations that wrote the dataplane without going through
  the registry respond `501` with `DX-6302`** (#555): firewall, egress, `attach`,
  and `attach-extra`. The reads and `publish`, which does write the registry,
  continue to work. It was an explicit decision: reject all of them, rather than
  broaden them.

**Containers and cgroups**

- **`--cpuset`, `--io-weight`, and `--device-read/write-bps/iops` are rejected
  (exit 69) when the container's cgroup lacks the controller** (#545). Before,
  `--device-write-bps 5mb` would write at 1.6 GB/s and exit with 0, with only a
  warning. The `DELONIX_ALLOW_UNENFORCED_LIMITS` escape hatch still applies. It
  reaches every entry point (CLI, manifest, compose, Docker API, CRI); the CRI
  now receives exit 69 for a `cpuset_cpus` with no `cpuset`, as it already did
  for CPU and memory. As root, `delonix.slice` now delegates `cpuset` too, which
  was previously silently ignored.
- **`sudo delonix system setup --delegate` always writes the drop-in** (#550).
  Before, the write was only reachable on a branch a root process never takes,
  so it almost never wrote. Under `sudo`, the report is now about the
  user who ran `sudo`, and the next step names
  `systemctl restart user@<uid>.service`: a `daemon-reload` alone is a false
  positive.
- **`container rm -f` only returns once the process has died** (#562). Before it
  returned on the signal: with the disk under load, `delete pod --force` returned
  in 0.76 s with the members still alive in D state. It now waits for the real
  exit, with the same 30 s limit as `stop`. Past that limit, it **keeps the
  registry entry** and returns **DX-8101** `container.still_exiting` (exit 124); a
  repeated `rm -f` removes it once the process dies.
- **An `--rm` container is mounted with the `volatile` overlay** (ADR-0056, #537).
  Exit no longer waits for the host filesystem's writeback.
  Measured with 1 GB dirty on another file on the disk: `run --rm … alpine true`
  in 0.16 s, against 9.5–14 s for a kept container. Kept, pod, and CRI
  containers do not change.

**Providers and VMs**

- **A `defaultProvider` the process cannot serve fails with 69**, naming the
  provider (ADR-0054, #514). Before it was discarded, and the next `vm create`
  could create the VM on a local hypervisor. An unreadable `providers.yaml`
  makes VM requests without `--backend` fail; commands that do not choose a
  provider continue to work.
- **A `providers.yaml` with `type: opnsense` now registers the appliance**
  (#556). Registering does not contact anything.
- **Proxmox: a `network` named after an engine network is rejected** (#478). Before
  it was accepted and discarded: the registry said `Network: lab-net` and the VM
  ended up on `vmbr0`.
- **Proxmox: a task that finishes with `WARNINGS: <n>` is a success** (#546), and the
  `WARN:` lines go into the task log. Before it was read as a failure, and the
  action could be resent on top of a live resource.
- **Proxmox: an SDN apply waits for each node's network reload** (#571). PVE's
  `reloadnetworkall` finishes `OK` as soon as the reloads *start*; a reload that
  fails, or that does not show up within the timeout, now rejects the apply with
  **DX-6512**.
- **`vm create --require` with a cloud image actually filters** (#539). Before,
  libvirt was requested by name and the filter never ran.

**Other**

- **The binary no longer dies from SIGPIPE on a write to a socket** (#573). An
  EPIPE on a network connection now becomes a returned error (with retry, in push).
  A closed stdout or stderr (`image ls | head`) still terminates the process
  via SIGPIPE, as before.
- **`net netns down` rejects a root that does not exist**, instead of recreating it.
- **`kind: App` no longer deletes the CNB layer cache after every build**
  (#529), as ADR-0035 already said it should.

### Networking: what else went into sessions S1–S6

The network audit (`docs/discovery/62_NAAS_FASE0_AUDITORIA.md`, #544)
inventoried the engine's networking, found five resources with two writers and
seven fail-open findings, and split the fix across sessions. The behaviour
changes are above; the rest is this:

- **Dispatch migration with no manual step** (#560). A holder created by an
  earlier binary has the old, single-chain dispatch. The host now migrates it in
  `ensure_up` and in `apply_firewall_all` (`nsenter` into the pin's userns and
  netns, `nft -f`, one atomic and idempotent transaction), once per pin. If the
  migration fails, it is an error with the remedy.
- **`network rm` leaves nothing behind on the holder** (#555). It removes the
  `@netpair` keys, the `@dlxbr` member, the egress rules and the FQDN set, and
  the DHCP thread stops. Before, a network recreated under the same name was
  born with no DHCP and with the previous one's `deny`. A `publish` that fails
  partway undoes only the ports it published; a network created by a VM now
  shows up in `network ls`; `httproute` writes under a lock and atomically.
- **A single `/16` allocator** (#553), under a lock, that sees the registry
  entries and the NetDefs in any form. Before there were two, which ignored
  each other. NetDef writes lock and are atomic: 60 concurrent egress writes
  with gateway changes used to leave **0** survivors.
- **Ownership by mark, not by name, on remote providers** (S6, #558). An
  OPNsense alias or rule and a Proxmox SDN vnet belonged to the engine if they
  had the right name, so a hand-made rule with the same description was
  adopted and then deleted. Now:
  - on OPNsense, the mark is a firewall category `delonix-owner:<token>`.
    An object found without it is rejected (**DX-5340**); one of ours edited on
    the appliance, **DX-5341**; a commit with changes staged by someone else,
    **DX-5342**;
  - on Proxmox, the mark goes in the vnet's `alias`. A zone has no text field,
    so it is only the engine's when the registry says the engine created it. The
    commit goes through a transaction under the SDN's global lock, and pending
    changes from someone else reject it (**DX-5516**);
  - a registry entry predating the mark does not prove ownership: teardown does
    not touch the remote side and names what it left behind.
- **`vm unbridge` undoes what `vm bridge` applied** (#559). `bridge --apply`
  writes the subnets to `<state>/ingress/vmbridge-<bridge>.subnets`, before
  running the plan, and `unbridge` removes the rules and the route for those
  subnets. Before, a bridge made with `--vm-subnet` left both `FORWARD …
  ACCEPT` rules and the return route after teardown. `unbridge` gains
  `--vm-subnet` (repeatable).
- **ADR-0059 (accepted, #547)**: network providers by role (segment, gateway, and
  later NAT, IPAM, DNS), chosen by name and negotiated through the capability
  catalogue, with the validate → plan → apply → observe → verify cycle. Only
  phase F1 ships in this release (#556):
  - **catalogue 1.0.0 → 1.1.0**, with 27 new network and firewall entries (127
    total);
  - **`ProviderKind::Gateway`** and **OPNsense in `provider ls`**, with a
    declared and never-probed report: 3 supported, 1 partial;
  - **`type: opnsense` in `providers.yaml`**, with `keyFile`/`secretFile` (a
    secret written inline in the file is rejected by name) and
    `networkDefaults`. No Kind resolves via `networkDefaults` yet; that is F2.
- **ADR-0051: `kind: NetworkGateway`** (#498), with `GatewayProvider` as the
  port and OPNsense as the first implementation (aliases and filter rules via
  the appliance's REST API). The default memory of a registered appliance went
  from 2G to 3G, the minimum the manufacturer documents (#494).

### Proxmox VE: API coverage is a measured matrix

ADR-0049 (#474) fixed the denominator: the **675 routes** (method, path) that
PVE 9.2.2 itself publishes. `scripts/proxmox_api_inventory.py` reads that schema
and what `delonix-proxmox` calls from the source code, and
`docs/proxmox/matrix-9.2.2.md` is generated and checked by a test. The
"tested" column comes from a trace of routes recorded during live runs, with
provenance in the header.

**At the start of this cycle: 16 routes called (2.4%). On `main` for this
release: 161 calls (23.9%), 160 seen in a live trace.** The only one still
unseen is the `GET /nodes/{node}/tasks` from lost-response reconciliation,
reachable only by fault injection. By area: qemu 59/109, sdn 85/90, storage
5/25; the 62 LXC routes are `unsupported-by-design`.

- **Transport** (slice 1, #475): errors typed by HTTP status (401, 403, 404
  with exit 4, 409 with exit 5, 502–504 with exit 69), a **per-VM task log**
  (`<vmdir>/proxmox-tasks.json`, UPID recorded before waiting), and the rule
  that **a lost response is not a lost request**: after a transport failure the
  client looks for the task or the effect, and never resends a non-idempotent
  write. Every write goes through the task path, and a test reads the crate's
  source code and fails on a write outside it (#478).
- **New engine verbs**, tested live against Proxmox:
  - `vm resize <name> [--vcpus N] [--memory M]` (#503): cold resize of a
    stopped VM, also on libvirt and Cloud Hypervisor. Rejected with the VM
    running (**DX-5505**).
  - `vm cloud-init <name> [--hostname] [--user] [--ssh-key]` (#509): changes
    the cloud-init of a stopped VM. On Proxmox, the proof is the node's own
    rendering; on libvirt and Cloud Hypervisor it is rejected by name, because
    the seed is an ISO made at creation time.
  - `vm move <name> --node <target> [--live] [--with-local-disks]
    [--target-storage <id>]` (ADR-0053, #522, #532, #536): moves a VM between
    the nodes of its cluster, cold or live, with the same `vmid` and the same
    registry entry. By default, a VM with local disks is rejected; with
    `--with-local-disks` the node copies them (NBD mirror with `--live`).
  - `provider describe proxmox --probe` (#505): five `GET`s against the
    target's cluster (quorum, nodes, storages, HA, SDN zones), read-only.
- **Each VM is addressed on its own node** (ADR-0053, #515). Before, every
  per-VM path used the configured node, so a VM migrated via the Proxmox UI
  was looked for on the wrong node. A VM moved outside the engine is found
  with a read of `/cluster/resources`.
- **Power** (#502): `shutdown`, `reboot`, `reset`, `suspend`, and `resume`.
  `vm pause` is no longer rejected on Proxmox.
- **Creation**: `diskSize` on a clone of a template grows the disk via
  `PUT …/resize`, and a shrink is rejected by name (#485); `extraDisks` and
  `extraNics` in the same VM `POST`, and `destroy` takes all the disks with it
  (#504).
- **Booting an image from the engine's store** (ADR-0057, #541): the
  `vm create --backend proxmox --disk <store image>` command sends the image to
  the node's import storage (with the sha256, verified by the node, once per
  image and per node) and creates the VM with `import-from`. There is no
  longer a need to hand-prepare a template. Storages via
  `DELONIX_PROXMOX_IMPORT_STORAGE` and `DELONIX_PROXMOX_DISK_STORAGE`, or
  `storage.import`/`storage.disk` in `providers.yaml`. The engine never
  toggles the `import` content type on the node (**DX-6510**); insufficient
  space is **DX-6511**.
- **Backup and restore** via `vzdump` (#487, #489): restore never writes over
  an occupied `vmid`. With the guest agent (#528), a backup is only reported
  as quiesced when the node's log shows `fs-freeze` and `fs-thaw` (otherwise
  **DX-6509**), and `vm describe` gains a *Guest* block (OS, kernel, hostname,
  filesystems).
- **Per-node firewall by VM** (ADR-0052, #492, #496, #512): `kind:
  NetworkPolicy` gains `scope: vm`, and a VM's direction policy goes to the
  firewall of the node it runs on. The engine only replaces rules marked
  `delonix-managed:<n>`, and hand-made rules stay. With the datacenter
  firewall off, the apply rejects with **DX-6508** before any write.
- **Proxmox's own SDN** (#493, #497, #500, #542): zones, vnets, subnets,
  IPAM/DNS/BGP/EVPN controllers, fabrics, DHCP, IP reservations, prefix lists,
  route maps, and vnet firewall. The global lock is used as a transaction
  (`sdn_transaction`), with rollback if a step fails. **`kind: NetworkZone`**
  (#501) links Proxmox's SDN to a manifest, with no `provider` field.
- **Three measured facts the schema does not state**, which changed code:
  - `…/status/suspend` creates a `qmpause` task, not `qmsuspend`;
  - vnet firewall is only applied by `proxmox-firewall` nftables, and filters
    bridge traffic within the vnet, **not traffic routed between vnets**
    (#549, #551, documentation only);
  - the repository's appliance image rewrote `/etc/network/interfaces`
    without `source /etc/network/interfaces.d/*`, and SDN applies before #500
    were accepted **with nothing actually done** on the node. The script was
    fixed. The Proxmox images also now rewrite `/etc/hosts` with the real
    `vmbr0` address on every boot (#548).
- **ADR-0058 (Accepted on 2026-09-28; proposed in #543)**: a Proxmox LXC
  container does **not** serve `kind: Container`. There is no `exec`, no logs,
  no exit status in the API, and none of the engine's SDN applies. If LXC
  comes in, it will be its own resource. The 62 routes stay
  `unsupported-by-design`, and only slice 0 (the three task outcomes, above)
  and slice 1 (below) ship in this release. Accepted with the resource to be
  named `kind: SystemContainer`, for parity with Proxmox
  (#574); the Kind does not exist yet.
- **OCI archive a Proxmox node accepts** (#574, plan 63 slice 1):
  `delonix_oci::write_oci_media_archive` writes an OCI-layout archive with OCI
  media types (the store's blobs byte for byte, only the manifest rewritten)
  and rejects a zstd or foreign layer by name (DX-1409). Measured on the lab
  node: the `alpine:3.20` archive was accepted by `pvesh create
  /nodes/pve/lxc`; Docker v2 from `image save` was rejected. **No command
  calls it yet** — the upload is slice 2 — and `image save` is still Docker v2.
- **The archive goes up to the node as a container template** (#576, slice 2):
  `Client::stage_template` sends it as a `vztmpl`, with the name taken from the
  manifest's digest (`dlx-<hex>.tar`) and the sha256 for the node to verify; an
  archive the node already has is not resent, and a lost response is resolved
  by listing the storage. It rejects, before sending a single byte, a storage
  with no `vztmpl` (**DX-6513**) or no space (**DX-6514**). Measured on the lab
  node: a bad checksum ends the task with `checksum mismatch` and leaves no
  file behind. **Also still with no command that calls it**: wiring the
  engine's pull to this is slice 3.

### Providers: a capability catalogue and a per-node file

- **Versioned capability catalogue** (ADR-0050, #476). `delonix provider
  ls|describe|matrix` answers, per provider, each catalogue entry with one of
  six states. **`supported` does not self-certify**: it has to cite a check, an
  e2e, a chaos case, or a live test, and a test confirms each citation exists.
  `provider ls` makes no request at all; Proxmox is declared and never probed.
  `docs/providers/capability-matrix.md` is generated and checked by a test.
  With new checks in the battery, 17 lines for libvirt and Cloud Hypervisor
  went from `partial` to `supported` (#499); writing those checks found three
  defects, also fixed (a CH VM in the `default` namespace with no anti-spoof
  rule, the live backup of a libvirt VM with two disks, and `vm vnc` printing
  `127.0.0.1:0` for a `host:N` response).
- **`vm create --require <capability>`** and `spec.requiredCapabilities`
  (#479): a name outside the catalogue is **DX-1527** (exit 1), a backend that
  does not serve the entry is **DX-6507** (exit 69), and both rejections happen
  before the disk is touched. The two internal predicates that used to compare
  the backend name now read the capability report instead (#482).
- **`providers.yaml`** (ADR-0054, #514, #519, #521): a per-node file
  (`config.delonix.io/v1`) says which providers a node has, how to reach them,
  and which serves a request with no `--backend`. It is looked up in this
  order: `DELONIX_PROVIDERS_CONFIG`, `$XDG_CONFIG_HOME/delonix`,
  `/etc/delonix`; the first file found wins, and files are never merged.
  Unknown fields and inline secrets are rejected by name. Verbs:
  - `provider config show [-o json]`: the file read, the files the order
    skips, the default, and where it comes from. A credential appears only by
    its origin;
  - `provider config validate [-f]`: the parser and what the file points to
    (token readable only by its owner, CA, secret), with no contact to
    anything;
  - `provider config schema`: the JSON Schema, published at
    `docs/schema/v1/providers.json`;
  - `vm default-backend --set/--clear` now edits the file;
  - `install.sh --vm-provider <libvirt|cloud-hypervisor>` writes it **only if
    it does not exist** (noclobber, symlinks included).
- **`vm create --allow-mac-spoofing`** / `allowMacSpoofing` (ADR-0055, #531):
  explicit, per-VM opt-out of libvirt's anti-spoofing filter, for a nested
  hypervisor. Visible in `describe vm` (`Antispoof: OFF`), with a warning on
  `create`, and rejected where there is no filter (**DX-1505**).
- **VM port in the compute context** (ADR-0044, accepted, #486, #517):
  `VmBackend` and its types move to `delonix-compute`, and
  `delonix-proxmox` no longer depends on `delonix-vm`. It is an internal
  change; no caller changed.

### OCI images: pull and push without the whole image in memory

A performance batch covering pull, push, and build. Each gain was measured;
the timing measurements were taken on a shared, loaded host, and the PRs say
so themselves.

- **Pull streamed directly into the CAS** (#535): each layer is written as it
  arrives, with the hash computed in the stream and the write on its own
  thread. Peak RSS for a `node:22` pull: **214 MB → 27 MB**. The config now
  downloads in parallel with the layers (#518).
- **VM image pull straight to disk, resumable across processes**
  (#523): a partial `<dest>.<digest12>.download` is resumed via `Range` by the
  next process, and is only renamed once the content matches the manifest.
  Peak RSS for 276 MiB: **278 MB → 13 MB**.
- **First run with parallel layer extraction** (#533): up to 4 at a time,
  streamed from the CAS. RSS of the first `node:22` `run`: **~220 MB →
  ~21 MB**.
- **A warm pull no longer rewrites the image registry entry, and the CAS
  survives a crash** (#530): `fsync` on the blob and the directory after the
  rename. Measured cost: 18 `fsync` calls per pull.
- **Push with no 5-minute ceiling** (#518). Before, any layer that did not
  finish uploading in 300 s always failed (at ~1.3 MB/s, above ~390 MB).
- **Push straight from the file** (#524), instead of three in-memory copies.
  `vm push` of 276 MiB: peak RSS **837 MB → 10–13 MB**.
- **Upload retry** (#526): up to 5 attempts, with backoff of 1, 2, 4, and 8 s,
  for transport failures and 5xx, 408, or 429 responses. Each attempt starts
  with a `HEAD`, so a blob the registry already accepted is not sent twice. A
  400 or a 403 fail immediately.
- **Parallel push layers, with a progress bar** (#527): up to 4 at a time.
  `node:22` (389.5 MiB) with a 20 MB/s-per-connection ceiling: **22–65 s →
  11 s**. `image sign` publishes with the same client that read the manifest.
- **Cross-repository mount within the same registry** (#538): a blob the
  registry already has in another repository is linked with no bytes sent.
  Measured against ghcr.io: promoting an image to a new repository took
  **7.0 s**, against 356 s for the first push. If the token server refuses the
  broader scope, the push continues without the mount.
- **A push that loses the connection says why** (#573). An `image vm push` to
  ghcr.io exited with a non-zero code after ~4 min, with the only output being
  the startup INFO line. The cause, reproduced against a local registry that
  closes the connection mid-PUT: the process was dying from **SIGPIPE (rc
  141), with no word and no retry**. Now:
  - an EPIPE on a network socket is an error, and the retry runs;
  - the message carries the full cause chain and how much was sent
    (`connection lost with N of M bytes sent`);
  - a rejected response carries the status and the start of the body (the OCI
    code, for example `DIGEST_INVALID`). The `delonix login` hint only shows
    up on 401/403.

  **Push has retry but does not resume**: each attempt resends the blob from
  byte 0 (monolithic PUT). Pull resumes via `Range`; push does not. See the
  limitations.

### Containers: the death of a process is a fact to be measured

Three PRs about the same class of defect: a delivered SIGKILL is not a dead
process.

- **`rm -f` waits for the real exit** (#562), described above. The chaos
  harness now measures processes, not registry entries (#561, #562): a
  `sandbox-teardown` verdict fails if any process with the sandbox root is left
  standing.
- **A boot that fails after `clone` reaps the child and only then removes the
  cgroup** (#564). Before, with userns (the normal rootless path), an empty
  `dlx-<id>` was left on the host in 4 of 4 runs, and a zombie for every failed
  boot.
- **A new incarnation is published under the registry lock** (#570). `spawn`
  was writing the new pid with an unlocked `save`, and the old supervisor's
  `update` could delete it afterwards. The registry ended up with no process,
  and the next `rm -f` signalled nobody. Publishing over another live
  incarnation is now rejected with **DX-5101** and the child is reaped.

### Resources, build, and disk

- **`system df` counts the whole store** (#480): the `VM disks`, `build
  cache`, and `images-build` areas are now in, an `other` line closes the
  table, and a `TOTAL` matches `du`. Before, on a real node, a 190 GiB state
  reported 105.
- **`net netns gc [--force]`** (#481): finds, via `/proc`, network
  infrastructure whose root has been deleted (pins, controls, slirps) and,
  without `--force`, only reports it.
- **Malloc arena ceiling** in the processes that stay resident (pin, control,
  CRI, mgmt, Docker API): `delonix-mgmt` at rest went from **2.3 GB to 111 MB**
  of VmSize. An operator's `MALLOC_ARENA_MAX` still takes precedence.
- **Parallel disk traversal** in `system df`, in volume usage, and in the
  rootless quota: **2.0–2.5 s → 0.35 s** over 32 GiB, with identical output.
  `DELONIX_WALK_THREADS=1` restores the sequential path.
- **The build cache expires** 7 days after its last use, and `system prune`
  sweeps it. `vm prune` names the `vms/` directories no registry entry points to.
- **`delonix build`** (#529): no more free wait for every work container, and
  a cached step closes with a ✓ (before it closed with a ✗ even though the
  build finished fine).

### Node contract and MCP

- **`delonix-node-api`: the node contract now has a server** (ADR-0050 D5,
  #525). It is a new executable, `delonix-node-api` (crate
  `delonix-node-api-bin`), run by `delonix serve node-api`, installed by
  `install.sh` alongside `delonix` and built by `release.yml`. It serves gRPC
  and HTTP/JSON from the same `.proto` files on a `0600` unix socket with

  names the step that brings it in. The contract gains two additive fields
  (`Capability.state`, `ProviderInfo.catalog_version`), and `buf breaking`
  against v4.4.0 passes.
- **`workload.usage`** (MCP, #568): cumulative per-workload counters (CPU,
  memory and peak, block I/O, pids, the ceilings in force), read from each
  container's cgroup and from each local VM's VMM process. These are
  counters, not rates: whoever samples twice gets the rate. **A missing number
  is named with the reason, never zero.**

### Known limitations and what was NOT validated

**Image push**

- **#573 was not reproduced against the real ghcr.io** (HTTPS/rustls). It was
  reproduced against a local registry that closes the connection mid-PUT. The

## v4.4.0 — `drift`, the Compose matrix with a denominator, and a performance gate that refuses to judge

Seventeen commits since `v4.3.0`. Numbered as MINOR: there are three new verbs
(`delonix drift`, `delonix migrate assess`, `compatibility compose`) and a new
Kind (`RuntimePolicy`), all additive — no surface was removed nor changed
meaning. The common theme of the three headline improvements is the same:
**stop answering one question with another**.

A PROCESS change also lands, and it affects who publishes: **pushing a tag no
longer publishes anything** — see the last section.

### `delonix drift` — what the MACHINE changed, with the manifest out of the comparison (M05, #470)

`stack plan` answers "what would an apply do", and that answer mixes two
things from different origins: the edits someone made to the FILE and the
ones someone made to the NODE. The `plan`'s own `--help` already admitted the
limit — "with the manifest unchanged, whatever it prints IS drift" — and that
is precisely the condition that makes it unusable as a gate: in a PR the file
has always changed.

- **Compares the last-apply stamp (`delonix.io/last-applied`) against what is
  observed.** Whatever differs happened outside the declarative path: a
  `container update`, a hand-run `nft`, someone fixing an incident at
  4 a.m.
- **The manifest is OPTIONAL**, and that is what gives it its main use case: on
  a node without the repository the command still answers. The six Kinds that
  can only be enumerated from the document (`RuntimePolicy`, `Image`, `App`,
  `NetworkPolicy`, `HTTPRoute`, `Gateway`) are **named in the output** instead
  of being omitted — a shorter table reads as "clean node".
- **A resource with no stamp is a THIRD STATE, not drift** (`unstamped`):
  created by hand, or adopted from a version prior to the stamp. There is no
  recorded intent to compare against, and calling it drift would be inventing
  a baseline.
- **Only the keys the stamp carries are compared** — a field present in what is
  observed and absent from the stamp is an engine default the apply never set,
  and reporting it would bury the line that matters under noise.
- `--stack <name>`, `-o json`, and `--detailed-exitcode` (2 = there is drift),
  the same contract as `plan` and `diff`.
- **The gate caught a real bug on its first run.** The list of
  document-dependent Kinds would be the seventh list in this repository that
  has to agree with another and silently stops agreeing, so
  `doc_scoped_matches_the_stack_wiring` reads `stack.rs` instead of trusting a
  comment — and it failed: `network_access_rule::actual` receives `docs` and
  **ignores them**, so it did not belong in the list.

New group, **not stable** (`docs/cli-stability.md`), with its own page on the
site.

### `compatibility compose` + `migrate assess` — the third state needs a denominator (M02, #471)

`compatibility docker` has published three states since it existed: served,
refused with a reason, missing. `compose` did not have the third, and the
module itself said why — "has an allowlist but no three-state surface of its
own to reuse". The "missing" state needs a DENOMINATOR.

- **The spec list was MEASURED, not written from memory**: a minimal compose
  file per candidate key, `docker compose config` on each one, and what

### The performance-regression gate, and the third exit (M11, #469)

`scripts/bench.sh` already measured the three engines on the same machine and
already refused to run on a loaded bench. What was missing was the other
half: nothing compared today's number against a recorded one.

- **`scripts/bench_gate.py` READS a measurement and never takes one** — two
  opinions about the same number is how they start to diverge.
- **Three exits, not two**: `0` within tolerance (25%), `1` regression, and
  **`3` refuses to judge**. The third is what makes it trustworthy, and it
  comes from the 2026-08-10 incident: docker 1406, podman 1351, delonix 640,
  and the next run 208/268/89. A naive gate would have read that as "delonix
  regressed 7×" because of a machine problem. Docker and podman are
  **anchors**: if they degraded as much as we did, what changed was the bench
  — and with no anchor at all it also refuses, instead of guessing.
- **Baseline per MACHINE.** A median measured on a 32-thread desktop says
  nothing about a 2-vCPU VM, and comparing the two fabricates exactly the
  noise the gate exists to filter out.
- **Dispersion, because the load threshold is not enough**: measured at load
  6.44 (below the limit), a ten-sample run of docker went from 434 ms to
  5,407 ms and the median absorbed it. Above **3×** the gate does not judge;
  **recording is stricter, 1.5×** — a judgement run gets discarded, a baseline
  gets reused by every run that follows.
- **Three harness defects fixed along the way**: `--json` was accepted and
  IGNORED (the variable was assigned and never read); `time_n` did not look at

- **One dead gate**: no `scripts/test_*.py` was running in CI — `
  test_release_verify.py` was born the day before with ten tests that nothing

Baseline recorded on the development machine (2026-09-23, `ceec7f8c`): docker
**224 ms**, podman **279 ms**, delonix **87 ms**.

### Build: cache mounts and per-image SBOM (M03, #468 and #466)

- **`RUN --mount=type=cache,target=<path>[,id=<name>]`** — a persistent,
  read-write directory that survives across builds, generalizing the
  mechanism `type=secret` already used (`mount_live`, invisible to the final
  image). The directory is `<root>/build-cache/mounts/<sha256(id)>` — **as a
  hash, never the raw string**: an omitted `id` defaults to `target`, an
  arbitrary path controlled by the Dockerfile. `sharing=` and `ro` are
  **refused** instead of accepted-and-ignored. Validated live: two separate
  `delonix build` runs wrote into the SAME cache mount and the second saw
  what the first had written; the content never showed up in the final image
  (confirmed by `container run` inside it).
- **Automatic SPDX 2.3 SBOM per built image** — `delonix build` writes it
  best-effort right after a successful commit, and `delonix image sbom <ref>`
  serves it. Reuses the already-existing `extract_sbom` (apk/dpkg, without
  mounting or running the image). Validated live: a build of `alpine:3.20` +
  `apk add curl` produced an SBOM with 25 packages, and `image sbom` returned

  recomputation.

### BREAKING for whoever publishes: pushing a tag no longer publishes anything (#472)

`release.yml` triggered on `push: tags: ["v*"]`, meaning the release was built
the instant the tag reached the remote — including a tag pushed by accident
(`git push --tags`, `push.followTags=true`), and with no step between "the tag
exists" and "the world has a binary". **The tag and the release now become two
decisions:**

```bash
git tag -a v4.5.0 -m "v4.5.0" && git push origin v4.5.0   # cuts the version
gh workflow run release.yml -f tag=v4.5.0                 # publishes it
```

- **The tag is DATA, not the ref**: every job reads the tag from the input and
  checks it out explicitly, instead of `GITHUB_REF_NAME` — which on a dispatch
  is whatever ref the operator happened to have selected, and a release that
  builds one commit and calls it another is the worst kind of wrong.
- **New `guard` job**, first and costing seconds, because the input is now
  trusted by everything downstream (it chooses the commit to build, names the
  release, and gets compared against the binary's own version). It refuses a
  tag that does not have the `vX.Y.Z` shape, one that does not exist on the
  remote, and one that **already has a release** (republishing over it is like
  the assets changing under someone who already downloaded them). Without the
  first guard, a `tag: main` would have checked out a branch and published a
  release called "main".
- **The cost, stated because it is a cost**: a tag with no release becomes a
  normal intermediate state. `scripts/version_gate.py` is unaffected — it has
  always looked at the TAG, never at the release.

## v4.3.0 — `delonix hosts sync`, and the installer accepts aarch64

Four commits since `v4.2.0`. Numbered as MINOR: there is a new command group
(`delonix hosts`, marked **not stable**). A small release, two user-visible changes
and two documentation ones; each section says what was proven and what was not,
and what was not validated is listed at the end.

### `delonix hosts sync` — service names in `/etc/hosts` (#449, ADR-0048, phase 2)

- **`delonix hosts sync`** publishes the default name of every exposed container
  (`<name>.<ns>.svc.delonix.internal`) into a delimited block in `/etc/hosts` —
  the same block, per state root, as ADR-0046, so a name a route requested via
  `hosts: [host]` and one published here share **one** block and one refusal
  rule. Every name points to `127.0.0.1`: it is the published port of the L7
  proxy the host uses to reach a workload on the SDN.
- **`--print`** shows the block and touches nothing; **`--off`** removes it and
  stops maintaining it.
- **Once enabled**, `container run --expose` and `rm` keep the current block,
  best-effort: a name a route *requested* fails `apply`, but a name published by
  this command is a convenience the operator switched on, and a `run --expose`
  without root does **not** fail because the file needs root — it only warns.
- **Without root it refuses and prints the block** to add by hand. A name that
  already has an entry outside the block is refused (never overwritten), and a
  refusal never leaves state half-done: the file stays intact and the switch off.
- **Under `sudo` it reads the invoking user's store**, not root's. Without this,
  `sudo delonix hosts sync` (the natural step when the command refuses without
  root) would read `/var/lib/delonix`, which is empty, and would publish «0
  names». It is the same fix `vm bridge` already had
  (`adopt_invoking_user_root`); an explicit `DELONIX_ROOT` still wins.
- **New group, not stable** (`docs/cli-stability.md`): documented in the
  `README.rst` table and on the site, with its own page
  (`docs/commands/hosts.html`).

### Installer: accepts aarch64 (#447)

- `install.sh` accepts `aarch64` (and `arm64`, normalised) instead of refusing
  everything that is not x86_64. The asset name is built from `uname -m`:
  `delonix[-cri|-mcp|-mgmt]-aarch64-linux` — the ones `release.yml` has published
  since `v4.2.0`. Other architectures still refuse, saying which are supported.
- **On aarch64 there is no `-v3` variant** (it is an x86-64 microarchitecture
  level), and the QEMU probe asks for `qemu-system-aarch64` — it used to ask for
  the x86 emulator and install it on an ARM host.
- **Outside x86_64 it does not download** the static Cloud Hypervisor, the EDK2
  `CLOUDHV.fd` nor `hypervisor-fw` (they are all x86-64 builds, and the pinned
  checksums too); the installer says so, and the VM backend is libvirt. No pins
  were invented for arm64.
- **Important note:** the `install.sh` published by `v4.2.0` is the old one,
  which still refuses aarch64. **This is the first release whose `install.sh`
  accepts it.**

### Documentation

- **Contributor manual** (`docs/dev/`) updated for `v4.2.0` (#453): `vm
  build`/`vm.yaml`, `verify-images.sh`, the aarch64 binaries, `--performance`
  and the default service name.
- **`v4.2.0` notes corrected** (#454): they claimed a libvirt VM was refused and
  that `kind: IPPool` was a later phase. Both are built (phases 2 and 3 of
  ADR-0046) — only `announce: l2` and `hosts: guest` (phase 4) are missing. The
  mistake was copying the body of an outdated PR.

### What was NOT validated

- **`delonix hosts sync`:** the **real** write to `/etc/hosts` (requires root;
  only proven on a test file, checking content by `md5`: write, idempotency,
  refusal on conflict, refusal without permission, and `--off` restoring the
  file byte for byte) and a client resolving a name from the block and reaching
  the backend. **Automatic refresh** only works when the file is writable by the
  process: for a typical rootless user, a `container run --expose` only warns,
  and `hosts sync` is, in practice, a manual command. Phase 3 of ADR-0048
  (credentials) is not in this release.
- **Installer on aarch64:** a full install on a real aarch64 host never ran (no
  ARM binary was installed on top of an x86 machine), nor were the QEMU package
  names per distro on arm64, nor the `dnf`/`apk` paths. What was proven: the
  asset name composition — the real `fetch_asset` function, against the assets
  published from `v4.2.0`, with negative controls.
- **What `v4.2.0` already listed** remains unvalidated: package installation and
  the `vm build` golden profiles, booting the built images, the real appliance
  builders, and what ADR-0046 marks as not measured.

## v4.2.0 — `vm build` with `vm.yaml`, per-distro and per-appliance recipes, VM services by name

Seventeen commits since `v4.1.1`. Numbered as MINOR: there is new CLI
surface (`vm build`, the `vm.yaml` file), a new Kind (`IPPool`) and new manifest
fields. The series comes
from several independent fronts, and each section says what was proved and what
was not — what was not validated is listed at the end, together.

### `vm build` and `vm.yaml` — the `docker build` experience for VMs (#451)

- **`delonix vm build` now exists.** Until now there was only `delonix image vm
  build`; the two share the same argument set and do the same thing.
- **`vm build .` picks the recipe like `docker build` does:** an explicit `-f`
  decides (a `.yaml`/`.yml` is read as `vm.yaml`, anything else as `VMfile`); without
  `-f`, a `vm.yaml` in the folder wins over a `VMfile`, which wins over the golden
  recipe. `-t` names the result **and** the `${TAG}` inside the file; `--target`
  picks one image when the file declares several. With a `vm.yaml`, `-t`
  becomes optional (it uses the image's `tag:`).
- **`vm.yaml` is `VMfile`'s "compose"** (the "Dockerfile"). Strict schema — an
  unknown key is an error, and a field the chosen route does not support is
  refused by name, never ignored. It describes the full qcow2: base, size,
  hostname, vcpus/memory, packages, users (sudo, groups, shell, keys),
  services, files (with the full destination path and mode), `env`,
  cloud-init, `run:`, **what to remove** (`remove.packages/paths/users/services`,
  applied after everything else, so it also prunes what a package brought in) and
  cleanup (`package cache, logs, history, /tmp, machine-id`). `${TAG}` and
  `${VAR:-value}` expand in values, not in comments.
- **No second build engine.** Each image compiles to a builder that already
  existed: a synthesized `VMfile`, the golden recipe (`profile: rootless|k8s`),
  an existing `VMfile` (`build.file`), or an appliance builder.
- **`appliance:` route** for what cannot be described as edits to a cloud image
  (Proxmox from an ISO, OpenStack pulling ~20 GiB of containers). The
  `vm.yaml` **names a builder** (`builder: proxmox`), never a path: the
  engine resolves it to `scripts/appliances/build-<name>.sh` inside the
  repository, validates the arguments and environment variables (no `PATH`,
  `LD_*`, `BASH_ENV`…), runs it with an isolated `OUT_DIR` next to the store,
  imports the single qcow2 it leaves behind and deletes the working folder, even on
  failure. A foreign `vm.yaml` cannot make the host run a file of its own
  choosing.
- **`images/`**: one folder per image, each with a `vm.yaml` and an end-to-end
  README. Four distros that build **offline** (`ubuntu`, `debian`, `rocky`,
  `fedora`) and eight appliances (`opnsense`, `proxmox`, `truenas`, `openstack`,
  `monitoring`, `carbonio`, `glpi`, `wazuh`). The scripts stay in
  `scripts/appliances/`, where the workflow that publishes the images reads them from. The
  recipes keep `/usr/share/doc` on purpose: it holds the licences a published image
  has to redistribute.
- **`scripts/verify-images.sh`** builds the recipes in an isolated `DELONIX_ROOT` and
  **reads the qcow2's content** (or the VM's) against what the recipe declared. It has a
  probe recipe with values the base cannot have (the base already ships a
  `delonix` account with sudo, so verifying that on the delivered recipe proved
  nothing) and a `--self-test` requiring the checks to **fail** on an image
  nobody built.
- **A test closes the loop**: `every_shipped_recipe_is_valid_and_complete` fails
  if a shipped recipe stops being valid or points at a file or
  builder that does not exist.
- Error messages from `vm.yaml` and the appliances go through the catalog (`pt.po`).

### VM services by name (#444, #448, ADR-0046/0047/0048)

- **`VirtualMachine.spec.expose`** publishes an HTTP/S service of a VM by name:
  it lowers on `load` to an `HTTPRoute/<vm>-expose`. The route resolver knows
  **Cloud Hypervisor** VMs (on the SDN) and **libvirt** VMs in `nat`/`bridge` mode (ADR-0046,
  phase 2): these are reached through a second instance of the proxy in the host's netns,
  without root, listening only on `127.0.0.1`. A libvirt VM in *user-mode* has
  no reachable address and is refused with the fix (`netMode: nat` in
  `qemu:///system`); a document mixing backends from the two halves is
  refused, naming which falls into which.
- **`kind: IPPool`** (`networking` group; ADR-0046, phase 3): a ledger of
  **host** address reservations (a single address, a range or a CIDR; IPv4 only) that
  routes claim via `spec.pool` (and `expose[].pool`). A route claims a single
  address while it is declared, becomes reachable on it instead of on
  `127.0.0.1`, and `hosts: [host]` points the name at it. It is a full Kind
  (`apply`, `plan`, drift, `--prune`, `get`/`describe`/`delete ippools`) and applies
  before `HTTPRoute`. **Only `announce: local`**: the address must already be on
  a host interface, and `apply` verifies it by binding to it; `announce: l2`,
  `interface`, IPv6 and BGP are refused (phase 4, yet to be built). A pool with leases
  is not deleted nor shrunk below a lease, and release happens by
  declaration — there is no reaper guessing who is alive.
- **`hosts: [name]`** on an `HTTPRoute` (and on `expose[].hosts`) writes each host
  as `127.0.0.1 <host>` in a delimited block of the operator's `/etc/hosts`
  (`cmd/hosts_file.rs`), reading the names from both proxy instances. Only the block
  is touched; a name already present outside it is refused, and a block without an `END`
  line is refused instead of deleting the rest of the file. Without root, it refuses and shows
  the block to add.
- **Drift fixed**: a route to a VM used to read as permanent drift,
  because `actual()` only mapped addresses to container names.
- **ADR-0048, phase 1 (#448)**: the default service name `<name>.<ns>.svc.delonix.
  internal` (the old FQDN still works as an alias) and the `SVC` column in
  `container/vm/stack ls`. ADR-0047 (the L7 proxy authorizing container origins,
  for `hosts: containers`) stays **a proposal only**, and
  `hosts: guest` and ADR-0046's `announce: l2` (phase 4) are still to be built.

## v4.1.0 — ADR-0043 closes on the last five crates, and a fresh root node accepts `-m`/`--cpus` again

Eleven commits since `v4.0.0`. The trigger was a production fix (#415, external
PR, reviewed and merged in this session): a FRESH root node refused `-m`/`--cpus`/
`--cpu-weight` even when the kernel delegated all three controllers — and, in the
case where delegation was indeed real but partial, the operator saw "Permission denied"
where the right answer was "`cpu` is not delegated, run this". Alongside it, the five
crates `v4.0.0` had left undone ("Known, not fixed in this series") gained
ADR-0043's `DX-CDNN` code dictionary — which now becomes **Accepted**. No CLI
surface change (commands, flags, Kinds): this series is about the QUALITY of
what the engine was already doing.

### `-m`/`--cpus`/`--cpu-weight` on a root node: the refusal was asking the wrong question (#415)

`cgroup_limits_apply()`, in root mode, only asked "can I create a cgroup under
`delonix.slice`?" — necessary, but not sufficient: the right question is "were the
controllers actually HANDED DOWN to the slice's children?". `ensure_delonix_slice`
discarded every write to `cgroup.subtree_control` with `let _ =`, so a
slice that didn't receive `cpu` from `/sys/fs/cgroup` ended up with no `cpu.max` — and
the error message said **"Permission denied"**, because `std::fs::write` opens with
`O_CREAT` and cgroupfs refuses to create a regular file with `EACCES`: same
directory, same uid, `memory.max` accepted one line before.

Two fixes, both measured and not just read:

- `cgroup_limits_apply()` in root now asks BOTH questions, the way the rootless
  leg already did — create the cgroup, **and** confirm that `memory`/`cpu`/`pids`
  are in `cgroup.subtree_control`.
- A MISSING `cpu.max` (or `memory.max`/`pids.max`) no longer reports the kernel's
  errno and instead names the missing controller and the command that fixes it. A
  file that EXISTS but refuses the write keeps the errno — that's the right answer
  there. The repair itself is bounded: it only activates a controller the level
  above already offers, never moves a process or tightens someone else's limit.

Four tests cover the pair (reading the delegation, the message, and the two
distinctions — missing file vs. file that refuses). Not validated live in this
session against a real root node (the original finding was reproduced on an aarch64
VM by the PR's author, 2026-09-18); validated in this session with the crate's full
build/clippy/tests and with the merge against current `main` (which had meanwhile
already renamed `Error::Runtime` to `Error::Syscall`, ADR-0043 — the three-way merge
resolved on its own, with no conflict).

### ADR-0043 — the `DX-CDNN` code dictionary

3. The exit code is asked for the error's CLASS, not a variant `match`.

## v3.1.0 — the group-by-group audit: 33 findings, zero new leaves, and the README no longer teaching a CLI from two versions ago

Twenty-nine commits since `v3.0.0`, almost all from a systematic
group-by-group sweep of the CLI (`container`, `image`, `secret`, `stack`, `manifest`, `net`)
plus the residue of fixes the ACH series had already been logging since `v3.0.0`.
No surface breaks — `cli-tree.sh --gate` confirms the same 245 leaves as the
baseline; this release is behaviour, not shape.

Each finding below was measured against the binary BEFORE any code existed, and has its
own gate (`scripts/e2e.sh` or a unit test) that fails red if the fix is reverted.

### `container` — the health probe filled the container with zombies, and `stop` didn't stop

- **The `--health-cmd` probe left TWO zombies per run.** The watchdog that kills it
  at the end of the timeout was never waited on (`wait`), nor was the `sleep` it
  used itself. Measured with `--health-interval 2`: +8 zombie processes every 10s, with no
  ceiling — with the default `pids.max=512`, a container with a healthcheck stops
  being able to fork within ~10 minutes at that interval, and within less than three hours at
  the default 30s interval. The watchdog now kills AND reaps its own
  child, and the caller now waits for it.
- **A requested `stop` could end up `Crashed`.** `runtime::stop` already records `Stopped`
  "even if it needs SIGKILL" — and it does, whenever PID 1 has no SIGTERM handler (the
  most common case: `alpine sleep 600`). The supervisor, waiting in the same
  process, saw `Signaled` and wrote `Crashed` over it — `ps -a` said `Dead`,
  `wait` returned 137, for a container the operator had just told to
  stop. Fixed by honouring `stopped_by_user` at the point where the supervisor records
  the final state.
- **`start`/`restart` lost the supervisor.** `run -d` always forks one (that's what
  makes a detached's exit code knowable); `start` only did it with a restart
  policy defined. `run -d … 'exit 7'` gave `wait` = 7; the SAME container, after
  a `container start`, replied "exit code … was not captured". Now `start`
  asks the same question `run` does.
- **`container healthcheck <id>` ignored the container's own probe.** It only read the
  image's `HEALTHCHECK` — a `run --health-cmd …` showed `Up (healthy)` in
  `ps` and the verb replied "image defines no HEALTHCHECK", a permanent red in
  the CI script that is this command's whole reason to exist.
- **`container port` showed `0.0.0.0` over a loopback bind.**

### `image`/`secret` — a `load` that erased names, a `create` that erased keys

- **`image load` erased the OTHER names of the same image.** `pull` already merges tags
  (`merged_tags`, "identical content ⇒ same id, can have several tags — like
  Docker"); `load` stored the archive's `repo_tags` verbatim, and `save` writes the
  whole registry entry. Measured: a store with `alpine:3.20` and a second name for the
  SAME id, plus a `load` of the second one's `save`, ended up with only the second — on an
  offline node, a manifest or compose using the first name no longer resolves.
- **`secret create` on an existing secret erased the keys it didn't repeat and
  replied `created`.** `a=1,b=2` plus `secret create --from-literal c=3` left
  only `c`, read as "I created a new secret." Now it says `replaced (1 key(s)) —
  2 key(s) dropped: a, b` and points to `secret set`, the non-destructive verb.
- Two broken messages: `image vm rm` of a nonexistent one replied with a nonsensical
  2nd line (`no such one or more VM images were not removed` — the `no such {0}`
  template received a whole sentence), and `image vm describe`/the pull warning in
  `resolve_or_pull` came out half-translated in an otherwise English CLI.

### `stack`/`manifest`/generic verbs — an adoption that silently changed the owner

- **`stack apply` adopted someone else's resource and said "nothing to do."** Adopting is
  the instant a resource with no owner becomes destroyable by the stack — it's
  the ownership that authorizes `destroy`/`--prune`. Measured end to end: a container
  created by hand → `apply` replies "already exists, nothing to do" and stamps
  `delonix.io/stack` → `destroy` removes it. `apply` still adopts (refusing
  would break the normal case of bringing into a manifest what already exists) — now
  it says so: `Container/x: adopted — it belonged to no stack, and a destroy or apply
  --prune of 'st' now removes it`.
- A `kind: Stack` with a misspelled group (`contaienrs:`) expanded to nothing, and the
  error said "`<file>` is empty (no YAML documents)" about a file with one
  document — the warning naming the real cause was left behind in the scroll.
- Two more messages the `no such {0}` template broke: an invalid `kind: Workload`
  exited with class **4** ("doesn't exist") for a manifest that doesn't even
  parse — now `Invalid` (1), as its sibling twenty lines above already was — and
  `volume snapshot restore` replied half a sentence in Portuguese inside the
  English template.

### Inherited from the ACH series since `v3.0.0`

- **ACH-011 — `pod exec` without `--container` was a lottery.** The tiebreak between
  members born in the same second fell to `read_dir` order, which is random on
  every `pod create`. Now it uses the index declared in the manifest.
- **ACH-014 — the cloud-hypervisor backend's `stop` returned with the VMM still holding
  the disk.** A `qemu-img` right after caught the qcow2 lock still taken.
- **ACH-015/016 — a `kill -9` on the network *pin* closed the node to new work
  forever, and the pidfile proved the argv instead of the real owner** — a
  root's `netns down` could kill another root's *pin*.
- **ACH-017 — removing one root's HTTPRoute killed ANOTHER root's L7 proxy**,
  and `apply` said "serving" while not serving.
- **ACH-018 — proof of tunnel ownership was "the cmdline contains `ssh`"**, which any
  `ssh-agent`/Ansible mux for the same user passed — and `stop`
  sent SIGTERM to that unrelated process.
- **Runtime — the resource ceiling covered PID 1 and nobody else.** `-m 64M`

## v3.0.0 — `--vm` and `sharevolume` disappear, and compose is complete

Thirty-nine commits since `v2.0.0`. It is `3.0.0` and not `2.1.0` because the CLI surface
**lost 14 leaves with no alias** — and one of them is in a group that
`docs/cli-stability.md` declares *Stable*, the same reason `v2.0.0` did not fit in a
`1.x`.

### Breaks — what stops existing, and what to use

Every replacement in the table below was **run**, not just checked with `--help`. In `get`
the resource is an ARGUMENT, not a subcommand, so `get vms --help` prints `get`'s help and
returns 0 regardless of the name — that is how the first version of this note sent
everyone to a `get vms` that replies `no such resource kind`. The name is
`virtualmachines`, which abbreviates to `vm`.

Measured against `v2.0.0:scripts/cli_baseline.tsv`: **249 → 244 leaves**, 14 out and 9
in. None of this has an alias: a script that still invokes the old form fails with
`unrecognized subcommand`, never silently.

| Stopped existing | Use |
|---|---|
| `image build`, `image convert`, `image import`, `image init`, `image ls-remote` (the `--vm` forms) | `image vm build\|convert\|import\|init\|ls-remote` |
| `sharevolume apply\|describe\|ls\|rm` | `volume create --parent <volume>`, `volume ls -A`, `volume describe`, `volume rm` |
| `sharevolume migrate` | — removed; see the warning below |
| `storage create`, `storage ls` | `volume create --type nfs\|cifs\|smb\|webdav …`, `volume ls` |
| `pod ls` | `get pods` |
| `vm status` | `vm ls`, `get virtualmachines` (abbreviates `get vm`), or `vm describe <name>` |

**A never-migrated `ShareRecord` (prior to v0.53.x) stops being read.** The
`sharevolume migrate` command that converted it was removed in this series; whoever is in
that state must run it on an earlier binary **before** upgrading.

### Two defects that brought down an entire cluster

Neither failed to compile nor failed a unit test — they only failed a real node.

- **`PodSandboxStatus` returned `linux: null`, and no `kubeadm` would come up** (#233).
- **A privileged container still got `masked`/`readonly paths` anyway** (#239). The
  kubelet sends `readonly_paths` with `/proc/sys` for EVERY container; deciding which to
  honour is up to the runtime, and for a privileged one the answer is none — as in
  containerd and CRI-O. Without this, `kube-proxy` would not write `nf_conntrack_max`,
  stayed in `CrashLoopBackOff`, and without it there is no `ClusterIP` or CoreDNS: the
  cluster's entire service plane fell over two arguments.

And a third that has nothing to do with Kubernetes: **the classic `mount(2)` truncates
`lowerdir=` SILENTLY above ~4 KB**, so an image with many layers gave `ENOENT` preparing
the rootfs. The boundary was measured: 20 layers mount, 30 always fail, and
`paketobuildpacks/builder-jammy-base` needs 9,107 bytes. The overlay moved to the new API
(`fsopen`/`fsconfig`/`fsmount`), one `lowerdir+` call per layer — with no ceiling a
per-layer call could ever hit (ADR-0037).

### `docker compose` no longer has holes

Eight capabilities in one series: `profiles:` (with transitive closure via
`depends_on`), `extends:` (same file, `depends_on` never inherited), `build.target`,
`deploy.replicas`, fixed `networks.*.ipv4_address`, top-level `configs:`/`secrets:`,
anonymous volumes, and **multi-file** (`-f a.yml -f b.yml`).

Only the YAML `include:` directive is left out — it has its own path-relativity rules and
project-name propagation, and the refusal points to `-f a -f b`.

**An anonymous volume is named by PATH, not by position in the file.** Swapping two
`- /path` lines — a trivial edit — would swap which volume backs which path: a database
would come up on the volume that had the logs, silently, with the data intact in the
wrong place.

### Two new Kinds

- **`kind: Service`** (ADR-0032) — selects containers by `matchLabels` and publishes them
  as several `A` DNS records under `<name>.<namespace>.delonix.internal`, with rotation
  in the response. **No VIP, no new dataplane, no daemon.** A client that resolves once
  and keeps the connection is not rebalanced — the limitation of any round-robin DNS.
- **`kind: App`** (ADR-0035) — Cloud Native Buildpacks wired to a real build path. The
  three CNB modules had existed in `delonix-image` all along **with not a single
  caller**; what blocked them was `creator` exporting to an OCI registry the container
  builder could not reach. Fixed with a disposable registry on the SDN.

### New commands

`image sign` (ECDSA-P256 compatible with cosign, key generated once at `0600` on
creation), `cluster drain`/`uncordon`/`upgrade`, `vm migrate` (stop-copy-start, with a
real stop — live migration is a measured NO-GO, ADR-0031), `vm pause`/`unpause`,
`net capture`, `pod port-forward`.

### What does NOT change

The engine remains daemonless and rootless-first. No new dependency entered the supply
chain because of `image sign` — `ring` was already in `delonix-image` for `verify`. Fleet
management remains blocked by ADR-0010, and `cluster drain`/`upgrade` does not reopen it:
they are operations over the Kubernetes API and over SSH, the path the ADR itself calls
*built and shipped*.

### Hygiene measured, not claimed

`Cargo.toml` spent 38 commits saying `2.0.0` — the series' binary and the published one
presented the same number, and what discriminated between them became behaviour. And the
language *ratchet* was being used as a ceiling that keeps rising: #218 raised
`identifiers` from 1056 to 1061 and #220 to 1062. Sixteen test names translated; the
baseline **drops** to **1045**, below `v2.0.0`'s own 1049.

## v2.0.0 — `image list`/`backup list` revert to `ls`

Reversal of an earlier contract break, itself a contract break — that's
why it's `2.0.0` and not another `1.x`. `docs/cli-stability.md` has said, since v1.0.0, that "a
breaking change no longer fits in a `1.x`": `image list`/`image remove` were in the
*Stable* table, and reverting `list` undoes a promise made in that table.

### What changes

| old (v0.67.0+) | new |
|---|---|
| `delonix image list` | `delonix image ls` |
| `delonix backup list` | `delonix backup ls` |

Clean cut, no alias — the `list` spelling fails with `unrecognized subcommand` (rc=2),
never silently, the same rule as every previous reorganization (v0.30.0,
v1.0.0). `image remove` **stays** — only the listing verb reverts.

### Why

The B2 CLI restructuring (v0.67.0) had renamed `image ls`/`image rm` to
`image list`/`image remove`. That left `image list` as the **only** naming exception
in a CLI where the other 15 "list" leaves use `ls` — `network
ls`, `volume ls`, `vm ls`, `pod ls`, `secret ls`, `stack ls`, and more — following the
Docker/Podman/kubectl pattern this same project already cites for `container`'s
verbs. `backup list` had never been `ls` (the `backup` group was born after
B2, already with that spelling), but it's rolled into this reversal so the CLI tells a
consistent story ("`ls` everywhere, no exceptions") in a single release instead of two.

The `backup` group is declared **not stable** in `docs/cli-stability.md` — that
half alone wouldn't force a major. Only `image list` does.

### What does NOT change

No other command, flag, or semantics. `image remove`, `image pull`, `image push`,
`image build --type`, and the rest of the `image`/`backup` group stay exactly as they
were. Exit codes don't change.

### Bonus found while measuring, fixed along the way

`scripts/e2e.sh` had ~6 checks that had been calling `image ls` since before B2
— dead since then (`unrecognized subcommand`, rc=2, never caught by CI). This
reversal makes them pass again, without touching them. The `backup list`
checks were renamed to `backup ls`.

### The leaf count

`scripts/cli_baseline.tsv` stays at **236** — it's a name swap on two lines
(`image list`→`image ls`, `backup list`→`backup ls`), not an addition or removal.

### `delonix system resources` — the flags this host accepts and ignores

`system info` used to say `cgroup2 delegated: yes`. **Which** controllers, it didn't say
— and that's exactly where a whole class of silent failures lives: a `--cpuset-cpus`
or an `--io-max` on a host without those controllers is read, accepted, and
ignored, the container runs with no ceiling at all, and nothing anywhere says so.

The new command answers three questions at once, because answered separately they're worthless:
how much there is, how much can actually be enforced, and what is under strain right now.

```
$ delonix system resources
control — what the engine can actually enforce here
  mode                rootless
  cgroup base         /sys/fs/cgroup/user.slice/user-1000.slice/user@1000.service/dlx-containers
  cpu       enforced  --cpus, --cpu-weight
  memory    enforced  --memory, --memory-swap
  pids      enforced  --pids-limit
  cpuset    IGNORED   --cpuset-cpus, --cpuset-mems
  io        IGNORED   --io-weight, --io-max

pressure — share of time some task was stalled (avg10 / avg60 / avg300)
  cpu         0.00% /   0.01% /   0.03%
  memory      0.00% /   0.00% /   0.13%
  io         19.04% /   5.01% /   2.68%   ← the bottleneck right now

4 flag(s) are accepted and silently ignored on this host: --cpuset-cpus --cpuset-mems --io-weight --io-max
```

Three things it does that a naive reading wouldn't:

- **It reads the controllers at the delegation boundary, not at the current cgroup.** In a
  graphical session the current cgroup is an `app-*.scope` offering only `memory pids`,
  while the `user@<uid>.service` two layers up offers `cpu memory pids`.
  The engine escapes to that boundary before creating anything at all, so
  reporting the scope's view would list a missing `cpu` that's never actually reached.
- **It only names a bottleneck above 5% stalled time.** On an idle machine
  all three numbers sit near zero, and whatever wins by 0.01 means
  nothing — calling it a bottleneck would be a lie with a number next to it.
- **It never sends anyone chasing a fix that doesn't exist.** `io` is not a
  delegation this host forgot to grant: systemd doesn't give it to an
  unprivileged user, period — no rootless engine, this one, podman, or
  docker, writes `io.max`. For I/O ceilings the path is running the node as root.

`-o json` for a capacity dashboard or a gate. It's read-only: it writes
nothing, anywhere.

#### The advice is code, with stable identifiers

`system resources` doesn't just show numbers: each finding has an id
`DLX-RES-nnn` that survives a rewrite of the text, a severity, and a **class**.

```
findings
  DLX-RES-001   2 flag(s) are accepted and silently ignored: --cpuset-cpus --cpuset-mems
                → sudo delonix system setup --delegate, then log out and back in
  DLX-RES-003   no aggregate ceiling: one workload with no --memory can take the whole host
                → run the node as root for delonix.slice, or set a per-container --memory
  DLX-RES-002   --io-weight and --io-max cannot apply: systemd never delegates the io
                controller to a rootless user
```

The three classes exist for the gate, not for decoration: `config` and `capacity`
describe something stable one can act on, and `--strict` exits with a non-zero
code in the face of either; `load` describes **this minute** and never
fails anything — a gate that goes red because someone ran a build
teaches everyone to ignore it. That's why chronic pressure (avg300) and a
spike (high avg10, low avg300) are different findings, with different ids.

Notice `DLX-RES-002`: it's the only one with no action. `io` is not a delegation
someone forgot to grant — systemd doesn't give it to an unprivileged user,
and no rootless engine writes `io.max`. Telling the operator to run `system setup` over
that would be sending them chasing a fix that doesn't exist.

#### `resources.get` in the MCP, and the verdict on running the model here

The same pure function serves the MCP. An agent and the CLI give exactly the same ids
over the same machine — if they diverged, whoever read both would have no way to know
which one was lying.

And the server answers a question an agent running on this machine should
ask first: **should this machine be running the model that's reading this?**
The verdict is measured arithmetic, not opinion:

```json
"local_inference": {
  "verdict": "marginal",
  "largest_model_b_q4": 10,
  "reasons": [
    "this GPU also drives a display: a model that fills its VRAM makes the desktop stutter…",
    "10 GiB already swapped out — CPU offload would swap, and swapped inference is unusable"
  ]
}
```

The sizing is anchored on a number anyone can confirm — an 8B
model at `Q4_K_M` takes ~4.7 GiB — and counts what almost everyone forgets: **the
context isn't free**. In this card's 7581 MiB free, a 10B model fits
with 8k of context, and only an 8B model fits with 32k. A model that "fits"
without counting the KV cache is a model that dies mid-response.

It refuses with a written reason when there's no usable GPU, when there's no CDI
spec (the container would never reach the card), or when not even a 7B model fits
— below that, the model fills a template but doesn't weigh a trade-off.

#### `delonix system regulate` — giving the CPU back to whoever's waiting

The deterministic half. It reads the pressure, finds the load that **causes** it,
cuts its `cpu.weight` in half, and gives it back when the contention passes.

**The cause, not the victim.** High pressure *inside* a container means that
container is being starved — it's the victim. The cause is whoever consumes the most.
Throttling "whoever is waiting the most" would punish exactly the wrong
load, so the target is picked by consumption share, measured across two
samples (`usage_usec` is a counter since the container started; a single
reading only says who spent the most CPU since last Tuesday).

**Only `cpu.weight`, on purpose.** It's a share, not a ceiling: with nothing
to compete against, a throttled load still has the whole machine. Nothing
is killed, suspended, or limited. `memory.high` would be the obvious second button and
it's left out by decision: set wrong, it traps a database in permanent
reclaim, and that deserves a design of its own.

Two watermarks in two windows (25% over 10s to act, 5% over 60s to
restore) because with only one the regulator throttles and restores the same
load on every tick. And recovery **beats** a new spike: without this, a build costs
some load half its share until the node reboots.

Proven under real contention — 48 processes burning CPU inside a container, with
the host at 95% stalled time:

```
cpu stalled 95.0% over 10s, 46.4% over 60s · 3 workload(s)
  reg-burn               100.0%  cpu.weight 100
  oqsi-e2e-server          0.0%  cpu.weight 100
  kaeso-db                 0.0%  cpu.weight 100
  throttle reg-burn: cpu.weight 100 → 50  [applied]
    cpu stalled 95.0% over 10s and this workload is taking 100% of the engine's cpu time
```

It picked the cause, left the two victims alone, stepped 100 → 50 → 25 → 20 and
stopped at the floor. Restoration was proven in the reverse direction, with the event in the log.

That run found a defect no test was catching: the container
died while throttled before the minute settled, and the **memo outlived it**. Now
memos for loads that no longer exist are swept on every tick.

Nothing changes without `--apply`.

#### `scripts/advisor_eval.py` — choosing the model with numbers

Choosing a model to read a host's state was being done by
opinion. This is one of the rare cases where the right answer is **computable**: the
`bottleneck()` and the `DLX-RES-nnn` findings are deterministic, so there's an
answer key, and a model that doesn't match it doesn't qualify — whatever its benchmarks say.

Seventeen synthetic hosts cover the decision space, and each one's ground truth is
**computed by the real rules, never hand-written**: a hand-written
expectation is a second implementation of the rules, and the day the rules
change it becomes a lie a green test defends. Changing a threshold without
regenerating the goldens fails the test, in the same commit.

```
DELONIX_UPDATE_FIXTURES=1 cargo test -p delonix-runtime --test advisor_fixtures
scripts/advisor_eval.py --backend ollama --model qwen3:8b
scripts/advisor_eval.py --backend stub      # proves the harness with no model at all
```

It measures, in order of importance: **valid JSON** (an advisor that returns
prose doesn't wire into anything — anything below 100% is disqualified),
**correct bottleneck**, **correct findings** (Jaccard over the `id:subject`
pair), **invented findings**, and p50/p95 latency. Invented findings count just as much
as correct ones: a model that finds problems on a healthy host
teaches the operator to ignore it.

Two pairs in the corpus exist only to separate who understood from who memorized:

| pair | what it separates |
|---|---|
| `io-bound-chronic` vs `io-spike-transient` | the same bad instant, five different minutes |
| `memory-thrashing` vs `swap-used-but-calm` | 10 GiB in swap on a calm host is **health**, not a problem |

And the corpus has a gate against itself. The first version gave **69%**
to whoever always answered "nothing" — nine of thirteen hosts were calm, and a
ranking where silence scores 69% doesn't separate a good model from a mute one. A
test now measures the trivial response and refuses a corpus where it scores above 60%; today
it scores 53%, and that's the line the report prints next to any
score.

`--backend openai` speaks the `/v1/chat/completions` dialect, which any
vendor serves. The end user picks their own model and their own vendor;
this only tells you how much the choice costs.

#### The aggregate ceiling now exists in rootless

`delonix.slice` is `/sys/fs/cgroup/delonix.slice` — a **root** path. And
rootless is this engine's default mode, so until now the aggregate budget
simply **didn't exist where most installs run**. Two consequences,
both measured: a load with no `--memory` could take the whole host, and
the thermal governor was lowering the `cpu.max` of a cgroup that wasn't there.

The answer already existed and was being ignored: in rootless, the delegated base where
the engine creates leaves (`<user@uid.service>/dlx-containers`) **is** the common parent of
all the loads. Putting the ceiling there needs no new privilege or
new path — it's the same directory where the leaves already live.

Measured on this machine, after the change:

```
memory.max   27878420480     (85% of 30.5 GiB)
cpu.max      2720000 100000  (27.2 of 32 cores)
pids.max     131072
```

Three things this unlocks:

- **`DLX-RES-003`** ("no aggregate ceiling") stops appearing, because it stopped
  being true;
- **admission** (`admission_check`) stops bailing out just because it's rootless — it now
  bails out only when there's no delegation boundary at all, which is a different case;
- **`system thermal`** no longer requires root. Proven live: at 85 °C it lowered the
  engine's ceiling from 27.2 to 21.8 cores, with no sudo.

Where there's no boundary — an SSH session, which is a **sibling** scope of
`user@<uid>.service` and not a descendant — the response is `None` and the command
refuses, saying so. Writing a ceiling to a place the engine could never move
a container into would be worse than having no ceiling at all.

#### `doctor` stops having a second hidden list

`system doctor` used to say "every prerequisite holds" on a host where two flags
were being accepted and ignored — because that list lived in another command. Two
lists of problems about the same host, in two places, is how an operator reads one
and misses the other, and `doctor` is what you run when something's wrong.

It now shows resource findings, from the **same** rules, and only the
stable classes: `doctor` answers "can this host do what the engine
promises", and this minute's pressure isn't an answer to that question. `--strict`
now also fails on them.

#### The regulator gains memory — and never `memory.max`

The second half of `system regulate`. Only `memory.high`, and the distinction isn't
stylistic: `high` pushes a load above the line into aggressive reclaim and
slows it down; `max` kills it. A regulator that can kill a database because
a five-minute average crossed a threshold isn't a regulator, it's an incident.

**Two decisions, two culprits.** The biggest CPU consumer is rarely the biggest
memory holder, so the planners are kept separate, and each observation
credits **one** decision per resource. Proven under real pressure on this machine —
39.2% stalled time on memory, with CPU at 0.1%:

```
stalled: cpu 0.1%/0.3%, memory 39.2%/35.4% (10s/60s) · 2 workload(s)
  oqsi-e2e-server          0.2% cpu  648.7 MiB mem  cpu.weight 100
  kaeso-db                99.8% cpu    2.7 GiB mem  cpu.weight 100
  throttle kaeso-db: memory.high 2.7 GiB → 2.4 GiB  [would apply (use --apply)]
    memory stalled 39.2% over 10s and this workload holds 81% of the engine's memory
```

Note that `kaeso-db` has 99.8% of the CPU and was **not** throttled on CPU: at
0.1% stalled time there's no contention at all to resolve. It's the same principle
already in place — 90% of CPU on a machine where nobody's waiting isn't a
problem.

The squeeze targets **90% of what the load uses right now**: a nudge toward
reclaim, not a cliff. The load keeps what it has and only pays for growing, which is
exactly what `memory.high` is for. Never below 128 MiB, and never
twice on the same load — whoever is already squeezed is excluded, or a single sustained
event would drive it to the floor in four ticks.

One memo per **pair (load, button)**, not one per load: a load can be
throttled on CPU and on memory at the same time, and a single file would make the second
claim overwrite the first — one of them would never come back. Restoring memory
writes the literal `max`, not a number, because a number would still be a
ceiling. A `memory.high` a human set by hand has no memo and is **never**
touched.

#### First measurement of a model: `qwen3:8b` loses to silence

The harness existed and had never seen a model. Now it has.

```
model qwen3:8b · ollama · 17 cases
  valid json        100%
  correct bottleneck 47%     (the trivial response scores 53%)
  findings (jaccard) 0.32    (the trivial response scores 0.35)
  invented              5
  latency p50/p95   7.0s / 9.7s
```

It passes the hard gate — **100% valid JSON**, and an advisor that returns prose
doesn't wire into anything — and then **loses to whoever always answers "nothing"** on the two
metrics that matter.

The why is in the cases, and it's a single failure mode:

| where | result |
|---|---|
| hosts **under contention** (chronic cpu/io/memory, spike, no PSI) | 8 of 9 correct |
| **calm** hosts (healthy, swap-but-calm, the three GPU variants, full disk) | 0 of 6, and it invented findings on 5 |

**The model can't say "nothing's going on".** It's the worst possible
property in an advisor, because it's exactly what teaches an operator to
ignore it — and it's why the calm hosts are in the corpus. Without them,
this model would have scored ~89% and looked excellent.

Three things this number is **not**: it is not a verdict on Qwen3 (the prompt
was not tuned, and the harness still doesn't separate the model's fault from the
prompt's fault); it is not a measurement of GPU speed (it ran on **CPU** — the
Ollama server on this machine had no CUDA libraries, and the card was free the
whole time); and it is not a comparison (one model, one prompt, temperature 0, one run
per case).

The harness gains `--think`, off by default. Reasoning models emit
a thinking block before the answer and it dominates latency — and here the
numbers come from a fixed table, not from a reasoning chain, so the block is
spent on nothing. With it on, the same question took three times as long.

#### `system resources` now looks inside each load

The host findings answer "can this host enforce anything at all". The
next question is different, and on a mixed host it has a different answer: **"and the
ceiling I asked for — did it hold?"** A load started before a delegation was
fixed keeps running without the limit it asked for, and nothing said so.

Proven live — a load asking for a `--cpuset` this machine can't
enforce:

```
workloads — what each asked for, and its own stall (10s cpu/mem/io)
  wl-probe                 0%    0%    0%
      --memory        256M      in force
      --cpus          0.5       in force
      --cpuset        0-1       IGNORED   controller not delegated — the flag was accepted and ignored
```

The comparison is against **what the engine would actually have written**, computed by the
same converters the boot path uses — not by a second understanding of
"what `--memory 512M` means in cgroup terms". A second
implementation would drift, and the first sign of that drift would be this report
calling a correct host biased.

And each load carries **its own** pressure. The `io` one shows up even where the
`io` controller isn't delegated: the kernel counts the stall whether anyone
can limit it or not. In rootless, it's the only honest answer to "who's waiting
on the disk".

#### Four flags the advice named don't exist

Measured on 2026-08-31: `--memory-swap`, `--pids-limit`, `--cpuset-mems`, and
`--io-max` are Docker's spelling. This engine has `--cpuset` and the
`--device-*-bps/iops` family, and `pids` has **no flag at all** — the ceiling is a
cgroup property, not a `container run` one.

So `system resources` had been telling operators to stop using
flags they can't write. Nothing could catch it: they're string literals in another
crate, and the compiler has no opinion on the inside of a string. Now a test walks
the `clap` tree and rejects any name that doesn't actually exist — one more
that fails if any of the four Docker spellings
reappears without being added to the map in the same commit.

#### The regulator gets someone to start it

It's not a daemon — this engine is daemonless by design, and a resident
process would need its own ADR. It's the other half of the problem: **a
regulator nobody starts regulates nothing.**

```
delonix system regulate --install-timer --interval 60
delonix system regulate --uninstall-timer
```

A `systemd` timer running `--apply --once`. In rootless it installs a
**user** unit — no privilege — and as root it goes to the system. Proven
live: it fired, ran the regulator, logged the decision to the journal, and
scheduled the next one.

```
Aug 31 08:11:11 delonix[…]:   kaeso-db  52.0% cpu  1.7 GiB mem  cpu.weight 100
Aug 31 08:11:11 delonix[…]:   nothing to do
Aug 31 08:11:11 systemd[1775]: Finished delonix-regulate.service
```

`Persistent=false` on purpose: a decision missed while the machine was
off isn't worth recovering — last week's pressure isn't pressure.

### Known limitations

- **I/O is still not regulated**, and that's not our choice: `io` is not
  delegable to an unprivileged user, so there's no knob to turn. What
  exists is visibility, and it's now exposed — each load's `io` pressure
  appears in `system resources`.

#### Findings now speak Portuguese

They didn't, and the reason was structural: the CLI catalogue indexes by the
exact English string, and a `format!("{n} flag(s)…")` produces a different key for
every host. Translating already-formatted text is impossible by construction.

The engine now emits **a template plus data** instead of finished text:

```rust
finding: Message::new(
    "{n} flag(s) are accepted and silently ignored: {flags}",
    &[("n", …), ("flags", …)],
)
```

The template is a `&'static str` literal — so it's a catalogue key — and
the CLI renders it in the user's language. **The engine says what, the CLI decides which
language**, and the engine crate still has no idea Portuguese exists.

```
findings
  DLX-RES-001   cgroup   2 flag(s) são aceites e ignoradas em silêncio: --cpuset
                         → sudo delonix system setup --delegate, e depois sair e voltar a entrar
  DLX-RES-002   io       o --io-weight e as flags --device-*-bps não se aplicam: o
                         systemd nunca delega o controlador io a um utilizador sem privilégios
```

JSON and the MCP always keep getting **English**: a machine consumer that has to
guess a field's locale is a consumer that breaks whenever
someone changes the shell. For machines, the key is the `id`.

And `action` went from an empty `String` to `Option<Message>` — "there's nothing to
do" stopped being written as "the action is the empty string", which was the same
thing said in a way nobody notices.

### Known limitations
- **Memory's `--apply` wasn't exercised against a live container.** The decision
  was proven under real pressure, and the write-and-restore mechanics by tests with
  real files; squeezing someone's database to put on a
  demonstration wasn't proportionate.
- **One model measured, and on CPU.** `qwen3:8b` ran entirely on CPU because this
  machine's Ollama server had no CUDA libraries; that affects latency,
  not accuracy. No second model, and no GPU run.
- **The prompt wasn't tuned.** A low score can be the model's fault or the
  prompt's, and the harness still doesn't separate the two — the next step is
  varying the prompt with a fixed model.
- **The corpus hosts are synthetic.** Real captures of a machine only
  occupy one corner of the space (this one would only produce "rootless, cpu memory pids, at
  rest"), but the harness reads any file the same way — the output of
  `delonix system resources -o json` fits right alongside these.

## CLI restructuring, blocks B1 and B3 (slice 1) — identity, diagnostics, and a local preference

Direct continuation of the plan in `docs/discovery/52_CLI_PLANO_MIGRACAO.md`. B1 closes
the addressable identity of the two Kinds that never had a persisted document
name; B3 (slice 1) adds four cheap pieces — the mechanism already existed,
only the surface was missing.

### B1 — `get`/`describe`/`delete` now reach `NetworkRoute` and `NetworkPolicy`

`NetworkRoute` (`<from>-><to>`) and `NetworkPolicy`/`FirewallPolicy` (`<target>/<direction>`)
had no identity of their own anywhere — the record, where it exists, only knew the
pair or the (target, direction). The generic verbs require a NAME, and they now answer to
that identity. `get networkpolicies` gained, along the way, the combined listing that
was missing: `net ingress ls`/`net egress ls` only answered for their own direction, one
at a time. `cluster describe` (kind mode) now also exists.

No new CLI verb — the two Kinds still have no native `network route describe`/
`net ingress describe`, only the generic verb was wired up, the same pattern
`kind: Dependency`/`kind: NetworkAccessRule` already followed.

### `delonix diff <kind> <name>` — a resource's three faces, side by side

The 3-way diff engine already existed inside `stack plan` (`desired`/`last-applied`/
`observed`) — what was missing was the surface showing the three faces of ONE named
resource, instead of the whole plan's change list. `delonix diff <kind> <name> [-f <manifest>]`
prints a `FIELD | DESIRED | LAST-APPLIED | OBSERVED` table; `--detailed-exitcode`
follows the same idiom as `stack plan` (0 with no differences, 2 with them). Zero change to
any Kind — it reuses the `desired()`/`actual()` each already exposes.

### `delonix cluster health <name>` — the control plane answers, the nodes are `Ready`

Covers kind-mode clusters only (same boundary as `cluster kubeconfig`/`get
kubernetesclusters` already have). Runs `kubectl get --raw=/readyz?verbose` and `kubectl get
nodes` **inside the control-plane container** — with no need for `kubectl` on the host. Exits
non-zero if the control plane doesn't respond or a node isn't `Ready`: a `health`
that returned 0 on a `NotReady` node would be exactly the dishonest report this repo
is chasing out.

### `delonix system metrics [-o json]`

Another consumer of `delonix-mgmt::dashstats::collect`, which already feeds `dash --json`
and the Prometheus `/metrics` — zero new logic. Returns the raw `DashSummary` (the
counters, for scripts), not the `DashData` shaped for the TUI that `dash --json` already
gives. `system state` wasn't built on purpose: `system info` already answers the same
question, and a second command for the same answer would be the duplication this
project already avoids elsewhere.

### `delonix config get|set|unset` — one preference, one read point

Scope kept narrow on purpose: only the `output` preference (`table`/`json`) is
covered — not `namespace`, which would have a dozen application points instead of
just one, and turns into decoration if nobody actually reads it everywhere. Persisted in
`<DELONIX_ROOT>/config.json`, the same pattern as `delonix_vm::{get,set,clear}_default_
backend`. The only read point is `output::OutputFormat`'s default — every
command with `-o/--output` gets the new behaviour for free, without touching any
other file. `config set output json` changes the default for ANY command with no
explicit `-o`; `config unset output` reverts to the table.

### `delonix secret rotate <name> <key> [--length N]`

Generates a new value for ONE existing key of a secret, without touching the other
keys or the master key (that's still `rotate-key`, a separate command).
Reuses the already-proven `SecretStore::update` wholesale (flock, read-modify-write)
and the name-based resolution that already makes a rotated value apply only on the next
`start`. Refuses a key that doesn't exist — it never creates a new one pretending
it's a rotation — and never echoes the generated value, the same discipline as
`secret create`/`set`. Risk: none (zero new privilege or mechanism).

### `volume ls` gains SIZE/USED BY, `network ls` gains USED BY

Direct user request, read through a DevOps/SRE/platform-engineering lens: a
`volume ls` with no size or consumer forces an `inspect` per volume just to
answer "how much space does this take, and who uses it"; same for networks. Two new
columns in each:

- **`volume ls`**: `SIZE` (the same `measured_usage` as `volumes inspect` — never a
  lying `0` when a mapped subuid directory isn't readable from here: it shows
  the value with a `+` suffix when the measurement is incomplete) and `USED BY` (the
  names of containers whose `Mount.source` points at the volume's `mountpoint`).
- **`network ls`**: `USED BY` (the containers whose `network`/`extra_networks` includes
  the network).

In both cases, `None` (couldn't tell) and `Some(empty)` (genuinely nobody uses it)
are distinct — `?` versus `-` in the table, and in `-o json` the field only disappears in the
first case (`skip_serializing_if` applies only to `None`, never to a genuinely
empty list). Columns with no information at all across the whole table hide
themselves automatically (`Table::drop_uninformative`).

### `pod`/`secret`/`image`/`container`/`cluster ls` gain six more columns

Continuation of the same request — the DevOps/SRE/platform-engineering lens applied
to the rest of the `ls` commands:

- **`pod ls`**: `AGE`, from the `created_unix` of the oldest member (a pod has no
  creation time of its own — it's derived from the containers that make it up).
- **`secret ls`**: `AGE` (`updated_unix`) and `USED BY` — the same
  `None`/`Some(empty)` distinction as volume/network, against `Container.secrets`.
- **`image ls`**: one row per TAG instead of just the first (a multi-tag
  image used to hide the others), and `ORPHAN` (zero containers reference it).
- **`container ls`**: `RESTARTS` (from the event log) and an opt-in `SIZE`
  column (`-s/--size`) — the container's own write-layer space,
  never the shared image layers; off by default because it's a
  per-container directory walk, the same cost `volumes inspect`
  already pays instead of charging it on every listing.
- **`cluster ls`** (kind mode): `K8S VERSION`, read from the control-plane node
  image's tag (`kindest/node:v1.34.0…`) — the actual version running, not the one
  `kubeadm init` was told to expect. Namespace filtering was left out: `cluster
  create` has no `--namespace` at all today, and adding one is a larger, separate
  scope.

**A real security bug, found while validating `ORPHAN`**: `image remove`
never matched a container created with the image's BARE name
(`container run alpine ...` records `image: "alpine"`, which never matched a
`repo_tags` entry like `"alpine:latest"`) — `image remove alpine:latest`
silently unmarked an image a live container still depended on.
Fixed by normalizing through the same `normalise_tag` that `ImageStore::resolve`
already uses, shared between `cmd_rm` and the new `ORPHAN`. Confirmed live: before
the fix, `remove` succeeded with the container still pointing at the
image; afterward, it correctly refuses.

## v1.1.0 — admission becomes a single point, and the engine gains a surface for agents

Two new surfaces and two bugs that let work run outside where it should. It is MINOR
and not PATCH because new commands are added; and it is not MAJOR because the
three subcommands that leave (`storage dash|inspect|rm`) are in the group that
[`cli-stability.md`](../cli-stability.md) has declared **not stable** since it existed.

### `delonix-security-runtime` — admission no longer has a VM-sized hole

Until now, `policy::enforce` had **exactly one caller**: the container path.
`cmd/vm.rs` had none. A node that wrote

```json
{ "denyPrivileged": true }
```

refused `container run --privileged` and **accepted** `vm create --device
0000:01:00.0` — VFIO passthrough, which gives the guest DMA to the host's hardware,
and is a wider hole than the one it was refusing. It also accepted
`vm create --url-img https://any-site/x.qcow2`, whose own help admits that
without a `.sha256` published alongside it, the download is trusted on TLS alone.

`delonix-security-runtime` is the decision, and only the decision — policy, admission,
event, score, and secret redaction. Three dependencies, no sensors, no
daemon, no privileges. The VM path calls it **before** resolving,
downloading, or writing anything. See [ADR-0026](../adr/0026-security-runtime-decision-crate.md).

**Nothing starts being refused on upgrade.** The VM rules are NEW fields,
all off by default:

| field | refuses |
|---|---|
| `denyDevicePassthrough` | `vm create --device` (VFIO PCI) |
| `denyLatestVmImage` | a VM disk image with no tag or `:latest` |
| `allowedImageUrlHosts` | `--url-img` from a host outside the list |

Silently extending `denyPrivileged` to VMs would have closed the hole by breaking
nodes already running. Instead, the node **points at the half you left
open** — by name, with a stable identifier, on the path where you can act, once
per command, and silenceable with `DELONIX_POLICY_LINT=0`:

```
warning: runtime policy [POLICY-VM-PASSTHROUGH-OPEN] this node refuses containers
`--privileged` but allows `vm create --device` (VFIO PCI passthrough)…
```

Every refusal leaves a line in `events.jsonl` with `kind: security` and a
stable identifier (`ADM-DEVICE-PASSTHROUGH`, `ADM-IMAGE-URL-HOST`, …).
Alert on the identifier, not the text.

Operator guide: [`docs/guia-politica-de-seguranca.md`](../guia-politica-de-seguranca.md).

### `delonix mcp` — a local surface for AI agents

`delonix mcp serve|doctor|capabilities`: an MCP (Model Context Protocol) server
for an agent to discover, inspect, and — with explicit `confirm` on anything above
`SAFE_WRITE` — operate this engine, **without becoming a bypass around it**.

Deliberately narrower than the original request: **no OAuth/OIDC, no
`tenant`/`project`/`environment`, no remote HTTP**, per
[ADR-0010](../adr/0010-remote-management-api.md) (the remote management API was
refused) and [ADR-0003](../adr/0003-capability-model.md). stdio only in this pass.

### Two bugs that put work in the wrong place

**An `exec` right after a `run -d` could run on the HOST's filesystem.**
It was reported as «exec writes to the rootfs instead of the volume»; measurement
said worse — it wasn't the wrong destination *inside* the container, it was **outside
it**. 3 of 12 runs landed on the host and two created real files in
the host's `/tmp`, with exit 0. On the detached path, `spawn` returned before init
did `setup_rootfs`, and `exec` did a `setns` into a mount namespace that wasn't yet
the container's.

**The CRI's `exec` killed by pid number.** The server spawns a child per
session and kills it when the client disappears. It stored the NUMBER: while the child
is a zombie the number is held, but whoever waits for it reaps it — and reaping is
exactly what frees the number for another process. Switched to `pidfd`.

### What stops being silently accepted

`kind: Ingress` read three fields and discarded them without saying anything. In all
three cases the engine served or routed something **different** from what the
document said — which is worse than refusing the field, because the manifest
looks applied. `tls[].hosts` is the example: the proxy serves ONE certificate and
does not do SNI selection, so whoever wrote two hosts got the same certificate for both.

### Messages

- **Nine errors said "does not exist" about things that exist.** The pattern was
  `fs::read(p).map_err(|_| NotFound(...))`: right for `ENOENT`, a lie for a
  permission denied, an I/O error, or a broken mount — and the operator would go
  `ls` a file that was right there.
- **Eight operator-facing messages carried the source file's indentation along.**

### CLI

`storage dash|inspect|rm` collapse into `volume` — they were genuine duplicates,
measured field by field. `storage create|ls` **stay** (`create` has no
generic equivalent; `ls` filters to network drivers and shows the `DEVICE` column).
`volume inspect` gained `device`/`options` so the only
information that only `storage inspect` gave isn't lost, and `volume rm` now
clears the vault credentials unconditionally, closing a gap that existed.

`sharevolume` was measured and **nothing was cut**: the five subcommands have genuine
capability gaps against the generic verbs. It's a measured result, not an
oversight.

### Known limitations

- **`delonix-security-runtime` watches nothing at runtime.** It decides at
  admission, and nothing else: no eBPF sensors, no file-integrity
  monitoring, no malware, no ransomware behavioral detection, no response
  engine. All of these need a resident process, and this engine is daemonless by
  design.
- **`events.jsonl` is operational signal, not proof.** It is *best-effort* by
  design, does not detect its own failures, and anyone with write access to the
  state root can edit it.
- **The three VM guards are born off.** Whoever upgrades without reading anything
  gets the warning, not the protection — it's the deliberate price of not breaking
  running fleets.
- **`delonix mcp` is stdio-only, local, with no notion of tenant.** A fleet
  control plane for agents is PaaS matter, not this repo's.

## v1.0.0 — the top-level shortcuts leave, the rest of the contract stays as it was

`v1.0.0` is the first stable release of the Delonix Engine: from here on
`docs/cli-stability.md` is a semver contract, and a break only ships in a major.
It gathers everything built during the development phase (the `v0.x` series, from
16 July to 29 August 2026), which stopped being published as standalone releases.
That phase's summary is in the "What 1.0 brings" section further below; the
full text of each `v0.x` version is in
[`docs/releases/archive/v0.md`](https://github.com/angolardevops/delonix-runtime/blob/main/docs/releases/archive/v0.md).

This is the release that closes the "major" block of the CLI restructuring
(`docs/discovery/52_CLI_PLANO_MIGRACAO.md`, B8+B9). It is the first published
contract break since `docs/cli-stability.md` has existed — hence
`1.0.0`, and not another `0.x`. It is also the dedicated migration note this
plan required for this block.

### What leaves

The six top-level shortcuts — `ps`, `run`, `exec`, `logs`, `rm`, `images` — were
argv rewrites to `container <verb>`/`image list`, and were
**declared stable**. They're gone. A clean cut, no alias: the old spelling
fails with `unrecognized subcommand`, never silently — the same rule the
v0.30.0 reorganization already followed.

| old | new |
|---|---|
| `delonix ps` | `delonix container ps` |
| `delonix run` | `delonix container run` |
| `delonix exec` | `delonix container exec` |
| `delonix logs` | `delonix container logs` |
| `delonix rm` | `delonix container rm` |
| `delonix images` | `delonix image list` |

All other commands, flags and the semantics inside each group remain
exactly the same — only the top-level spelling disappears.

### What does NOT leave, despite the original plan asking for it

Plan block B8 also asked to collapse `delonix workload` "for consistency" with
the shortcuts. It didn't leave. `workload` (ADR-0002) is a deliberate surface —
real disambiguation between a container and a VM that share a
name (`delonix container` or `delonix vm` directly, if we know which one it
is). It isn't a duplicate: `get`/`describe`/`delete` answer by Kind,
`workload` is the only path that crosses Container+VM by name. Cutting it
needs a successor ADR that names the loss — a plan line isn't
enough, and the same discipline already applied to B4–B7 ("only cut what is truly
duplicated").

### Exit codes don't change

Plan block B9 asked for `2→64`, `4→66`, `5→73`. Measured against the current
code: `cmd/exitcode.rs` already has a closed design, exhaustively tested
and aligned with LSB/`systemctl` (`3`=won't run, `4`=doesn't exist, `5`=conflict) and
`sysexits.h` (`69`/`74`/`77`/`124`) — built AFTER the B9 text, and
the module itself already evaluates and rejects the literal request: `Error::Invalid`
is used in 643 places for two classes the proposal separates (invalid flag
vs invalid manifest), and remapping would require splitting that variant
first — new engineering, not a renumbering. An already-existing test
(`nenhum_codigo_colide_com_uma_convencao_instalada`) already guards exactly
the collisions B9 feared. **Nothing changes in the exit codes in this
version** — anyone who wrote automation against the published table has nothing
to update.

### What v1.0.0 means from now on

`docs/cli-stability.md` stops being "the list of what's committed within
0.x" — it becomes the project's semver contract. A break like this one
no longer fits inside a `1.x`.

Found while measuring: the document itself promised `image rm` as stable —
dead since B2 (`image remove`, no alias, nobody noticed). Fixed in the
same window.

### Also in this window

"Delonix Runtime" in the surfaces the user sees running
(`--help`/`--about`, `system info`, the man page, the
`Platform`/`OperatingSystem` fields of `serve docker-api`) now says "Delonix
Engine" — that's the public brand; the repository name and the internal
doc-comments stay "Delonix Runtime" on purpose.

| | value |
|---|---|
| leaves in v0.67.0 (before B4) | 247 |
| leaves in this tag | **235** |
| leaves of the spec (final target) | 103 |

### BREAKING — a bare `run` no longer shares the host's network

Until `0.1.2`, `delonix run <image>` with no `--net` put the container on the
**host's** network namespace. It now gets **its own**, with an outbound uplink,
at both privilege levels:

- **rootless** — its own netns with a `slirp4netns` uplink, even with no
  published ports. It is the Podman-rootless model, and it is what
  `docker run`/`podman run` already did.
- **rootful** — its own netns wired to a shared `dlxnat0` bridge
  (`10.88.0.0/16`) with NAT egress, the docker/podman rootful model. The bridge
  address is leased from IPAM at `run` and persisted, so a `start` of a stopped
  container comes back on the same one.

`--net host` is how you opt back into sharing; `--net none`, `--net <network>`
and pods are unchanged, and `-p` still adds host port forwards on top. **A
container created before this release keeps the host netns** — the record
predates the field, and `start` reconstructs the mode from the record rather
than imposing the new default on something already running.

If anything of yours reached a service on the host through a bare `run`, it now
needs `--net host`.

**And the declarative side means the same thing**, which it did not when this
change first landed. The default of `kind: Container`'s `network:` stayed `host`
while `run`'s became `private`, so one field meant opposite things depending on
which door read it — the class this engine already paid for once with
`resolve_image_ref`: a string cannot mean two things depending on the entry
point. Measured on 2026-11-22, with an isolated root: a hand-made
`container run -d --name x <image>` against a manifest that declares `x` with no
`network:` planned

```
-/+ Container/x  — does not converge live: network
      network: private → host
Summary: 1 to replace
```

— a REPLACE, which destroys and recreates a container that was already running,
so `stack apply` refused it and the container could not be adopted at all
without `--replace`. The declarative default is now `private` too, and the
published schema (`docs/schema/v1/delonix.json`) carries it.

**What this means for a manifest of yours:** one that does not name a network
changes behaviour. Declare `network: host` to keep sharing the host's netns. A
`kind: Pod` is unchanged — it always builds a netns of its own anyway. One
welcome consequence: a `GitOpsSource` may now declare a container without naming
a network, which the guard used to refuse — that guard exists to keep a
repository off the HOST's network, and an unnamed network is no longer on it.

### The node contract is reachable from outside, with an identity

The node API stopped being a local-socket-only surface. It now serves the
`delonix.node.v1` contract **over TCP with mutual TLS** (ADR-0096), and the
fleet operability slice A2–A6 (ADR-0099) adds enrollment, authorization,
generation, watch and scheduling on top of it — the operations a control plane
needs to drive a node it did not start.

The identity underneath it is **SPIFFE** (ADR-0102, phase H0): the node's
X.509-SVID chain, key and trust bundle become a rustls `ServerConfig`/
`ClientConfig`, so an external authority such as SPIRE can be the issuer with no
product-specific code in the engine. It is a foundation, not a running agent:
there is no resident process and no rotation loop, which is the daemonless rule
applied to identity. `AttestWorkload` is the RPC that goes with it.

### Conformance, measured rather than claimed

- **OCI runtime at the root tier**: the capability model (5 sets), seccomp and
  the stdio plumbing that the validation suite reads, each with the evidence
  recorded — `delonix oci-runtime` goes from 19 to 32 passing assertions, with
  the gap to runc's 53 named case by case.
- **The CNCF compatibility campaign** gets its foundation: `tests/interop` and a
  generated `docs/compatibility` matrix, so the number has a denominator and a
  source instead of a claim.

### The cold start, profiled and then shortened

A per-phase profile of the cold start (ADR-0095) found that `pre_spawn`
dominates — not the mechanics everyone assumed. The **warm plane** that follows
from it keeps pre-loaded runners (binary in memory, stores open, image resolved)
behind an isolated path, with per-image CRI warming and asynchronous refill.

### Docker parity where the CLI was still surprising

`exec` gained `-d/--detach`, `--env-file` and a `--privileged` that raises the
capabilities **for that call only**; `-u` now loads the supplementary groups
from `/etc/group`, and a `-w` that does not exist aborts with rc 126 instead of
silently landing the process in `/`. The positional split was fixed so container
flags written after the image are no longer stolen by the parser — and, in the
same family, a mistyped flag is no longer consumed as the image or the container
name, which used to send a typo to a public registry.

The help is now grouped Docker-style, by command and by flag (#1020).

### Images and VMs

`distroless`-by-default with a labelled fallback, `vm create --distro`, and
`vm logs` with `--capture-serial` plus a lab for centralizing them.

### Supply chain and the gates

`RUSTSEC-2026-0592` (stack overflow in `Url::origin()` on nested `blob:` URLs)
is closed by `url 2.5.9`, and three `deny.toml` ignores that no longer matched
any crate were removed — each had met the exit condition its own comment
described.

The gate drift that had accumulated on `develop` was **paid, not absorbed**:
119 lines of Portuguese prose translated in three measurement reports whose
siblings were already in English, and two counters corrected where they were
measuring the sentence that describes the rule rather than code. The baselines
that moved down were verified to move only for those false positives, by
re-measuring the commit that set them.

### The rootless uplink leaves nothing behind

Giving every bare `run` a netns of its own also gives it a `slirp4netns` of its
own, and that turned a latent leak into one process per container. The uplink
only carried an ownership token — its api-socket — when there were ports to
publish, so a slirp whose supervisor had died could not be claimed by the
reaper, and refusing to claim it was correct: `slirp4netns` is not our binary,
and rootless Podman spawns it with the same argv. Measured on a clean host, a
chaos run left 19 of them alive while the engine's own `net netns down` answered
«ingress DOWN — infra netns torn down»; a day of runs had accumulated 274.

The token is now unconditional, `net netns down` reaps and says how many, and a
`container rm` takes the slirp of a port-less container with it instead of
leaving it for the next teardown. Where `TMPDIR` is long enough that the socket
path cannot fit a unix socket's name, a `-p` is refused — with the length, the
limit and the remedy — rather than started with the port in the record and
nothing listening on the host.

### Upgrading

Nothing in the state directories, sockets, systemd units, `DELONIX_*` variables
or the `*.delonix.io` schema groups changes. The one thing to check before
updating is the network default above: if a workload of yours talked to the host
through a bare `run`, add `--net host`.

## v0.1.2 — zero-vuln supply chain, VFIO/platform hardening, and CLI parity

Second fix-and-consolidation release on top of `v0.1.0`. It is a **patch** under the
line policy (see [VERSIONING.md](https://github.com/ngolacloud/delonix/blob/main/VERSIONING.md)):
the CLI, API, JSON, and schema surface is **additive** relative to `0.1.1`. The only
exceptions are **deliberate security hardenings** (VFIO passthrough and
the platform base) that now **refuse** what used to be permissive — more
restrictive, never less safe. Whoever is running `0.1.1` updates with nothing changing,
unless they depended on a passthrough outside the new allowlist.

The prose notes were written from the measured history (`git rev-list
--count v0.1.1..<tag>`); the section-categorized summary is in
[CHANGELOG.md](https://github.com/ngolacloud/delonix/blob/main/CHANGELOG.md).

---

### A zero-vulnerability supply chain

The dependency tree was reviewed in three phases, taking `cargo audit` from
**8 vulnerabilities to 0**:

- **Phase 1** — maintenance within the *caret* range (`cargo update`), adapting to
  constants removed from recent `libc`.
- **Phase 2** — sovereignty: `serde_yaml` moved to `serde_norway` (with no change at the
  call sites) and unmaintained crates left the tree.
- **Phase 3** — `ratatui` 0.29 → 0.30, which eliminates the *unsound* `lru` and `paste`.

No observable behavior change — just less third-party surface and
less supply-chain risk.

### Security hardening

- **VFIO passthrough (V3-V5):** device passthrough now has an
  **allowlist**, failures are no longer **silent**, and raw XML goes through
  a *gate* before reaching the hypervisor.
- **NgolaCloud platform base (W1-W4):** hardening accompanied by a
  VM and storage audit, so that delonix serves as a reliable base for the
  platform.

### CLI parity with Docker/Podman

- **Per-layer** `pull` progress, docker-style.
- **Logs** captured on *foreground* runs (previously only with `-d`).
- **TTY** forced on `run` and `--disk-size` on `vm create`.
- *Preflight* warning when an `EXPOSE` < 1024 is requested on rootless `--net host`.

### Kernel-native axis

First base of the **kernel-native** axis (KRN-0001..0006) and the accompanying
native-ification backlog — the path toward pressing the engine even closer to the
kernel, out of intermediate runtime chains.

### Reproducible `init`

`delonix init` now generates a **reproducible lockfile**, with e2e tests per
stack class and secret generation for the WordPress template.

### Production readiness, documented

The README and the site's *landing page* gain a **"Production readiness"**
section. The dependency review was followed by a **live re-measurement** confirming
no regression in startup, density, and failure recovery
(`reports/production-readiness-2026-11-18/`).

## v0.1.1 — CLI parity, a live Kind catalog, rootful CRI conformance, and supply chain

First fix-and-consolidation release over `v0.1.0`. It is a **patch** under the
line policy (see [VERSIONING.md](https://github.com/ngolacloud/delonix/blob/main/VERSIONING.md)):
everything that lands is **additive** — new subcommands, Kinds that become
*live*, conformance and hardening — **with no contract broken** for CLI, API,
JSON, or schema from `0.1.0`. Whoever runs `0.1.0` upgrades without changing
anything.

The prose notes were written from the measured history (`git rev-list
--count v0.1.0..<tag>`); the categorized summary by section is in the
[CHANGELOG.md](https://github.com/ngolacloud/delonix/blob/main/CHANGELOG.md).

---

### CLI parity with Docker/Podman

The set of imperative verbs moves closer to what a Docker/Podman user
expects, without changing the declarative surface (`kind: *`):

- **Volume:** `volume export/import/mount/unmount` and `volume exists/prune`.
- **Network:** `network reload`, `network prune`, `network exists`.
- **Container:** `container export/mount/unmount/clone/checkpoint/restore`.
- **Image:** `image build/diff/tree`, `image search`, `image import`,
  `image history`, `image untag` — plus the root-level shortcuts `search`,
  `import`, `export`, `history`, `untag`.
- **Pod:** `pod ps/exists/prune/kill/pause/unpause/stats/top/inspect`.
- **Actionable root-level shortcuts** for `buildx`/`builder`/`bake` and
  `checkpoint`.

The **imperative vs declarative** boundary stays intact: `container …` is
the imperative surface; declarative containers live in `kind: Pod`, and
`delete …` correctly refuses imperative objects.

### Live Kind catalog on the restructured engine (ADR-0086)

The Kind catalog was ported to the restructured engine and several Kinds
moved from declaration to **real convergence**:

- **`kind: Config`** — the plaintext sibling of `Secret`.
- **`kind: IPAddress`** — a reservation out of an `IPPool`.
- **`kind: Snapshot`** — a convergent snapshot of a `VM` or `Volume`.
- Catalog v1 **and** v2 now sit on ADR-0086's clean layering structure.

### Rootful CRI conformance

- **Bidirectional `rshared` mount propagation** (ADR-0093).
- **Per-pod PID namespace** with a dedicated `pause` anchor (ADR-0092) and
  **shared-PID** on the root-CNI path.
- **AppArmor** `localhost/…` normalization and **seccomp** with explicit
  opt-in.

### Supply chain and CNCF value areas

- **in-toto attestations** attached to the image: **SLSA v1 provenance** and
  **SBOM** (SPDX), published via the **OCI 1.1 Referrers API** with a
  *fallback* to the `sha256-<hex>` tag scheme.
- **`scan --policy` / `scan --compare-to`** and **CI gating** on top of the
  existing OSV + `--fail-on`; **policy-based trust** at signature admission.
- **`cluster kube play` / `kube generate`** — interoperability with
  Kubernetes manifests.
- **`${VAR}` interpolation** in Compose (with `.env` and braces).

### Recovery and supervision

- **`boot.rs`: valid systemd `Restart=`.** Delonix's policy
  (`unless-stopped`/`always` → `always`, `on-failure[:N]` → `on-failure`) is no
  longer written *verbatim* as an invalid specifier that systemd silently
  ignored.
- **`cluster create`: load-aware node wait** — a live node gets a grace
  extension under contention instead of aborting the whole cluster over one
  slow node.

### Hardening (OCI/linux/CRI)

- **OCI whiteout confined to the layer's directory** via a shared
  `scoped_resolve` (closing a symlink escape), and **its own scratch per
  concurrent unpack**.
- Container **placed into its cgroup before the workload runs** (non-userns).
- VM: `move_namespace` records the entry **before** moving the overlay.
- CRI: the *Streamer* **tolerates Mutex poisoning** instead of propagating
  the panic; OOM/cgroup and `clone3`/`cmsghdr` hardening.
- `perf(linux)`: `ldconfig` is skipped on **musl/scratch** rootfs (no
  `ld.so.cache`).

### Measurements accompanying the release (not a contract)

In `reports/` are this campaign's measurements: **CNCF acceptance** (Delonix
vs Docker/Podman, 8 value areas) and **readiness for critical production**
(perf, recovery, CNI parity 6/6 + critest 103/103). They are evidence, not
promises.

## v0.1.0 — Delonix: the first release of the new identity

This release **opens the Delonix line**. The `delonix-runtime` product has been renamed
**Delonix** and the repository moved to `github.com/ngolacloud/delonix`. The version
number was **deliberately re-based** from `5.1.1` to `0.1.0` — a new line, not
a regression (see [VERSIONING.md](https://github.com/ngolacloud/delonix/blob/main/VERSIONING.md)).

**The engine is the same.** Every capability inherited from the `delonix-runtime`
line (v1.0.0 … v5.1.1) stays: rootless-first, daemonless containers and microVMs,
pods, OCI, rootless SDN, VMs (Cloud Hypervisor/libvirt/Proxmox), `delonix-cri`,
`cluster kubeadm`, the declarative Kinds, and the providers. **None of this is new work
in `0.1.0`** — the history is in [CHANGELOG.md](https://github.com/ngolacloud/delonix/blob/main/CHANGELOG.md),
section "`delonix-runtime` line." The `v1.*`…`v5.1.1` releases remain published and
immutable.

### What this release changes

- **Identity:** name, repository (`ngolacloud/delonix`), site
  (`ngolacloud.github.io/delonix`), image (`ghcr.io/ngolacloud/delonix`). The CLI
  binary is still called `delonix`.
- **Version line:** `scripts/version_gate.py` is now line-aware — the
  `delonix-runtime` line (majors 1..5) is frozen and the Delonix line opens at
  `0.1.0`; comparison happens within the line.
- **Compatibility policy (pre-1.0):** while in `0.x`, a *minor* may
  break contracts (announced as `BREAKING` in the CHANGELOG); *patch* is compatible.
  Stabilization to strict SemVer arrives with `1.0.0`.

### What does NOT change (operational contracts)

A `5.1.1` install keeps everything when moving to `0.1.0`: state in
`/var/lib/delonix` and `~/.local/share/delonix`, config in `/etc/delonix`, sockets
`/run/delonix-*.sock`, systemd services, `DELONIX_*` variables, and the
`*.delonix.io` schema groups.

### Updating

See the [migration guide](https://github.com/ngolacloud/delonix/blob/main/MIGRATION.md).
In short: reinstall via `install.sh` (GitHub's "latest" is by date, it resolves
to `0.1.0`); the five binaries (`delonix`, `-cri`, `-mcp`, `-mgmt`, `-node-api`)
all have to stay on the same version. A SemVer-order auto-update does **not** fire
(`0.1.0 < 5.1.1`); it is a line transition, announced.

### Known limitations

- The regenerated documentation already uses the new identity; the *handbook*
  (`docs/handbook/`) has been regenerated. The `oci-runtime` implementation plan
  moved to `docs/discovery/69_RT4_PHASE1_IMPL_MAP.md` (outside the page catalog).
- GHCR images from the previous line stay in the old namespace; starting with this line
  they are published at `ghcr.io/ngolacloud/delonix`.
