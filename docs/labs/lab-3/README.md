# Lab 3 — Two applications that talk to each other by name

> **Identifier:** `lab-3` · **Level:** intermediate · **Journey:** first contact

## Concrete objective

Put two applications on their own **user network** and prove two things
that a network alone does not give you: the app resolves the database **by name** (internal DNS,
no `/etc/hosts`, no variables), and a `kind: Dependency` closes the `db` off
to **everyone except the app** — *directed* reachability. The proof is
functional: the same network, **two outcomes** (the app reaches it, a third party does not).

## Prerequisite knowledge

Linux terminal and a notion of container/network. Lab 1 helps but is not required.

## Tested version and environment

> **Historical baseline (5.1.x line):** the values below were measured on the old line and **have not yet been re-measured on the current 0.1.0 line**.

`delonix 5.1.1`, Linux with cgroup v2, rootless execution. Validated on 2026-10-24
(internal DNS, `kind: Dependency` → `NetworkPolicy` with *default deny*, and the
policy-vs-service distinction confirmed live — positive `EXIT=0`, negative
`EXIT=1`).

## Minimum resources

~140 MiB of disk for `postgres:16-alpine`, `nginx:alpine`, and `alpine`; network
for the first `pull`.

## Required privileges and access

No `sudo`. Everything runs on the rootless user network.

## Estimated duration

~15 seconds once the images are cached (dominated by postgres startup).

## Preparation files

No external files. The `kind: Dependency`'s `dep.yaml` is **generated by the
lab itself** (in the state directory) and removed during cleanup. The harness
lives in this folder:

| File | Phase |
|---|---|
| `prepare.sh` | ensures prerequisites and local images; cleans up leftovers |
| `run.sh`     | runs the journey (network → db+app → DNS → baseline → Dependency → block) |
| `verify.sh`  | asserts internal DNS and directed isolation |
| `cleanup.sh` | removes only what the lab created (containers, network, `dep.yaml`) |
| `lab.sh`     | orchestrator `prepare → run → verify → cleanup` |

## How to run

```bash
# with delonix on the PATH (normal install):
bash docs/labs/lab-3/lab.sh

# pointing at a specific binary (e.g. a local build):
DELONIX=/path/to/delonix bash docs/labs/lab-3/lab.sh

# leave the network and containers up to explore:
bash docs/labs/lab-3/lab.sh --no-clean
```

## Steps (what `run.sh` does) and why

1. `network create loja` — its own network; internal DNS **comes for free**.
2. `container run` of the `db` (`postgres:16-alpine`) and the `app` (`nginx:alpine`),
   both on `--net loja`.
3. The app resolves `db` **by name** (`getent hosts db` → IP) — no config needed.
4. **Baseline** (before the policy): a third container on the same network
   **reaches** the `db`. We first wait for the `db` to open port `5432` (postgres
   warms up slowly), otherwise the baseline would lie because the *service wasn't ready yet*.
5. `stack apply -f dep.yaml` for the `kind: Dependency` (`app` → `db`, port
   `5432`). It compiles down to a *default deny* `NetworkPolicy` applied to the `db`.
6. **After the policy**: the same third party **no longer reaches** the `db`, but
   the app still does. Same network, two outcomes.

## Checkpoints / success assertions (what `verify.sh` requires)

- **A** — `db` and `app` are `Up`.
- **B** — the app resolves `db` to a **valid IPv4** (internal DNS).
- **C** — the **authorized peer** (the app) reaches `db:5432`, with retries. This is the
  anchor that proves the service is **up** — and distinguishes a policy block from a
  `db` that is down.
- **D** — a **third-party** container on the same network is **BLOCKED**. The harness
  **fails loudly** if the third party still reaches it (`db ended up OPEN TO
  EVERYONE` — the failure the lab exists to catch) and also if `nc` is missing from the
  prober (inconclusive assertion, not a false block).
- **E** — the app is a real service: **HTTP 200** on the host's published port.

## Cleanup

`cleanup.sh` removes the `db`/`app` containers, the `loja` network, and the `dep.yaml`. The
`Dependency`'s `NetworkPolicy` lives on the `db`'s firewall and **goes away with it**
(confirmed live) — there is no orphaned policy to clean up separately. It does **not** remove the
images (other labs reuse them).

## Lesson learned

A user network gives you internal DNS for free, but leaves everything inside it open to
everything else. The `kind: Dependency` turns "who shares the network" into "who
has explicit permission": the `db` switches to *default deny* and only admits the `app`. And the
proof is never the exit code of an isolated `nc` — it is the same network producing **two**
outcomes, with the authorized peer as the anchor that the service is alive.
