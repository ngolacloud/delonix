# 66 — NaaS capability matrix (delonix-runtime, measured 2026-10-08)

Read-only survey of this engine's (`delonix-runtime`) native networking capabilities, done
to prepare the technical foundation for NaaS/KaaS/CaaS. Scope: NaaS (network) only. KaaS/CaaS
are left for another survey.

**Measured baseline**: `delonix-runtime` `main` `1cbe9639` (tag `v5.0.0`), worktree
`naas-kaas-caas`. Every state claim below was confirmed in the current code (grep + Read,
file:line or function/test name cited) — the root `AGENTS.md` was used only as a map
of where to look, never as proof; in at least three sections `AGENTS.md` was
out of date relative to the code (see the note at the end of each section where that happened — the
biggest example is that `GatewayProvider`/`NetworkZoneProvider` no longer live in `delonix-sdn`:
they moved to `crates/contexts/delonix-networking` in ADR-0059, F2a/F2c, and `AGENTS.md`
still describes them in the old place).

**Complementary authoritative source**: `docs/providers/capability-matrix.md` (generated by
`delonix provider matrix`, catalog `1.3.0`, **a test fails if this file diverges from the
code** — which is why it is the most reliable source in this repo for "what is proven vs. just
written") and `docs/proxmox/matrix-9.2.2.md` (generated by `scripts/proxmox_api_inventory.py`,
same guarantee). Both are cited extensively below instead of being reconstructed.

States used in the "Status" column (vocabulary of `capability-matrix.md` itself, ADR-0050):
**PASS measured** (`supported`: implemented and exercised — evidence is a battery check, an
E2E section, a chaos scenario, a unit test, or a LIVE test against a real target),
**PASS by reading** (implemented, only unit/read proof — `partial` in the catalog, no
"live:" evidence), **PARTIAL** (implemented with a written limit, or with no proof at all),
**GAP** (`not-implemented`: zero code), **NOT SUPPORTED** (`unsupported-by-provider`: that
provider cannot offer this, by design).

## 2. IPv6 — exact state, re-confirmed directly in the code

`AGENTS.md` documents a CRITICAL finding (v0.37.1, "Block 0 of plan 33"): up to that version, the
SDN assigned an IPv6 ULA address to every container and **the entire firewall was `table ip` — zero
IPv6 policy**, a total bypass of the unprivileged isolation model. I confirmed
**directly in the current code** (not merely in ADR text) that the fix is in place:

- `ipv6_sdn_enabled` (`delonix-sdn/src/infra.rs:3047`) is `false` by default.
- **Layer 1** (per container, at attach time): `disable_ipv6_argv` (`:3151`), executed inside
  `do_attach` (`:3323`) and `do_attach_extra` (`:3420`) — BEFORE any traffic.
- **Layer 2** (holder-wide, covers containers already alive and a privileged one remounting
  `/proc/sys`): `disable_ipv6_live` (`:3096`), `table ip6 dlxing` with `forward policy drop`
  (`:3066`, installed at `:8313`).
- `DELONIX_ENABLE_IPV6=1` is a LOUD escape hatch (`SECURITY WARNING` in the code itself,
  `:3051`), never a default.
- Test: `ipv6_is_refused_on_both_layers` (`infra.rs:10421`) confirms both layers.
- Self-report: `NetIpv6 => UnsupportedByProvider` (`provider_report.rs`) — honest: refused,
  not "degraded" or "partial".

**What does NOT exist**: real dual-stack IPv6 support (addressing, v6 IPAM, DNS AAAA,
v6 anti-spoof). **ADR-0065** designs this (a single `table inet` replacing the `table
ip`+`table ip6` refusal pair, v6 addresses derived from the v4 lease, v6 anti-spoof in the
`bridge` family) and is **`Proposed` (2026-10-02), nothing implemented** — I confirmed by grep that no
`table inet` exists anywhere in the crate, only `table ip` (default) and `table ip6 dlxing`
(refusal). `docs/discovery/66_CONTINUITY_PLAN.md` names it as item 6.2 of Sprint 6, "nothing
implemented".

**Conclusion**: the serious 2026 finding (IPv6 as a total policy bypass) is **closed and
confirmed today** — it is an active refusal, correctly on both layers. What is missing is IPv6 as a
CAPABILITY (not as a security fix), and that is new work, not security debt.

## 4. Provider combinations

**Question**: does the code today allow combining, in a single logical instance, compute on
one provider with networking on a different backend and firewall on a third (e.g.: VM on
Proxmox + the engine's native network + OPNsense firewall)?

**Answer, confirmed directly in the code (not inferred)**: **NO, for the "VM on
Proxmox + the engine's native network" part**, and **YES, in a limited way, for "compute on
a provider + firewall ON THE SAME provider"**.

- **A VM on Proxmox NEVER enters this engine's native SDN.** `net0_arg`
  (`delonix-proxmox/src/lib.rs:1762`) always resolves to the Proxmox node's OWN bridge
  (`vmbr0` by default); `delonix-proxmox` does not import `delonix_sdn` anywhere in code, only in
  comments that explicitly say the opposite ("Not `delonix-sdn`"). There is no mechanism
  equivalent to `vm bridge` (which `delonix-sdn` already has to connect a libvirt VM to the native
  SDN via a privileged veth) for a Proxmox VM. **So "VM on Proxmox + the engine's native network" is
  impossible today.**
- **"Compute on a provider + firewall ON THE SAME provider" EXISTS and is tested**:
  `NetworkPolicy` `scope: vm` (Proxmox VM → the Proxmox node's own firewall, `vm_firewall.rs`) and
  `scope: systemcontainer` (Proxmox LXC → the same node's LXC firewall). Confirmed end-to-end
  (`cmd/firewall.rs:2162-2185`, dispatch by scope) with a LIVE test for both cases. This is not
  "firewall on a third provider" — it is "the firewall of the SAME provider already running the compute".
- **"VM on Proxmox + OPNsense perimeter firewall"**: technically possible IF the network
  topology (outside this engine's control) routes the VM's traffic through the OPNsense appliance
  as a gateway — but **the engine does no automatic orchestration of this**. The
  `NetworkGateway` (OPNsense) is an independent PERIMETER resource, with no programmatic
  link to where compute runs; OPNsense's `GatewayProvider`/`NatProvider` know
  nothing about Proxmox VMs and vice versa (confirmed: zero cross-references between
  `delonix-opnsense` and `delonix-proxmox`). The combination would work only via manual network
  topology set up by the operator (the VM has OPNsense as its gateway outside the engine), not because of
  anything `delonix-runtime` wires up.
- **Native container/VM (libvirt/CH) + native network + OPNsense as egress perimeter**: THIS
  case is fully supported — it is precisely the role of `GatewayProvider`
  (`net.nat.snat`/`dnat`, `net.gateway.filter`) over traffic that already leaves the native holder. It is the
  "native compute + native network + remote firewall" combination that WORKS, unlike the
  combination with Proxmox compute.

**Summary**: the real combination today is "the engine never mixes the Proxmox dataplane with its
own", and within each WORLD (native vs. Proxmox) the firewall follows the compute. The only
genuinely cross-provider exception is native compute + OPNsense perimeter, which is a case
designed on purpose (ADR-0051/0059) and proven live.

## 5. The 3 most serious gaps

### Gap 1 — Proxmox SDN's native vnet firewall: accepts and reads back, but does NOT FILTER anything under Proxmox's default firewall (risk: **security, false sense of protection**)

**What is measured, in the code itself and in a live trace**: `crates/providers/delonix-proxmox/src/sdn_routing.rs`,
module doc-comment (lines 16-44): writing a rule at `.../vnets/{vnet}/firewall/*` is
accepted, appears read back, and **nothing compiles it** when the node runs Proxmox's default
firewall (`pve-firewall`, iptables) — zero lines in `iptables-save`/`nft list ruleset`. It only
filters when the node has `nftables: 1` (`proxmox-firewall`) turned on. Measured with real PACKETS in the
lab (two vnets, a listener on 22 and 23, DROP on 23): under iptables, **23 is open in all
directions** despite the rule being "applied".

**Why this is serious and not just a footnote**: this is exactly the "accepts, reads back,
does nothing" pattern that separates a real firewall from a decorative one — and it happens on the backend this
NaaS program intends to use for multi-tenant VMs/LXCs.

**Measured mitigation, which lowers the IMMEDIATE risk**: I confirmed by grep that `sdn_vnet_firewall`/
`VnetFirewallOptions` **are not called from anywhere outside `delonix-proxmox` itself** —
zero in `bins/delonix-runtime-bin` or `delonix-networking`. There is no `kind:` or `delonix` command
that exposes this to an operator today. It is a tested, correct API client method, but
unreachable by the end user — the SAME shape of "dead public function with no caller, with a bug
waiting for its first consumer" this repo has already paid for 5 times (`mount_live`, `set_net_rate`,
`update_limits`, `publish_port_allow`, `Net`), documented in `AGENTS.md` itself.

**File/function to fix**: `crates/providers/delonix-proxmox/src/sdn_routing.rs`,
`set_sdn_vnet_firewall_options` (line ~1173) and the rule-writing path — add a
guard that probes the node's firewall option (`nodes/{node}/config` or equivalent, the same
pattern as `vm_firewall.rs:353`'s `Error::DatacenterFirewallDisabled`→DX-6508) and refuse the write
with a new error (e.g. `Error::VnetFirewallNotEnforced`) when the node does not have `nftables: 1`.
This guard must land **before** any CLI/Kind exposure of this path, not after.

**Acceptance test**: a live case (alongside
`sdn_routing_chain_vnet_firewall_and_the_lock_round_trip_through_the_node`) that (a) turns off
`nftables` on the node, tries to write a vnet firewall rule, and requires explicit refusal instead
of silent acceptance; (b) with `nftables: 1`, repeats the already manually-done packet measurement
(DROP on port 23, ACCEPT on 22) as an automated check — never `rc==0` without looking at the
real traffic.

**Follow-up (2026-10-09): the guard suggested above is BLOCKED by another decision already made
in this same repository — it is not a line to add.** The field that would decide the guard, the
per-NODE `nftables` option, lives at `/nodes/{node}/firewall/options` — and this repository's `docs/proxmox/
matrix-9.2.2.md` (ADR-0049, generated by an earlier session) already classifies the ENTIRE
`/nodes/{node}/firewall/*` tree as `unsupported-by-design`, reason "node firewall —
host administration" — the same boundary ADR-0049 D3 draws for cluster administration in
general. Reading that field, even just to DECIDE to refuse a write, would widen the
engine's reach beyond a boundary already drawn on purpose for another reason — the same
logic ADR-0064 D6 uses to refuse reusing a DNS controller's credential in another call.

**What was done in this session, without crossing that boundary**: documentation hardening in
`sdn_routing.rs` — a new section in the module doc-comment ("No caller may expose this without
reading this first") that names the impasse precisely and demands an explicit decision from the owner
(an ADR addendum) OR the capability catalog permanently reporting this row as `unavailable-on-host`/
`not-implemented`, before any `kind:`/CLI wires this up — plus a one-line pointer
in each of the three functions (`set_sdn_vnet_firewall_options`,
`add_sdn_vnet_firewall_rule`, `update_sdn_vnet_firewall_rule`). **No behaviour change.**
The acceptance test (a)/(b) above still remains to be done — it needs the owner's decision first, not just the lab.

Also tracked in `docs/discovery/naas-kaas-caas-auditoria-2026-10-08.md` §4.9 and item 6 of
that same section's §3 gap list.

### Gap 2 — DNS records left behind by the Proxmox node at teardown/rename, with no cleanup (risk: **cross-tenant isolation / stale pointer**)

**What is measured**: ADR-0064, D4 ("What the node leaves behind is said out loud") — destroying
a zone with `dns:` leaves the gateway's `A`/`PTR` record (`<vnet>-gw.<domain>`) on the shared DNS
server; D6 ("Cleaning the leaked records") is **"decided and not implemented"**, and also names
a "guest-rename leak" (renaming a guest leaves the old name pointing at the current IP). The existing
live test (`the_dns_provider_registers_a_guest_in_the_zones_dns_server`,
ADR-0064) proves the node WRITES records correctly — it does not prove the cleanup, because it
does not exist.

**Why this is serious**: on a Proxmox cluster shared by several "tenants" (via the control plane),
an IPv4 address reused by ANOTHER workload (possibly of another tenant) may keep
answering to an old DNS name no one removed, or a rename may leave an orphaned name
pointing at the current address of a resource that no longer goes by that name. It is a classic stale
pointer that can silently cross the tenant boundary — exactly the "silent
failure" class this repo's doctrine (guard-rail 6) exists to forbid, and ADR-0064
itself names "Hiding the leaked records" as rejected precisely for that reason, but the cleanup
itself has not yet been written.

**File/function to fix**: `crates/providers/delonix-proxmox/src/dns.rs` — today it has
no record-removal path; it needs a new function that talks to the DNS server
using a credential OWNED by the operator (`providers.yaml`, a `dns:` entry with `url`/`keyFile`
— the decision is already written in the ADR, "never the one the node returns"), called from teardown in
`network_zone.rs` (`remove_zone`/`remove_vnet`), removing only the `<vnet>-gw.<domain>`/PTR
this engine marked as its own (the same `OwnerMark` the rest of the crate already uses).

**Acceptance test**: the live case ADR-0064 itself already names as pending — destroying
a zone (or renaming a guest) against the lab's real PowerDNS and confirming, via a real
DNS query (not by reading the engine's local record), that the old record is gone.

### Gap 3 — `netops::remove`: asymmetric rollback leaves an orphaned `NetDef` on disk when the dataplane removal fails midway (risk: **state loss/inconsistency, availability blocker**)

**What is measured, directly in the code**: `crates/adapters/delonix-sdn/src/netops.rs:88`
(`remove`) deletes the declarative record (`store.remove(name)`) **BEFORE** the dataplane
(`infra::vxlan_remove`/`infra::network_remove`), and both dataplane sides are **best-effort
and swallow the error** (`network_remove` returns `()`, only `tracing::error!`). This is the OPPOSITE of
the order in `create_bridge` (`netops.rs:27`), which has explicit symmetric rollback: if the gateway OR
the dataplane fails, the freshly-created record is removed. `remove` has no equivalent — if
`infra::network_remove` fails midway (e.g.: `netdef_lock()` unavailable), the physical
`NetDef` stays on disk **without** any `NetworkStore` record pointing at it.

**Why this is serious**: `network_get` still finds the old `NetDef` by prefix; a SUBSEQUENT `network
create` with a different prefix can hit `NetworkPrefixConflict`
(`infra.rs:6616`) because of a resource that, from the operator's point of view, no longer exists (`network ls` no
longer shows it). This is a stuck network resource, silently unavailable,
with no obvious command to recover it — the same "state needed to rebuild the
resource must be persisted" class this repo has already catalogued several times, here in reverse: the
state needed to UNDO the resource did not survive the failure.

**File/function to fix**: `crates/adapters/delonix-sdn/src/netops.rs::remove` (line 88)
— either invert the order (dataplane first, record only removed once confirmed) propagating the error instead
of swallowing it, or keep the current order but **do not remove the record** when the dataplane
fails (leaving the resource visible in `network ls` for a manual retry/diagnosis, instead of
disappearing from the operator's view while the physical `NetDef` persists).

**Acceptance test**: a unit/chaos test that forces `infra::network_remove` to fail
(lock unavailable/locked file) and requires (a) that `network ls` CONTINUES to show the network
(or an explicit "removal failed" state), and (b) that a subsequent `network create` with a
different prefix is not refused by `NetworkPrefixConflict` coming from a `NetDef` that no longer
has an owner.
