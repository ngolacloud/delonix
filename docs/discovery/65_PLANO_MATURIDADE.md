# delonix-runtime maturity plan — every domain the engine promises

> **What this document is.** The plan to bring every domain the engine
> declares it offers to a level where a critical node can be put on top of
> it. Every item has a **measured exit criterion**. An item with no
> measurement does not close.
>
> **What it is not.** A wish list, nor a calendar estimate. The sizes (S/M/L)
> order the work; they do not promise dates.
>
> **Relation to what already exists.** It does not replace the 13-improvements
> program (`docs/roadmap/13-improvements-traceability.md`, M01–M13). That
> program organizes the work by *product axis*. This one organizes it by
> *functional domain*, with ADR-0050's capability catalog as the common
> denominator. Each item below says which M it belongs to. State continues to
> be recorded in the traceability matrix, in the same commit that changes it.

| Field | Value |
|---|---|
| Baseline measured on | **2026-10-02** |
| Against | `origin/main` `a0d683c6`, engine **4.5.0**, capability catalog **1.3.0** |
| Matrix source | `docs/providers/capability-matrix.md` (generated by `delonix provider matrix`) |
| Compatibility | `delonix compatibility docker` and `delonix compatibility compose` (binary 4.5.0) |

## 1. What «mature» means here

«Mature» is not an impression. It is a verifiable property of each **cell**
(capability × provider that declares it) of the catalog:

| Level | Name | Requires |
|---|---|---|
| **N0** | Missing | `not-implemented` |
| **N1** | Implemented | code and unit test; `partial` in the matrix |
| **N2** | Proven | `supported`, with named evidence (`check:`, `e2e:`, `chaos:`, `live:`) that the evidence gate confirms exists |
| **N3** | Production | N2 **and** the FAILURE path also proven (a chaos scenario or a refusal check with an exit-code class), **and** observable (an event or metric that says it failed), **and** documented for the user |
| **N4** | Guaranteed | N3 **and** run recurrently on a runner that actually executes it (not `skipped`), with a regression that turns red |

**A domain is mature when all its applicable cells are at N3**, and the whole
domain runs in a recurring job (N4) with the result published.

Two rules this repository has already paid dearly for, and that apply to the
whole plan:

1. **Green from not running does not count.** GitHub's hosted-runner chaos
   job stays green by skipping everything, because they block unprivileged
   user namespaces. A cell is only N4 if the log shows the case actually ran.
2. **"Done" = merged + gate + real proof.** A list of «not validated» does
   not close an item. Either it is measured, or the item stays open with the
   reason.

## 3. The common cause: why 63% of the cells are not proven

Measured: there are **88 `partial` cells**, **64 `not-implemented`** and **14
`requires-external-component`**. Reading the matrix line by line, the cells
below N2 fall into **four causes**. Splitting the 88 partials across C1–C3 is
a reading of the reason written in each cell, so it is approximate; the
total is not. The plan attacks the causes, not the cells one by one:

| Cause | Cells affected (approx.) | Example | Remedy |
|---|---|---|---|
| **C1 — Implemented, with no check naming it** | ~45 of the 88 partials | `vm.destroy`/`vm.restart` on CH and libvirt; `vm.pause` on CH; `pod.shared-ipc-uts` | Write the check. Cheap and high-return (Wave 1) |
| **C2 — The battery never enters a guest** | ~15 of the 88 partials | `vm.cloud-init`, `vm.ip.observed`, `vm.console.serial`, `vm.guest-agent` on libvirt/CH | A minimal test image that boots and responds, and a runner with KVM (F0.3) |
| **C3 — Needs hardware or infra the lab does not have** | ~28 of the 88 partials | PCI passthrough (IOMMU), GPU/CDI, NFS with CAP_SYS_ADMIN, multi-node fabric, overlay between two nodes | Dedicated lab (F0.3), or declare out of scope |
| **C4 — Not implemented** | 64 (measured) | `vm.hotplug`, `pod.shared-pid`, `net.lb.l4`, `storage.lvm-thin`, `firewall.icmp-type`, `host.capacity` | Implement **only** what passes the scope decision (§5) |

**Consequence for the plan's order**: C1 and C2 take the engine from 37% to
close to 60% of cells proven without a single line of new functionality.
Building new functionality before that increases the denominator and lowers
the percentage.

### F1 — Wave 1: turning implemented into proven (C1 + C2)

New functionality: none. Only checks, scenarios and assertions.

| Domain | Items | Exit criterion |
|---|---|---|
| VM compute | `vm.destroy`, `vm.restart` (CH, libvirt); `vm.pause`/`vm.resume`/`vm.resize.cold` (CH); `vm.disks.extra`/`vm.nics.extra` (libvirt, booting the domain); `vm.cpu.model`, `vm.cpu.pinning`, `vm.memory.hugepages` (read from the live domain) | each `supported` cell with its own `check:` |
| Guest (via F0.4) | `vm.cloud-init`, `vm.ip.observed`, `vm.console.serial`, `vm.guest-agent` (libvirt, CH) | a real guest login in the battery |
| Containers | `container.oom-detection` (`scen_oom` now requires `OOMKilled`); `pod.shared-ipc-uts` (read `ipc`/`uts` from the members) | an assertion in the scenario that fails when the code is reverted |
| Protection | `vm.backup.disk`/`vm.backup.restore` on CH and libvirt, with the destroy → restore → data-came-back cycle | check of the full cycle |
| Mobility | `vm.migration.cold` on CH and libvirt between two roots on the same host | check that confirms the disk on the destination |
| Networking (linux) | `net.static-ip`, `net.dns`, `net.l7-proxy`, `net.vlan`, `net.capture` | one check per cell proven by the dataplane, not by the command's output |
| Firewall (linux) | `firewall.default-deny`, `firewall.source-filtering`, `firewall.egress-policy`, `firewall.workload-peer` | real traffic blocked and allowed, with the rule counters read |
| Firewall (proxmox) | the four `scope: vm` / `scope: systemcontainer` lines | a packet crossing and being cut on a lab VM |
| Inventory | `provider.availability` (the host probes in `provider ls` with a check) | check per provider |
| Access | `access.transport-verified`, `access.credential-in-vault` | a check that refuses unverified TLS without the flag and confirms the credential read from the vault |

**F1 exit**: cell metric ≥ **60%**, with no new `supported` cell lacking the
matching check that fails when the code is reverted.

### F2 — Wave 2: the failure paths (N2 → N3)

An N2 cell says the happy path works. For production, what happens on
failure must be proven too.

| # | Item | Exit criterion | M |
|---|---|---|---|
| F2.1 | A chaos scenario or refusal check for **every N2 cell** of containers, VMs, networking and storage: process killed mid-way, full disk, holder restarted, provider unreachable, revoked credential | «cell → failure scenario» table in `capability-matrix.md`; a gate that requires the pair | M04 |
| F2.2 | **Exit-code classes** on every failure path of N3 cells (4 does-not-exist, 5 conflict, 69 unavailable, 77 permission) | numeric check per path | M12 |
| F2.3 | **Events**: every N3-cell failure writes an event to `system events` with a `DX-` code | check that reads the event after the triggered failure | M07 |
| F2.4 | **`WatchEvents` served** in the node contract (closes `provider.events` on all four providers) | a gRPC client receives the event of a container that dies | M07 |
| F2.5 | **Asynchronous operations** for remote providers: a task handle exposed by the engine (generalizing Proxmox's task ledger) | `provider.async-operations` N2 on proxmox, decision written for the local ones | M10 |

### F3 — Wave 3: implemented gaps (C4), only the approved ones

Every item only goes in after passing the scope decision (§5) and, when it
touches a boundary, an ADR (`delonix-adr`).

| Domain | Candidates | Notes |
|---|---|---|
| Containers | `pod.shared-pid` | the field is already in the schema |
| VMs | `vm.clone` and `vm.template` (libvirt, CH); `vm.disk.resize`; `vm.hotplug` | hotplug is the most expensive one; assess demand first |
| System containers | backup and firewall to N2; image with layer sharing | `exec`/logs/exit remain out of scope: the Proxmox API does not have them (ADR-0058) |
| Networking | `net.overlay.vxlan`/`encrypted` proven between **two real nodes**; `net.dns.records`/`authoritative` (ADR-0059's F5c); `net.apply.rollback` on linux; `net.verify.dataplane` | proof between two nodes needs F0.3 with two hosts |
| Gateway (opnsense) | `update-in-place`, `nat.one-to-one`, `vpn`, `multi-wan`, `ipam.reservation`/`dhcp` | by order of actual demand |
| Firewall | `firewall.logging` and `firewall.icmp-type` on linux | per-rule logging is what diagnostics is missing |
| Storage | `storage.pools` (libvirt, CH), `storage.lvm-thin`, `storage.zfs-btrfs`; provisioned CIFS | decide first whether the engine manages pools or only consumes them |
| Metrics | `metrics.prometheus` per provider, `host.capacity` | `host.capacity` is what an external scheduler needs |

## 5. Owner decisions (made on 2026-10-02)

The eight approved for implementation and validation. Each one that changes
a boundary (D2, D3, D4, D8) goes through an ADR before code, as `delonix-adr`
mandates.

| # | Decision | Chosen | How it closes |
|---|---|---|---|
| D1 | A lab that actually executes | **Yes** | nightly workflow on a self-hosted runner (`delonix-lab`) and a preflight that fails if the host lacks KVM, userns, delegated cgroup and `br_netfilter`. Registering the runner is a step for the owner |
| D2 | Storage | **The engine manages pools** (LVM-thin, ZFS/btrfs) | ADR + storage port + Kind; cells `storage.pools`, `storage.lvm-thin`, `storage.zfs-btrfs` |
| D3 | L4 load balancing | **In the engine** | ADR + nftables dataplane (vmap/numgen) + health check; `net.lb.l4`, `net.lb.health-check` |
| D4 | IPv6 in the dataplane | **Implement** | ADR + `table inet` + IPAM v6 + AAAA DNS; `net.ipv6`; the current refusal becomes opt-out |
| D5 | `br_netfilter` missing | **Refuse** the isolation that would not be enforced | error with class 69 before creating the workload, explicit escape hatch, check in the battery |
| D6 | `--wait` timing out | **Exits with an error** | non-zero exit with its own class, breaking-change note in the next major |
| D7 | Live migration, fleet management, HA, replication | **Out of scope, confirmed** | cells keep the reason written (ADR-0031, ADR-0010, external component) |
| D8 | VM hotplug | **Yes** | ADR + hot CPU/memory/disk/NIC on the backends that support it; `vm.hotplug` |

A cell withdrawn by decision becomes `unsupported-by-provider` with the
reason, never disappears from the matrix.

## 7. Governance

- **One task = one worktree = one PR**, per the workspace's `CLAUDE.md`.
- **The traceability matrix is updated in the same commit** that changes the
  state. So is this plan: each closed phase updates §2 with the date and the
  commit of the measurement.
- **Per-phase review** with the `revisor` agent (correctness) and, from F2
  on, with the `delonix-producao` skill (blast radius and failure direction).
- **Per-domain owners** (repo skills): containers `delonix-runtime-container`,
  VMs `delonix-runtime-vm` + `delonix-provider-lifecycle`, networking
  `delonix-runtime-network`, IaC `delonix-runtime-stack`, images
  `delonix-runtime-image`, testing `delonix-testing`, load `delonix-carga`,
  security `delonix-runtime-sec`.
- **Nothing from the consumer enters the engine.** An item motivated by a
  consumer is written as an engine capability, in its Kinds' vocabulary, or
  it does not go in (`AGENTS.md`, «What the engine does not know»).
