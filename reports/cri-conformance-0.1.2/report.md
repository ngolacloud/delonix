## Real findings (original backlog detail)

### CRI-F1 — `RemoveImage` is not idempotent under simultaneous calls
- **Spec:** `[k8s.io] Image Consistency … should not fail on simultaneous RemoveImage calls [Conformance] [Serial]` (`pkg/validate/image_consistency.go:171`).
- **Observed:** two concurrent `RemoveImage` on the same image → the 2nd returns
  `rpc error: code = Internal desc = I/O error: No such file or directory (os error 2)`.
  CRI requires that simultaneous removals **not** return an error (the image
  already having been removed is success, not `Internal`).
- **Expected:** `RemoveImage` tolerates the absence (ENOENT) and returns a handled
  OK/NotFound, not a raw I/O error. **Tier:** B. **Area:** `delonix-cri` image service.

### CRI-F2 — dropping ALL capabilities breaks exec (`setgroups([]) failed`)
- **Spec:** `[k8s.io] Security Context … runtime should support dropping ALL capabilities` (`pkg/validate/security_context_linux.go:593`).
- **Observed:** with all caps dropped, the container fails with
  `delonix: exec setgroups([]) failed`. Without `CAP_SETGID`, the exec path's
  `setgroups([])` call is refused (EPERM) — and **this ties into BUG-0008**
  (unconditional setgroups): the fix made `setgroups` always called, but when
  `CAP_SETGID` is dropped that call is no longer permitted.
- **Expected:** when `CAP_SETGID` is not in the effective set (or without
  `group_add`), **skip** `setgroups` or tolerate EPERM, rather than aborting the
  exec. **Tier:** B. **Area:** `delonix-linux` exec/init (same area as BUG-0008).

## Verdict
`delonix-cri 0.1.2` passes **97%** of upstream CRI conformance in a real rootful
lab — a **measured** number, no longer BLOCKED. **2 real gaps** remain (CRI-F1
RemoveImage concurrency, CRI-F2 drop-all-caps/setgroups) for the backlog, plus
one environmental failure (image pull) that is not the engine's. The rootful path
(CRI+CNI+cgroup2+AppArmor) is **proven on this host via a disposable VM**.
